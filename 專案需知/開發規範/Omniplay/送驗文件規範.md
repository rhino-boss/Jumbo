# 送驗文件規範

本文件屬於 `專案需知/` 專案需知文件集，總覽、共通原則與完成條件見 [_README.md](../../其他/_README.md)。

內容涵蓋送驗（BMM 等實驗室）交付物的命名、格式來源、內容規則、禁止內容與交付前檢查：**Game Description**、**Math Document Description**、**數學模型送驗版**、**SHA1 清單**。本文件適用 **OP 遊戲**（Game ID `101xxx`）。

送驗**流程面**（歸檔、Draft／Letter 檢查、OP Jackpot 報告要求）另見送驗根目錄 `\\192.168.139.6\JIG_Certification\送驗\送驗規範\送驗規範.md`。該文件是送驗的完整版，第 1～4 章與第 5 章的「送驗文件檢查清單」即本文件內容，修改本文件時必須同步過去（該文件第 7 章 Game List 對應[數學文件規範.md](數學文件規範.md) 第 4 節）。

- Help、`game_description.md` 的內容規範見[數學文件規範.md](數學文件規範.md)；Game List 見[數學文件規範.md](數學文件規範.md) 第 4 節；PARsheet 精簡文件見[數學文件規範.md](數學文件規範.md)。本文件只規範送驗交付面的要求。
- 製作與檢查的操作流程由對應 skill 執行（製作 Game Description：`game-description-generator`；檢查送驗文件：`math-doc-checker`）；規範內容以本文件為準，skill 與本文件不一致時，先修正其一使兩者一致。

**存放位置**（路徑以遊戲專案資料夾 `Slots/H0xx_遊戲名稱/` 為準）：

| 檔案 | 存放位置 |
|---|---|
| `{GameID}_Game Description.docx`（完整版） | `文件/` |
| `{GameID}_Math Document Description.md`＋`_EN.md` | `文件/`（送驗時只把 `_EN.md` 複製進送驗資料夾，中文版不送） |
| 送驗資料夾（送驗版 Game Description、`PARsheet/`、`Simulator/`） | `文件/{GameID}/` |
| 
## 1. 通用原則

### 1.1 一款遊戲的送驗產出

一款遊戲送驗時要產出下列內容：

```text
{GameID}/
├─ {GameID}_Game Description.docx
├─ {GameID}_Math Document Description_EN.md
├─ {GameID}_SHA1.txt
├─ PARsheet/
│  └─ H0xx19x.xlsx
└─ Simulator/
   ├─ Simulator.py
   └─ config_9x.js
{GameID}.zip
備份/
└─ {GameID}_YYMMDD.zip
```

| 產出 | 說明 |
|---|---|
| `{GameID}_Game Description.docx` | 送驗版，移除 1.3 禁止項目（第 2.4 節） |
| `{GameID}_Game Description_No Progressive.docx` | 使用非 OP 彩金的遊戲才有，移除彩金章節（第 2.4.5 節） |
| `{GameID}_Math Document Description_EN.md` | 英文數學說明（第 2.3 節）；**中文版不放入送驗包** |
| `{GameID}_SHA1.txt` | 資料夾內所有檔案的 SHA1 清單，每次打包前重產（第 1.5 節） |
| `PARsheet/H0xx19x.xlsx` | **數學模型送驗版**，每個送驗 RTP 版本一份（第 2.1 節） |
| `Simulator/` | `Simulator.py` 與各 RTP 版本的 `config_*.js`（第 2.2 節） |
| `{GameID}.zip` | 整個 `{GameID}/` 的最新壓縮檔，不加日期 |
| `備份/{GameID}_YYMMDD.zip` | 同一份壓縮檔的日期版，保留歷史 |

- `PARsheet/` 是送驗的既定資料夾名稱，內容物是**數學模型送驗版**：由 `Source/*.xlsx` 移除 1.3 禁止項目後另存，其餘數學內容與正式數學模型一致。它不是[數學文件規範.md](數學文件規範.md)定義的 PARsheet 精簡文件。
- 送驗包只有一個 zip，不另建 `{GameID}_note/`：流程圖、計算器、原始模擬資產等附屬檔案也放進 `{GameID}/` 一起打包，並列入 SHA1 清單。
- 製作順序：Game Description、Math Document Description、數學模型送驗版、Simulator 備齊後，先產 SHA1 清單，再打包兩個 zip。

範例：`260806_BMM送驗_101014_101025/101014/`。

### 1.2 必要檔案與命名

| 文件 | 檔名規則 |
|---|---|
| Game Description | `{GameID}_Game Description.docx`，無其他前後綴；無彩金版為 `{GameID}_Game Description_No Progressive.docx` |
| Math Document Description | `{GameID}_Math Document Description_EN.md`（只送英文版） |
| SHA1 清單 | `{GameID}_SHA1.txt`，格式見第 1.5 節 |
| 數學模型送驗版 | 檔名為 ParSheet ID＋RTP，無變體字母（例：`H026192.xlsx`） |
| Simulator | `Simulator.py`、各 RTP 版本的 `config_*.js` |

- Game ID 以 `iGaming 遊戲代號一覽.xlsx` 為準，查得英文名稱、中文名稱、ParSheet ID 與 Extra Bet／Buy Feature／Super Feature 支援情況。
- ParSheet ID 前 4 碼（例如 `H026`）對應 `Slots/` 下的 `H0xx_遊戲名稱` 專案資料夾。
- 文件內出現的遊戲英文名稱必須與代號一覽一致；檔名前綴必須與 Game ID 一致。
- 代號一覽查不到該 Game ID 時，先確認來源，不得逕行送驗。

### 1.3 禁止出現的內容

送驗版三份文件內，下列內容一律不得出現（不分大小寫搜尋，含表格儲存格）：

| 檢查項目 | 關鍵字 |
|---|---|
| Extra Bet 敘述 | `extra bet` |
| Buy Feature 敘述 | `buy feature` |
| Super Feature 敘述 | `super feature` |
| >$2 拉彩金門檻 | `>$2`、`> $2`、`bet $2`、`$2 or more`、`more than $2` |
| 新手卡組內容 | `newbie`、`新手`（工作表 `Detail_Newbie`、欄 `Weight_NB_*_Newbie`、SCR 列 `NB_Newbie`、config 的 `newbie` 卡組段） |

找到即為錯誤，必須移除後才可送驗。

- 新手卡組屬內部營運機制，不隨遊戲送驗：數學模型送驗版、送驗包 config、Math Document Description（中英）內一律移除。
- 送驗包 `Simulator.py`、`config*.js` 的禁止內容與報表檔名規則見第 2.2 節。

### 1.4 用詞一致性

用詞不一致不會讓數值出錯，但送驗時容易被挑，屬警告等級（明顯錯字升為錯誤）：

- **單一文件內部**：同一概念不得混用大小寫／連字號／空格變體（`GOLD-FRAME` vs `GOLD-FRAMED`、`Free Game` vs `FreeGame`）、單複數（`Free Spin` vs `Free Spins` 同語境混用）或同義換名（同一機制一下 `Free Game`、一下 `Free Spin`；一下 `Wild`、一下 `Joker`）。
- **跨三份文件**：功能名稱、符號名稱、RTP 分類名（Base Game／Free Game／Bonus／Link）在 Game Description、Math Document Description、PARsheet 之間必須同名。
- **中英對照**：同一中文概念只對應一組英文譯名（「免費遊戲」不得一處對 `Free Game`、另一處對 `Free Spin`）。

### 1.5 SHA1 清單

送驗報告（BMM 的 Draft／Letter）會逐檔列出送驗檔案的 SHA1 並據以認證。我方必須在送驗包內留一份對應清單 `{GameID}_SHA1.txt`，日後報告的 SHA1 表才有東西可比；被質疑時能立刻證明「BMM 驗的是不是我們手上這一份」。

**規則**

- **每一次產出送驗壓縮檔前都要重產清單，且清單要一起打包進 zip**。順序固定：先產清單，再打包；否則 zip 內的清單會是舊的或缺漏。
- 清單涵蓋送驗包內**所有送驗標的**（Game Description、Math Document Description、`PARsheet/*.xlsx`、`Simulator/*`）；不列入清單本身，排除 `~$` 開頭的 Office 暫存檔與 `__pycache__/`。
- 路徑用**相對於遊戲資料夾**的形式（含子資料夾，如 `PARsheet\H026192.xlsx`），依相對路徑排序。
- SHA1 為 40 碼**大寫**十六進位；`Generated` 填產生當天，`MODIFIED` 填檔案自身的修改時間。
- 檔案一律**二進位複製**，不得開啟後另存：xlsx／docx 重存會改變位元組，SHA1 就與 BMM 認證的對不上。落地後逐檔重算 SHA1 確認與來源相同。
- 換掉已被報告認證的檔案，等於讓該報告的 SHA1 失效：已有 Draft 的要請 BMM 依新版重出，已有 Letter 的先確認是否真的要動。
- 產完清單掃一眼有無**重複雜湊**：不同檔案不該有相同 SHA1（實例：106003 的 `H506R_MSweight_BG.xml` 與 `_FG.xml` 雜湊相同，BG／FG 權重被交付成同一份檔案）。

**格式**（沿用 `101025_SHA1.txt` 的既有慣例）

```text
{GameID} - {遊戲英文名}
SHA1 Checksum List
Generated: YYYY-MM-DD
Files: N

SHA1                                      FILE                           SIZE  MODIFIED
----------------------------------------  ---------------------------  ------  ----------------
5833C832A7E8A64FC3C9FB32F7F9DDA0C98FFC33  101016_Game Description.docx  2364965  2026-09-17 13:35
6EF35C67189982DE0572F0FFD7473BBC470F57C9  PARsheet\H0281.xlsx            746614  2026-09-24 12:09
A945E93DD2599D8607982582F8518E0E56E38C8A  Simulator\Simulator.py         143813  2026-09-24 14:12
```

**產出**：用 `submission-organizer-ctool/scripts/make_submission_zip.py` 一次完成「產清單 → 批次根目錄無日期 zip → `備份/` 日期 zip」；兩個 zip 內容相同且都含清單。

**比對報告時的兩個坑**（詳見送驗規範 6.3）：pdftotext 會把 40 碼雜湊拆行，不得用長度篩選 token；SharePoint／OneDrive 會加 `customXml` 標記改變 docx 的 SHA1 但 `word/document.xml` 不變，不符時先做 OOXML part 層級比對，不要直接判為 BMM 出錯。

## 2. 送驗文件

### 2.1 數學模型／PARsheet

送驗包 `文件/{GameID}/PARsheet/` 內的 `.xlsx` 是**數學模型送驗版**：以 `Source/*.xlsx` 為基礎，移除 1.3 禁止出現的項目（Extra Bet／Buy Feature／Super Feature 與 >$2 門檻相關的工作表、欄位與敘述，以及新手卡組——`Detail_Newbie` 工作表、`Multiplier_Weight` 的 `Weight_NB_*_Newbie` 欄、OP Jackpot 的 `NB_Newbie` 列）後另存。數學模型本體的規範見[數學模型規範.md](數學模型規範.md)；送驗交付面另要求：

**RTP 版本檔的工作表**（2026-10-15 起，H027 首例）：`Overview`、`Multiplier_Weight`、`Avg_Multi`、`Nature_Prob`、`OP Jackpot`。

- `Avg_Multi`（各得分倍率區間的平均倍率）**必須保留**，與 `Multiplier_Weight` 同列對應，只留送驗欄位（例 `Avg_Multi_NB_BG`／`Avg_Multi_NB_FG`；Newbie／EB／BF 欄依 1.3 移除），版面與 `Multiplier_Weight` 一致、數值格式 `0.0000`。審查端可用 `Σ（權重 × 平均倍率）÷ 10⁹` 直接核對 BG 派彩率與 FG 平均倍數。
- `Nature_Prob`（各區間的自然發生機率）同樣**必須保留**，欄位與版面規則同 `Avg_Multi`，數值格式 `0.0000%`；BG 欄各區間合計 100%，`Free Game` 列為自然 FG 觸發率。
- Math Document Description 的工作表一覽與 Multiplier_Weight 章節須同步說明 `Avg_Multi`、`Nature_Prob` 的欄位與核對方式。

#### 2.1.1 Overview 必要欄位

Overview 以三個表格呈現（H028 送驗版起的定版版面），以下欄位必須存在且有值：

| 表格 | 欄位標題 | 內容 |
|---|---|---|
| Coin in 表 | `Coin in`｜`Price(x)`｜`Total RTP`｜`Bet Type` | Normal Bet 一列；此處 `Total RTP` 為遊戲本身 RTP（Game RTP） |
| 彩金列（Coin in 表後空一列） | `Bonus RTP`｜`Link RTP`｜`Total RTP`｜`Hit JP Symbol appear rate` | Bonus／Link 派彩率、含彩金總 RTP（=Game+Bonus+Link）、JP 判定符號出現率（取模型 OP Jackpot 表 NB 列，Threshold 10,000,000,000） |
| Total Pay Back 表（彩金列後空一列） | `Bet Type`｜`Pay Back`｜`Hit%`｜`Pulls/Hit`｜`Description` | Base Game／Free Game 兩列拆解：BG RTP、FG RTP、命中率、免費遊戲週期（Pulls/Hit） |

- 版面格式：三表沿用模型既有樣式（灰底表頭、值列白／桃交錯、完整框線、字體與全簿一致）；RTP 類數值一律以 `0.00%` 百分比格式顯示（92.00%、2.00%、96.00%、72.00%…），`Pulls/Hit` 顯示兩位小數。
- 覆蓋的必要資訊：BG RTP、FG RTP、Bonus RTP、Progressive／Link RTP、免費遊戲週期、Scatter（JP 判定符號）出現機率——六項缺一不可。

> 以程式讀取檢查時，含公式的儲存格可能讀為空值；此時以人工開檔確認，不得直接判為缺漏。

#### 2.1.2 跨文件賠率一致性

- Game Description 的符號佔位符與數學模型送驗版的符號代號**按順序對應**（`[M1]`↔`W1`、`[M2]`↔`W2`，以此類推）。
- 逐符號比對 3 連、4 連、5 連的賠率值，任何不一致即為錯誤。
- 同一遊戲的多份數學模型送驗版（不同 RTP 版本）之間，非 RTP 差異欄位（如 Link Pay Back 設計）必須一致或有明確理由。

### 2.2 模擬程式

送驗包 `Simulator/` 放 `Simulator.py` 與各 RTP 版本的 `config_*.js`（`config.js` 基礎檔若有也放入），由正式版本的 Simulator／Config 去除禁止內容後產出。

- 送驗包 `Simulator.py` 與 `config*.js` 同樣不得含 1.3 禁止內容（2026-10-15 起，H027 首例）：Extra Bet／Buy Feature／Super Feature／新手卡組的程式碼、設定、註解與報表欄位，以及押注分層（$2 門檻）與內部彩金模擬一律移除，只保留 Normal Bet 路徑。移除後須以相同亂數種子與完整版 Simulator 比對，Normal Bet 輸出逐項相同；並在模擬機跑 1e8 局確認 RTP 與 SCR 與送驗模型一致。
- 送驗包 `Simulator.py` 的報表檔名使用**送驗模型 ID（無變體字母，例 `H028192`）**，與送驗模型檔名一致——這是對[模擬程式規範](../模擬程式規範.md) 1.1「完整 RTP／Variant Game ID」的送驗專屬例外；以送驗包模擬器產出的報表若要收進專案 `Record/`，檔名須改回完整變體 ID（例 `H028192A`）。

### 2.3 Math Document Description

#### 2.3.1 定位與範本

針對數學文件（`Source/*.xlsx`）的說明文件：說明各工作表用途與程式讀取範圍、Parameter 參數、遊戲邏輯與卡片系統。

- 製作 Markdown 雙語兩檔：`{GameID}_Math Document Description.md`（中文）與 `{GameID}_Math Document Description_EN.md`（英文），兩版內容須同步，存放在 `文件/`。
- **送驗只提供英文版**：`_EN.md` 複製進 `{GameID}/` 送驗資料夾並列入 SHA1 清單；中文版僅供內部查閱，不放入送驗包（2026-10-15 起，H027 首例）。範本參考 `H026_彩罐熱舞 1000/文件/101014_Math Document Description.md`。
- 過往他人專案曾以 DOCX 交付；新專案一律採 md＋`_EN.md` 格式。

#### 2.3.2 內容要求

- 開頭為基本資訊表：Game ID、Math files、Version、對應程式（Simulator／Config）、盤面、線數／得分方式、Coin In、押注模式。
- 四大章：①工作表說明（每張工作表標明程式是否讀取）②Parameter 工作表的遊戲參數說明 ③遊戲邏輯（spin 流程、判獎、Cascade、FG）④卡片系統說明。
- 公式／變數名稱：必須定義 `Ptheory`、`Pscatter`、`Phit`；`Phit` 公式必須使用 `Pscatter`（不得寫成 `Prespin`、`Presipn` 或其他變體）。
- 建議附上 Total RTP、Window Size、Denom 等欄位的實際數值。
- 禁止內容同 1.3。

### 2.4 Game Description

送驗用的 Game Description 以[數學文件規範.md](數學文件規範.md#22-docx-完整版)的完整版為基礎，移除 1.3 禁止項目（Extra Bet／Buy Feature／Super Feature 與 >$2 門檻相關章節與敘述）後產出；除刪減處外必須與完整版完全一致。

#### 2.4.1 格式來源：複製已核准模板

格式（字型、字級、邊界、標題與表格樣式）一律**複製既有已核准的 Game Description 文件**，不重新自建格式——公司對格式的核准是一次性的，自行重建有偏離已核准樣式的風險。

已知兩種版型，依模板實際版面選擇：

| 版型 | 特徵 | 用途 |
|---|---|---|
| A：純段落 | 每行規則為一般未條列段落 | 一般範例（`H000_範例`） |
| B：■ 條列＋框線賠率表 | 每行規則前有 ■（Word 編號清單），賠率表在框線表格內 | BMM 送驗版常用 |

- 選模板時避免內嵌整頁背景圖或遊戲 Logo 的文件，否則舊遊戲的美術會帶進新文件。
- 版型判斷以模板實際內容為準，不假設所有模板結構相同。

#### 2.4.2 內容來源：Help 英文欄逐字填寫

- 內容以該遊戲的 `{GameID}_Help.xlsx` 或 `game_help_draft.md` 的**英文欄逐字填寫**，不得改寫、摘要或自創文字——Help 是已核准的規則措辭唯一來源，改寫會製造兩份互相矛盾的文件。
- **一律使用英文欄**：簡中欄曾出現英文欄沒有的錯字（例如符號誤標 `[M4]`，英文欄正確為 `[M5]`）。
- 去除行首手動 bullet 字元（`▪`／`•`）；版型 B 的 ■ 來自模板的清單樣式，不是文字本身。
- 佔位符（`[WW]`、`[C1]`、`{12}`、`X2` 等）原樣保留；`{n}` 花括號要嘛全篇保留、要嘛全篇展開為實際數字，不得混用。
- 保持 Help 的章節順序，不重排、不遺漏；純圖片佔位列（`[走線圖 ...]`、`[跳階示意圖]`）跳過。
- Help 的章節外層標籤對應輸出的 Heading 2；注意慣例差異（Help 寫 `GAME RULE`，文件慣例為 `GAME RULES`），依既有文件慣例為準，不盲抄。

#### 2.4.3 結構

- **不放圖片**：Game Description 內一律不放任何圖片（符號圖、盤面圖、走線圖、示意圖）；需要舉例時，符號一律用代號文字表示（`M1`、`M2`…），不用圖片。
- Title 樣式段落「GAME DESCRIPTION」＋置中一般樣式段落放遊戲英文名。
- 每個 feature／規則章節一個 Heading 2（PAYTABLE、CASCADING FEATURE、MULTIPLIER FEATURE、FREE GAME FEATURE、OP JACKPOT、GAME RULES 等，依遊戲實際內容）。
- 副標籤（`WILD SYMBOL`、`SCATTER SYMBOL` 等）使用一般段落樣式，不自創粗體或 Heading 3 樣式。
- 賠率表為 3 欄表格，每個 payout tier 一列。

#### 2.4.4 交付前驗證

- 重新解析輸出文件（逐段樣式＋文字、逐表格列），確認：Help 的每個章節都已進入文件、賠率表列數與 Help 的 payout tier 數一致、無殘留 placeholder（`__TABLE__`、`None`、空 run）。
- 執行 1.3 禁止內容檢查與 1.4 用詞一致性檢查，並確認除刪減處外與完整版完全一致。

#### 2.4.5 有彩金遊戲的 No Progressive 版

- **適用**：使用非 OP Jackpot 彩金的遊戲，都要出兩份 Game Description。使用 OP Jackpot 的遊戲只出一份。
- **檔名**：含彩金版為 `{GameID}_Game Description.docx`，無彩金版為 `{GameID}_Game Description_No Progressive.docx`。一律使用 `No Progressive`，不得使用 `No Link` 或其他寫法。
- **No Progressive 版的內容**：移除彩金相關的章節與敘述（Progressive／Jackpot／Link 的規則、觸發條件、獎項與 RTP），其餘內容與含彩金版逐字相同。
- 兩份都依 2.4.1～2.4.4 製作與驗證，並都列入 SHA1 清單。
