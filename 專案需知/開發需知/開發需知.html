4. 開新專案必讀流程

開啟新的遊戲專案（或接手既有模型改版）前，必須依下列順序讀完相關規範：

  1. 本 README：共通原則與完成條件。
  2. 開發流程.md：整體流程、製作順序與階段關卡。
  3. 數學模型規範.md：建立數學模型與 Card System 前必讀。
  4. 數學文件規範.md：撰寫 Game Rule、Help 等文件前必讀。
  5. 送驗文件規範.md：製作 Game Description DOCX、Math Document Description 與數學模型送驗版前必讀。
  6. 模擬程式規範.md：撰寫 Simulator 與產生 Config 前必讀。
  7. Demogame規範.md：製作 Demogame 前必讀。
  8. 腳本規範.md：製作表演腳本前必讀。
  9. 提案報告規範.md：製作提案報告（提案說明簡報）前必讀。
  10. 壓測說明書.md：安排後端壓測與判讀壓測報表前必讀。
  11. 後端報表.md：核對後端 SPS 報表（倍率權重、Card System）前必讀。

只執行部分工作時，至少要讀完本 README 與該工作對應的文件。

5. 維護規則：HTML 同步

本資料夾最外層的 igaming_specification.html 是入口，上方切換 Omniplay／Landbase／Reskin／開發需知；各產線網頁放在各自資料夾：開發規範/Omniplay/omniplay_specification.html（Omniplay 全部 md 合併、頁籤式）、開發規範/Landbase/landbase_specification.html、開發規範/Reskin/reskin_specification.html、開發需知.html，皆由 _build_html.py 從 md 自動產生。

  • 任何一份 .md 更新後，必須在同一次修改中重跑產生器同步 HTML：
  py _build_html.py
  • 不得直接手改任何一份彙整版 HTML；內容修正一律改 md 再重建。
  • 產線資料夾內的 .md 連到 Omniplay 規範時寫 ../Omniplay/檔名.md，產生器會轉成 Omniplay 網頁的對應頁籤。

6. 共通原則

數學文件／XLSX
      ↓ AI 轉檔與驗證
    Config
     ├─→ 模擬程式 → Record 報表
     └─→ Demogame  → 操作與逐局對帳
  • 數學文件與 Source/*.xlsx 是規格來源，Config 是程式執行時的共同參數來源。
  • Excel 與 Config 之間的轉換（含 game_help_draft.md → {GameID}_Help.xlsx、數學模型 → PARsheet）一律由 AI 執行；專案內不建立、不維護轉檔工具。
  • 模擬程式與 Demogame 必須讀取同一份 Config，不得各自維護另一套輪帶、權重、Paytable 或 Feature 參數。
  • game_rule.md 必須說明玩法、判獎順序、倍率口徑、Feature 流程與例外；程式不可補猜未定義的規則。
  • Game Rule 是遊戲規則的正式說明來源；數學模型、程式與 Help 必須與其一致。
  • Help 必須依 Game Rule 編寫，並同時維護 {GameID}_Help.xlsx 與對應的 Markdown 文件；兩者內容不得不一致。
  • 同一項資料若在多個檔案出現，修改時必須同步更新並完成對帳。
  • 未支援的 RTP、Variant、Bet Mode、Profile 或 Feature，不得出現在 Config、Simulator 批次或 Demogame 選單。
  • 會影響結果分布、RTP、觸發率、最大獎或 Retry 的修改，都必須更新版本並重新模擬。

7. 完成條件

模型只有在下列條件全部成立後才可視為完成：

  1. 數學規則與計算口徑明確，無未決定的核心邏輯。
  2. Config 可由數學來源重建，版本與參數可追溯。
  3. Simulator 已完成所有支援組合的統計驗證。
  4. Card System 的權重、區間、Retry 與失敗監控通過。
  5. Demogame 的代表性單局可與 Simulator 對帳。
  6. 開發流程.md 第 2 節的必要產出文件（game_rule.md、game_help_draft.md／{GameID}_Help.xlsx、game_description.md、數學模型／PARsheet、config.js、Simulator.py、index.html、數值報告_<遊戲中文名>.md＋.html、注意事項.md、{GameID}_Game Description.docx、{GameID}_Math Document Description.md＋_EN.md）全部齊備，與 Game List 均為同一正式版本，且必要的 Markdown 文件皆已同步更新。

2.1 修改紀錄格式

修改紀錄.md 放在專案根目錄，依版本分節、不以日期分節：

  • 每個四碼版本一節，標題寫 ## v<第 1 碼>（<四碼版本>），例如 ## v5（5.1.0.0）、## v5（5.0.0.0）；由新到舊排列。

5. 各階段操作方式

5.1 開案與數學目標確認

  1. 建立 H0xx_遊戲名稱/ 專案資料夾。
  2. 讀取並確認 game_rule.md。
  3. 與使用者確認本專案的數學模型組合——每款遊戲的數學模型都不一樣，不得逕自沿用他款設定。未特別說明時，預設組合為：
    • A／B 兩個 Variant × 92／94 兩個 RTP，乘開共 4 個版本（92A、92B、94A、94B）。
    • 每個版本都有 Newbie／Oldhand 兩種 Profile。
    • 各版本依其支援內容有對應的押注區（Oldhand 小／中／大 Bet 層級）。
  4. 列出所有正式支援組合：RTP、Variant、Profile、Oldhand 小／中／大 Bet、NB／EB 或 BF／SF 模式類別、Bet Mode、Card System Off／On。
  5. 為每個組合定義 Link／Bonus Game／Game RTP、Total RTP、Link 資格、Hit Rate、Feature Frequency、BG／FG Max Multiplier 與其他遊戲專屬指標。
  6. 將未決定的判獎順序、倍率分母、Feature 上限與例外退回確認；未確認前不製作正式模型。

5.2 建立基礎數學模型

  1. 先完成 Base Game，再依狀態順序完成 Feature。
  2. 建立 Symbol、Paytable、Reel Strip／Weight、Table 與 Bet Mode。
  3. 建立 BG、FG、Cascade、Multiplier、Retrigger、Jackpot 等流程。
  4. 計算 RTP Breakdown 與理論 Max Win，不只計算 Total RTP。
  5. 建立基礎數學 XLSX，版本依規格使用 1 碼。

5.3 建立 RTP／Variant 與 Card System

  1. 只建立 5.1 與使用者確認過的 92／94、A／B 組合（未特別說明時為 92A、92B、94A、94B 四版本，各含 Newbie／Oldhand 與對應押注區）。
  2. A／B 表示數學 Variant，不表示 Newbie／Oldhand。
  3. 依 Profile、Oldhand 小／中／大 Bet 與 Bet Mode 建立 BG／FG 卡片區間及權重；NB／EB 以實際模式押注、BF／SF 以 Feature 基礎押注選擇層級。
  4. 確認每張正權重卡片的區間可達，並定義 Retry 行為。
  5. 建立 RTP／Variant XLSX，版本依規格使用四段格式。

5.4 轉檔與 Config 驗證

  1. 在數學模型的 Game Description 工作表記錄每項 Config 資料的來源。
  2. 由 AI 依 Source 與 Mapping 轉出 Config；專案內不建立、不維護 Excel↔Config 轉檔工具。
  3. 執行欄位、型別、陣列長度、ID、Weight、Min／Max、版本與模式驗證。
  4. 比較轉檔前後資料，確認 Config 可由 Source 重建且沒有非預期差異。
  5. 轉檔錯誤時修正 Source 或 Mapping 後重新轉出，不直接修改 Config 大型陣列。

5.5 Simulator 開發與 Debug

  1. 先完成自然機率核心，再加入 Card System 篩選與 Retry。
  2. 讓 Simulator 直接讀取正式 Config，不另寫一份參數。
  3. 建立固定 Seed、單執行緒與逐局 Trace 模式。
  4. 建立強制／指定案例，驗證無獎、一般獎、Wild、Scatter、Feature、Retrigger、倍率與封頂。
  5. 小場次確認正確後，再加入 Numba、多執行緒、BATCH_RUNS 與 Excel 報表。

5.6 模擬順序

模擬必須依下列順序執行：

  1. 小場次、Card System Off：驗證流程與報表。
  2. 中場次、Card System Off：確認自然機率 RTP 與分布。
  3. 大場次、Card System Off：以 NB 10⁹ 局（BF 為 10⁸ 局）產出自然機率正式報表。
  4. 卡片權重調性校準：依上一步報表分配各得分區間的卡片權重，使分布、RTP 拆分與 FG 週期符合目標遊戲調性；完成後才進入 Card System On。
  5. 小場次、Card System On：確認抽卡、Profile、Oldhand 押注層級、Link 資格、倍率上限、Mode 與 Retry。
  6. 中場次、Card System On：調整區間、權重與目標 RTP。
  7. 所有正式組合的大場次模擬。
  8. Max Win、低機率 Feature 與 Retry 邊界的專項驗證。

1. Game Rule

Game Rule 是遊戲規則說明文件。

1.1 用途

Game Rule 用於設定遊戲玩法規則，是數學模型、Config、Simulator、Demogame、Help 與測試案例共同遵循的規則來源。

  • Game Rule 必須沿用本節定義的固定章節骨架、標題層級、表格形式及規則表達方式。
  • 數學模型、Config、Simulator、Demogame 與 Help 不得自行補充或改寫 game_rule.md 未定義的玩法。

  • Game Rule 與其他來源內容衝突時，必須先確認正式規則，不得由開發端自行選擇其中一種實作。

1. 模擬程式

Simulator.py 是數學模型的主要驗證工具。數學邏輯、批次設定、Console 輸出與 Excel 報表必須使用相同的統計口徑。

1.1 程式架構

1.1.1 加速：Numba、多執行緒

  • 高頻數學核心使用 Numba 編譯；適用的核心函式使用 @njit(nogil=True)。
  • 使用多執行緒平行執行模擬，例如 ThreadPoolExecutor；每個 Worker 必須持有獨立的 RNG 狀態。
  • 正式計時前先執行 Warm-up，Numba 首次編譯時間不得計入 duration。
  • Numba Core 只處理數值及固定型別 Array／Tuple；Config 解析、字串、DataFrame 與 Excel 留在 Python 層。
  • 預先配置統計陣列與暫存 Buffer，模擬迴圈內不得反覆建立大型物件。
  • 場次平均分配給各 Worker，餘數由前幾個 Worker 各多執行一場；合併後必須等於 total_rounds。
  • Worker 回傳相同 shape／dtype；Count 與 Pay 欄位相加，Max 欄位取最大值。
  • 固定 RNG、逐局 Trace 與 Debug 重現模式使用單執行緒。

1.1.2 程式邏輯

程式依下列順序執行：

  1. 讀取 BATCH_RUNS 的本批參數。
  2. 載入 config_file 的自然機率參數。
  3. 載入 config_rtp_file 的倍率權重參數。
  4. 驗證兩份 Config 的 game_id、版本與資料相容性。
  5. 將 Config 正規化為模擬核心使用的固定型別資料。
  6. 依 bet_mode、Card System 開關、Profile 與基礎押注額建立本批設定，並選出押注層級、Link 資格及倍率上限。
  7. 執行 Warm-up，再開始正式計時與多執行緒模擬。
  8. 合併 Worker 統計，計算 RTP、Hit Rate、Feature、Retry 與遊戲專屬指標。
  9. 依固定格式印出執行結果。
  10. 需要輸出時，將相同結果寫入 Record/*.xlsx。

數學核心與報表／顯示邏輯必須分離。Card System 關閉時，不得執行抽卡或 Retry；config_rtp_file 不得改變 config_file 所定義的原始盤面與自然機率邏輯。

1.1.3 執行結束後印出的內容

每個 Batch 結束後必須依第 1.3 節的順序與格式輸出，不得只印 RTP。欄位名稱固定使用英文，數值格式由共用格式化函式處理。

1.2.1 BATCH_RUNS

2.2 最低資料

Config 至少應提供遊戲實際需要的：

  • game_id、game_name、excel_version 與 Config 類型／代號。
  • Reel 數、盤面尺寸、Symbol ID／名稱／屬性。
  • Reel Strip／Weight／Length、Paytable、Payline／Ways／Cluster。
  • Table、Table Weight、Drop Mode 與各 Scene 資料。
  • Bet Mode ID、成本倍率、Bet Level／DENOM。
  • BG、FG、Cascade、Multiplier、Retrigger 與 Feature 參數。
  • Card System 開關、Retry Limit、Profile、NB／EB 與 BF／SF 的押注層級判定方式、Oldhand 小／中／大 Bet 門檻、卡片區間與各模式／層級權重。
  • Link 資格、Link／Bonus Game／Game RTP 目標與 Total RTP。
  • Newbie BG／FG、Oldhand 小／中／大 Bet 的 Max Win／Max Multiplier 與其他產品限制。

同一概念在不同 Config 間必須保持一致，並記錄於數學模型的 Game Description 工作表。

2.3 資料驗證

  • game_id 與所在遊戲資料夾一致。
  • config.js 的 excel_version 與基礎 XLSX 完全一致，且只能是 1 碼。
  • 初次建立時，競品模型的基礎 XLSX／Config 版本為 0，非競品模型為 1；來源分類必須可追溯。
  • config_<RTP><Variant>.js 的 excel_version 與對應 RTP／Variant XLSX 完全一致，且必須是 4 碼。
  • RTP／Variant Config 的版本第 1 碼，必須與對應的基礎 Config（config.js，或 A／B 時的 config_A.js／config_B.js）及基礎 XLSX 的版本相同。
  • Config 檔名、類型、內部 RTP／Variant 與來源 XLSX 相符。
  • 所有 Weight 非負，啟用選項的總權重大於 0。
  • Newbie 與 Oldhand 小／中／大 Bet 的權重、Link 資格、RTP 拆分及倍率上限齊全且互相一致。
  • 押注層級邊界必須精確符合 < $2、>= $2 且 <= $100、> $100，不得因浮點誤差選錯層級。
  • NB／EB 必須以實際模式押注判斷；BF／SF 必須以購買價格除以 Feature Price 倍數後的基礎押注判斷。
  • Reel、Weight、Paytable、Symbol 與 Mode 陣列長度相容。
  • 所有 ID／索引在有效範圍，無重複或遺漏。
  • Min／Max、倍率、局數與 Max Win 限制合法。
  • 未支援的 Mode／Profile／Feature 不存在或明確停用。
  • 浮點精度足以還原來源數值，不因格式化造成 RTP 偏差。

2.4 版本與歷史檔

  • 正式 Config 放在遊戲資料夾根層，包括基礎 config.js（A／B 時為 config_A.js、config_B.js）與實際支援的 config_92A.js 等 RTP／Variant Config。
  • 歷史 Config 放在對應的 Versions/ 版本目錄；基礎 Config 與 RTP／Variant Config 都必須保留來源及版本關係。
  • Versions/version_manifest.js 記錄完整版本、可用 Config、路徑與變更說明。
  • Runtime、Simulator 與 Demogame 不得自行覆寫 Config 版本。
  • Index 載入基礎 Config（config.js、config_A.js、config_B.js）時顯示 1 碼基礎版本；載入 RTP／Variant Config 時顯示完整 4 碼版本。
  • RTP／Variant 版本若第 1、2 碼相同，Index 只顯示第 3、4 碼最新的版本。
  • Version 與 Config 選單只列出 manifest 中實際存在且相容的組合。

1. 用途與載入

Demogame 是模型邏輯、流程與 Debug 資訊的可操作驗證介面，不只是視覺展示。它必須能用單局結果證明 Config、Simulator 與遊戲規則一致。

  • 主入口固定為 index.html，使用相對路徑，雙擊即可離線執行。
  • Config 選單只列 Config 代號，不列 Profile，Demogame 不提供 Newbie：例如 BaseA、BaseB、92A、94A、92A_BET100、92B。
  • 卡片系統沒有獨立的開關，由 Config 選單決定：選 Base 為自然機率（卡片系統關），選 92A 等 Config 代號為卡片系統開（Oldhand）。
  • 自然機率只依基礎數學 Variant 區分，與 RTP 家族無關：只有一套時顯示 Base；有 A／B 兩套時顯示 BaseA、BaseB。
  • 標題列右側固定放「數值報告」（有報告時）、「說明」、「重置」三個文字按鈕（無底色、無外框，滑過才顯示底色），字型與標題相同，標題列高 44px；數值報告在同一分頁開啟。
  • 標題列樣式各遊戲一致：代號＋名稱 15px 粗體、上下置中（由共用 CSS 統一），不得另寫遊戲專屬的標題樣式。
  • 盤面不得裁掉格子的特效：中獎放大、百搭彈出與外發光在最外側一欄／一列也要完整顯示（共用 CSS 對 #board.board-grid 保留 14px 外圍可見範圍）。
  • 遊戲名稱、盤面、輪帶、權重、Paytable、Bet Mode 與 Feature 參數從 Config 取得。
  • 不得為演出方便另寫一套簡化數學邏輯。
  • Config 無法載入或欄位不完整時要顯示明確錯誤，不得靜默使用舊值。

2. 共用區域與 By Game 區域

2.1 By Game 區域

下列區域依各遊戲盤面、Feature 與美術需求自行設計：

  • Game Title：遊戲 ID、遊戲名稱及遊戲專屬標題樣式。
  • Feature Status：Cascade／Combo、FG Left、Multiplier 與其他遊戲狀態（不顯示 Base Game／Free Game 模式標題；沒有要顯示的特色時整列隱藏，由共用模組處理）。
  • Reel／Board：盤面尺寸、Reel、Symbol、框體、特殊符號及遊戲專屬資訊。
  • Board Animation：Spin、中獎、消除、補牌、掉落、轉換、Multiplier 與 Feature 動畫。
  • Board Message：盤面下方的局數、FG 進度、得分、No Win 與遊戲流程訊息。

對應元素通常為 #feature-bar、#strip-bar、#grid-panel／#board 及盤面 Message Bar。實際 ID 可以依遊戲調整，但範圍與責任不得擴張到共用區域。

By Game 區域必須：

  • 從 Config 取得名稱、盤面、Symbol、倍率與 Feature 資料，不得寫死其他遊戲的內容。
  • 只維護遊戲專屬 HTML、CSS、Render、動畫與狀態轉換。
  • 將共用操作需要的狀態與結果透過固定介面交給共用模組，不得複製整套共用控制邏輯。

2.2 共用區域

除第 2.1 節外，其餘區域與行為均由所有遊戲共用，包括：

  • Player：Credit、Bet、Win。Player／Play／Bet Mode 三區一律放在盤面下方（左欄），右欄只留統計；手機版（單欄）依序為盤面、這三區、統計（共用模組處理）。
  • Stats／Simulation。Stats（標題「基本指標」）放共用項目（總局數、RTP、中獎率、FG 觸發、BG／FG 最大倍數；原「最高倍數」與其重複，不再顯示）；遊戲自訂的特殊指標（只放觀察玩法機制用的即時統計，例如金框使用率；FG 週期等遊戲數據已在報告中，不放這裡）放在下方獨立的「特殊指標」區（共用模組自動把非共用列移入，也可在列上標 data-by-game），沒有特殊指標就不顯示這區。
  • Play：Spin、Auto、Bet Stepper、Speed。
  • Bet Mode 的容器、共用互動與狀態樣式；實際支援模式及倍率由 Config 決定。按鈕字體、大小一致、字一律白色：NB／EB 為切換鈕（選取中用「自動」鈕的深綠底白字），BF／SF 為購買鈕，用 SPIN 的藍底白字（共用模組依按鈕文字判斷）。
  • Debug Mode、Set RNG、Log 與歷史紀錄（Spin Result 面板與 Force FG 已停用，由共用模組隱藏；Reel RNG 停輪面板已拿掉，改用統計區的 BG／FG 最大倍數）。
  • Setting：Version、Config／Profile、Language、Help、Reset。
  • Language：共用區的固定英文標籤由 demogame_common.js 依 #languageSelect 統一切換中英（整段完全相同才替換）；By Game 區域與遊戲專屬文字仍由各遊戲自行翻譯，切回 English 必須還原。
  • 共用彈窗、按鈕狀態、欄位樣式、響應式版面、無障礙與錯誤顯示。各區塊上下、左右間距一律 10px（含盤面與右欄、頁尾與設定區），頁尾文字置中、用區域標題的說明色。字體統一：所有按鈕 12px 粗體；Debug 的 Previous／Next 兩顆同款（深藍底、細框、淺色字，共用 demogame_common.js 套用）；設定區文字標籤 12px 一般字重、下拉選項同按鈕；有名稱的區域標題 12px 粗體、說明色、不轉大寫，標題列滿版、下方加一條分隔線（同紀錄區）；遊戲區不顯示標題。倍率線型、紀錄、版本紀錄的標題後有「+」，點下去用彈窗顯示完整內容（倍率線型為大圖），彈窗一開就是最大尺寸（不隨內容長高，沒資料的地方維持深色底），可按 ⟳ 旋轉 90°（寬高對調後滿版）；直式手機放大倍率線型時一開就是橫的，紀錄與版本紀錄維持直式，關閉後放回原位；所有捲軸隱藏但保留上下捲動。

  • 有符號美術的遊戲必須接入共用 Image 開關：頁面在載入 demogame_common.js 前定義 window.DEMOGAME_IMAGE_TOGGLE = { supported: true, defaultEnabled: true, setEnabled(enabled) { … } }，setEnabled 內切換是否輸出符號圖並重繪目前盤面；不得自行另做圖片開關。共用模組會在 Setting 產生 Image 開關，選擇存於 localStorage（slotDemoSymbolImages）。
  • 有輸出符號圖的格子必須加上 has-symbol-art；圖片載入失敗時移除此 class 並改顯示代號。
  • 圖片預載（必做）：放到網頁上時，圖片若等第一次用到才下載，盤面會先出現空白格。有符號美術的遊戲必須在 DEMOGAME_IMAGE_TOGGLE 加上 images：本遊戲會用到的所有圖片網址（陣列，或回傳陣列的函式），包含大符號長圖、金框等所有變體。共用模組會在開局前預載並解碼完成：
    • 預載期間擋住點擊與鍵盤；超過 120 ms 才顯示「載入圖片 n / N」遮罩，避免已有快取時畫面閃一下。
    • 解碼最多等 1.5 秒；分頁在背景時略過解碼（瀏覽器在背景分頁不會完成 decode()），不得因此卡住遮罩。
    • 任一張載入失敗：關閉 Image 開關、改用文字顯示，並提示失敗張數；不得停在載入畫面。
    • 預載邏輯只寫在 demogame_common.js，遊戲專屬程式只提供 images 清單，不得自行另寫預載。
  • 圖片格式：Demo 使用的符號圖一律用 WebP（quality 90、保留透明），檔名與原 PNG 相同、副檔名改 .webp，放在 Source/Image/；原始 PNG 保留作為美術原檔，Demo 不引用。
  • 無美術時的代號可使用共用標籤 <span class="slot-symbol-label">代號</span>（置中、一般字重）。
  • 沒有任何符號美術的遊戲不接 Image 開關，固定顯示符號框＋代號。
  • 中獎、轉換等狀態框線（.hit、.convert、.wild-mark、.fx-win）不受此規則影響。
  • 符號一體：符號的字、框、底板是一體，所有動畫（長出來、消除、補牌、掉落）都整格一起動，不能只有部分變化（例如框先出現、字才長出來）。顯示得分框時，沒得分的符號完全不變（不變暗、不換框）。
  • 得分符號只把外框換成藍色框起來（金框符號得分時保留金框、外圈加藍框）（共用 demogame_common.js 套用），不放大、不閃、不跳；各遊戲不得另做中獎動畫。消除與掉落動畫不受影響。
  • Hook：框線本身屬規則狀態、且沒有對應美術時（例如純 CSS 的金框），在該格加 keep-symbol-frame 保留框線。金框若已有美術（例如 Frame 圖或金框版符號圖），不得再疊加 CSS 框。

3. 補牌方式

每款有消除機制的遊戲，必須在 Game Rule、Config 對應說明與 Demogame 中指定唯一補牌方式。Simulator 與 Demogame 必須使用相同邏輯。

  1. 消除後原地補牌
    • 中獎符號消除後，只在原本的空格位置抽取並顯示新符號。
    • 盤面上未消除的符號維持原座標，不播放向下移動動畫。
    • 新符號在空格原位「長出來」（縮放 0→1，共用 demogameMotion.grow()），不得播放掉落動畫。
  2. 消除後掉落補牌
    • 中獎符號消除後，同一 Reel／Column 上方未消除的符號依重力向下補位。
    • 剩餘空格由新符號從盤面上方掉入。
    • 動畫必須區分既有符號的 Settle 與新符號的 Drop／Refill。
    • 掉落整段時間＝一輪從滾動到滾停的時間（共用 demogameMotion.dropMs()）。
  3. 特殊補牌（By Game）
    • 不符合前兩類的 Random、Parallel、跨欄移動、整盤替換或其他特殊補牌皆歸此類。
    • 必須在該遊戲的 game_rule.md 與數學模型的 Game Description 工作表中明確定義抽取來源、移動方向、補牌順序、保留位置及動畫。
    • 不得把單一遊戲的特殊補牌邏輯寫成所有遊戲共用的預設行為。
  • 補牌資料必須來自 Config 定義的 Reel／Drop Table／Weight，不得只為動畫另外抽一組結果。
  • 補牌後重新判獎的次數、盤面與得分必須可由 Debug 結果重現，並與 Simulator 對帳。
  • Symbol 轉 Wild、鎖定位置或不補牌的位置，必須先依遊戲規則處理，再執行選定的補牌方式。

4. 必要行為

  • 支援 Normal Spin，以及遊戲實際存在的 Extra Bet、Buy Feature、Super Feature。
  • 押注選項依 Bet Currency：1～1500 加上最大押注 2000／3000／5000；押注層級由數學定義的遊戲（例如 H014 依押注各有自然表）以 Config 為準。
  • Bet 顯示與 Credit 扣款使用實際模式成本；Win 依流程即時更新：每次消除得分就加上去（BG 局與每轉 FG），局末數值與結算相同；觸發 FG 那局（含 BF 入場盤）的 BG 得分要累積進 FG，FG 期間 Win＝觸發局 BG 得分＋FG 累計，FG 結束時等於整局總得分；Debug 的 Previous／Next 逐步檢視時，Win 同步顯示該步的累計得分。
  • Auto、Speed、Reset 不得改變 RNG、得分或統計結果。
  • Speed 為 1～5 五階：1～4 階轉輪由左到右逐輪停；第 5 階不逐輪停，Spin 後所有轉輪同時到位（BG、FG、Respin 皆同）。
  • 轉輪滾動一律照 H020 超級寶石的滾法：每輪是一條連續往下捲動的輪帶，由左到右依序停在結果上；不得用每一幀換一次符號的方式表現滾動。轉輪類遊戲停輪前要多往下滾約 18% 格高再回彈到正確位置（總時間不變，輪帶上方墊一格避免露出空白）；Speed 1～4 每輪至少滾 10 個符號，Speed 5 維持。掉落類遊戲（H013、H019、H027、H045、急速糖果 2、糖果狂歡 2500）Spin 不播輪帶滾動：舊盤面整欄往下掉出、新符號整欄從上方掉入並輕微回彈，由左到右逐欄錯開（Speed 5 同時），每欄時間＝reelSpinMs()，用共用 demogameMotion.dropSpin()；連消後的補牌方式維持各遊戲原本規則。
  • 動畫時間統一由共用 window.demogameMotion 提供，各遊戲不得自訂：一輪滾動到滾停 reelSpinMs()＝700／520／380／260／180 ms（Speed 1～5），逐輪停錯開 stopStaggerMs()＝120／100／80／60／0 ms；掉落補牌 dropMs()、原地補牌長出來 growMs() 都等於 reelSpinMs()。
  • 每一轉（BG 局與每一轉 FG）算完分後固定停 0.5 秒（共用 window.demogameRoundPause()），才放行下一轉或 Auto；這段停頓不受 Speed 影響，Simulation 不停頓。
  • BG、Cascade、FG、Retrigger 與 Feature 狀態按真實流程播放。
  • FG 結束回到 BG 時，盤面還原成觸發 FG 那局的 BG 最終盤面（BF 為入場盤），Feature Status 回到基礎遊戲。
  • Config、Version、Profile、押注層級、Card System 與 Language 只顯示實際支援的內容。
  • Help 與 game_help_draft.md 一致，不在 HTML 另維護一份規則。
  • Help 至少要有賠率表：game_help_draft.md 沒有賠率（或讀不到、只剩離線副本）時，由 Config 的 Paytable 依目前押注產生。
  • Help 版式（共用 demogame_common.js）：標題由大到小（區塊標題 20px 置中 → 副標題 15px 置中 → 規則 13px），區塊之間用分隔線、規則前加方塊符號；賠率表顯示成兩欄符號卡片，每張是「符號＋由大到小的 N - 派彩」。有符號美術的遊戲要定義 window.DEMOGAME_SYMBOL_ART = { 代號: 圖片網址 }，卡片用該圖；沒美術或 Image 關閉時，顯示與盤面同款的深色代號方格（C1／SC 金色、WW 綠色）。
  • 連線（Line）遊戲有得分時要在盤面畫出得分線：呼叫共用 window.demogameWinLines.draw(盤面容器, [[格子元素…], …])，每條得分線要依線圖（paylines）整條畫出、連過每一輪的格子中心，不能只畫中獎的那幾連，顏色依序輪替；每次重畫盤面後要重新呼叫。

  • 初始盤面、每段 Cascade、Line／Ways Win、Multiplier 與最終結果。
  • FG 觸發、局數、Retrigger、整包 Win 及即時 Log。
  • 最後調性更新（共用，頁尾 .footer-note）：頁面在載入 demogame_common.js 前設 window.DEMOGAME_LAST_TUNING = "YYYY-MM-DD HH:MM"，頁尾顯示「最後調性更新：日期 時間」（24 小時制，到分鐘）。只有數學模型或倍率（卡片）權重調整才更新（與 修改紀錄.md 最新一項同日）；介面、演出、文件修改不更新。

  • BG／FG 最大倍數（共用，併在「統計」區，取代原「最高倍數」列）：頁面在載入 demogame_common.js 前設 window.DEMOGAME_HISTORY = true，每局呼叫 window.demogameHistory.record({ bg, fg })（BG 得分、該局 FG 總得分，皆 ÷ 底注）；沒有 FG 的遊戲只顯示 BG 列，重置清空。
  • Log（共用 window.demogameLog(text, type)）：帶時間的即時紀錄，Clear 清空，最多保留 500 行；所有遊戲行格式一致（照 H045），不記演出過程：
    • Config <名稱> loaded | Version <版本> | Card System On|Off
    • #<局號> Normal Bet|Extra Bet|Buy Feature|Super Feature | Bet <押注>[ | Card Range set][ | Replay]
    • RNG <碼>（可點，複製並填入 RNG 欄）
    • BG|BF Entry | <盤面表> | Cascade <n> | C1 <n> | Win <得分> (<倍數>x)

    • window.demogameSimulateRound({ mode })：用與畫面相同的遊戲邏輯產生一局（不得另寫簡化數學），回傳 multiplier（總得分含 FG ÷ 實際押注）、lineMultiplier（BF ÷ 底注，其餘同 multiplier）、fgTriggered、maxMultiplier、retryLimitExceeded、retryCount、bgCascade、fgCascades；mode 只在該局暫時套用，不得改動畫面押注模式與統計。
    • window.demogameSimulationModes = [{ value, label }]：只列實際支援的押注模式，面板據此顯示押注模式選單。
  • 累積倍率線型（共用，統計區下方，標題「倍率線型 (押注模式)」）：畫面實際遊玩的局，NB 記在 NB、EB 記在 EB，BF／SF 不記錄；依目前押注模式顯示對應的累積圖（標準 64 區間、Y 軸 1%），重置清空。遊戲每局（含 FG）結束時呼叫 window.demogameLineChart.record(總得分 ÷ 押注, "NB"|"EB")；押注模式按鈕沒有 is-active 樣式時另呼叫 setMode()。
  • 倍率線型（共用，併入 Simulation 面板）：該次模擬每局 lineMultiplier 的標準 64 區間分布，X 軸逐一標出 (下限, 上限]，Y 軸 NB／EB 1%、BF 20%，超過上限或為 0 的區間不畫點、線在該處斷開。沒有 Simulation 面板的頁面才在 Set RNG 上方顯示即時線型（NB 一局含 FG 結束時呼叫 window.demogameLineChart?.record(該局總得分 ÷ 底注)；批次模擬不得呼叫）。

Set RNG 的各欄位（卡片區間、遊戲專屬選單、RNG）互斥：設定其中一個時其他回到預設（共用模組處理）。所有設定都每局沿用，按重置才清空，遊戲不得在 Spin、FG、切換模式後自行清掉。指定值要檢查格式；不得因指定 RNG 進入無限重跑。

Set RNG（共用，#set-rng-panel）：欄位排成一列等寬（卡片 BG 區間、遊戲專屬選單、RNG #rngInput、重置 #setRngResetBtn）。

可重現 RNG（共用 window.demogameRng）：每局（BG＋整場 FG）以一組 32-bit 種子算出；Log 印一行 RNG <Config-Profile>/<NB|EB|BF|SF>/<on|off>/<選項|->/<種子 8 碼>，點一下複製並填入 RNG 欄，按 Spin 整局重跑出相同結果。遊戲在每局開始呼叫 demogameRng.takeInput() 取碼、用 demogameRng.run(seed, fn) 一次算完整局結果（表演用亂數放在外面），選項欄放重現所需的遊戲專屬設定（例：腳本名稱、r<卡片區間>）。
