適用範圍：`Slots/H0xx_遊戲名稱/` 下的新遊戲數學模型、既有模型改版，以及 RTP、Card System、Feature 或 Bet Mode 參數調整。

## 1. 過往專案整理後的標準做法

過往專案可看到數種演進中的做法：

- H013、H015、H019 使用 RTP Config、Simulator 與 Record 的基本流程。
- H016、H028 已拆分基礎 `config.js` 與 RTP／Variant Config，並保留 `Versions/`，較符合目前標準。
- H026 同時存在 92／94 與 A／B Variant，適合作為多模型組合的參考。
- 早期專案（H013～H027）曾使用 `xlsx_to_config.py`、`model_sync.py` 等轉檔腳本同步 Source 與程式資料；此做法已淘汰，Excel 與 Config 之間的轉換一律由 AI 執行，專案內不建立、不維護轉檔工具。

新專案採用以下統一原則：

1. `game_rule.md` 定義玩法，數學 XLSX／`Source/` 定義正式參數。
2. Config 必須由 Source 轉出（轉換由 AI 執行，不建立轉檔工具），不直接手改轉出的參數。
3. Simulator 與 Demogame 使用同一份 Config。
4. 先驗證 Card System Off 的自然機率，再驗證 Card System On。
5. 每次調參都依「Source → 版本 → Config → Simulator → Record → 對帳」完整重跑。
6. 舊專案若與目前命名、版本或報表格式不同，不直接複製舊格式；依現行規格建立。

### 2.1 修改紀錄格式

`修改紀錄.md` 放在專案根目錄，**依版本分節、不以日期分節**：

- 每個四碼版本一節，標題寫 `## v<第 1 碼>（<四碼版本>）`，例如 `## v5（5.1.0.0）`、`## v5（5.0.0.0）`；由新到舊排列。
- 只改倍率權重（卡片權重，[數學模型規範 1.3](../開發規範/Omniplay/數學模型規範.md) 第 2 碼）時升成 `5.1.0.0` 這類版本，同樣**獨立成一節**，只列該版本內的修改；SCR（第 3 碼）、其他文件（第 4 碼）同理。
- 每節用編號清單，一項一件事，句尾以全形括號附日期 `（MM/DD）`。
- **只記錄跟數學調性有關的內容**：規則、賠率、輪帶、金框與倍數權重、卡片權重、RTP 拆分與週期、模擬驗證結果等。Demogame 介面、演出、文件、工具的修改不記在這裡（以 git commit 為準）。Demogame 的「版本紀錄」（`index.html` 的 `#change-log-wrap`）是本檔的複本，本檔更新時同步更新。
- 項目歸到**修改當時的目前版本**；**只記已完成的修改**，不寫進行中、待辦或「待重算」之類的狀態。
- 數學版本細節另見 `Versions/version_manifest.json`。
- 每次新增調性項目（數學模型或倍率權重調整）時，同步把 Demogame `index.html` 的 `window.DEMOGAME_LAST_TUNING` 改成當下的日期與時間 `YYYY-MM-DD HH:MM`（頁尾「最後調性更新」，見 [Demogame規範](Demogame規範.md) 第 5 節）。

範例：

```text
## v5（5.1.0.0）

1. 92A 卡片權重重解：BG Trigger Cap 350x → 300x。（10/20）
2. Card-On 驗證 Oldhand 92.03%、Newbie 92.98%、BF 92.51%。（10/20）

## v5（5.0.0.0）

1. 升 v5：啟用盤面表 2（高連消表），BG 選表 9 : 1、FG 2 : 8。（10/12）
2. 表 2 補牌權重集中、輪帶 M1～M4 約一半換成低倍符號。（10/12）
```

## 3. 整體流程

七個大步驟，每一步的工作、產出與進入下一步的條件見第 4 節：

```flow
提案 :: 整理玩法、規格、特色與競品差異，製作提案簡報
開案 :: 遊戲規格確認：Game Rule、數學目標、模型組合
數學開發 :: 模型製作 → 模擬程式 → Demogame
調性調整 :: 卡片權重校準、Card System 驗證、調參與正式模擬、數值報告
後端對接／報表驗證 :: SPS 設定交付、後端報表驗證、挑腳本
文件製作 :: 數值文件、Help
文件檢查 :: 所有要交付給其他人的檔案逐項檢查，版本凍結
```

## 4. 製作順序與階段關卡

不得因為某個程式可以先寫就跳過前置規則。上一階段的完成條件成立後，才進入下一階段。

| 順序 | 階段 | 主要工作 | 產出 | 進入下一階段的條件 |
|---:|---|---|---|---|
| 1 | 提案 | 整理玩法、規格、特色與競品差異，製作提案簡報 | 提案簡報 `.pptx` | 提案通過、確定開案 |
| 2 | 開案（遊戲規格確認） | 確認 Game ID、盤面、判獎、Bet Mode、Feature、RTP 拆分、Link 資格、Hit Rate、Max Win、Profile、押注層級與 Variant；**與使用者確認數學模型組合**（預設 92A／92B／94A／94B，各含 Newbie／Oldhand 與對應押注區） | 已確認的 `game_rule.md`、數學目標表 | 核心規則、計算口徑與模型組合無待確認項目 |
| 3.1 | 數學開發：模型製作 | 基礎數學模型 → RTP／Variant 與 Card System 區間 → Mapping → 由 AI 轉出 Config | `H0xx1.xlsx`、`H0xx1<RTP><Variant>.xlsx`、`config*.js` | 自然機率可計算、理論上限已確認；Source、Config、版本逐項一致 |
| 3.2 | 數學開發：模擬程式 | 實作 Simulator；小場次 Debug 與單局驗證；Card System Off 大場次自然機率報表（NB 10⁹ 局、BF 10⁸ 局） | `Simulator.py`、自然機率報表 | 固定 Seed 可重現；代表性案例符合 Game Rule；RTP Breakdown、Hit Rate、Feature 與分布合理 |
| 3.3 | 數學開發：Demogame | 依 Config 製作可操作的 Demo，與 Simulator 單局對帳 | `index.html` | Config、Simulator、Demogame 單局結果一致 |
| 4 | 調性調整 | 依自然機率報表校準卡片權重；Card System On 分 RTP／Variant／Profile／押注層級驗證；調參與正式大場次模擬；Max Win、Retry 與極值驗證；數值報告對標競品與前作 | 校準後的 `Multiplier_Weight` 與 Config、Card-On 報表、`數值報告_<遊戲中文名>` | 所有組合符合目標與誤差要求，調性經使用者確認 |
| 5 | 後端對接／報表驗證 | 交付 SPS **Config 與模擬程式**（不交數學模型、PARsheet）；讀後端報表驗證 RTP；**挑腳本** | 交給 SPS 的 `config*.js`、`Simulator.py`，後端報表彙整、腳本 | 後端報表與 Simulator 一致，腳本挑選完成 |
| 6 | 文件製作 | **數值文件**：`game_description.md`、PARsheet、Math Document Description；**Help**：`game_help_draft.md` → `{GameID}_Help.xlsx` → Game Description | 各文件 | 文件內容與 Game Rule、數學模型一致 |
| 7 | 文件檢查 | 檢查**所有要交付給其他人的檔案**（Help、Game Description、Math Document Description、PARsheet、數學模型、Config、Simulator、Demogame、腳本）；版本凍結、整理 Record | 檢查紀錄、完整專案目錄 | 本文件第 9 節全部通過 |

### 4.2 工作進度表

每款遊戲在專案根目錄放 `進度.md`，記錄上表各階段工項的完成狀態；每次開啟該遊戲的工作 Session，先顯示進度條再開始工作。

```text
py 專案需知/其他/progress.py H045
```

- 遊戲還沒有 `進度.md` 時，腳本依預設工項建立（工項取自上表各階段的產出）；之後**依遊戲自行增刪工項**，以 `進度.md` 為準。
- 狀態欄：空白＝未完成；**`ok`＝使用者確認完成**（只有使用者確認後才可標 ok）；完成後若再調整，同一列依序改為 `v2`、`v3`…。
- 紀錄欄依序附日期與內容，例：`ok 2026-10-16；v2 2026-10-20 調整 BG 權重`；不刪舊紀錄。
- 進度條＝有狀態的工項數 ÷ 全部工項數；腳本另列出下一個未完成的工項。

## 5. 各階段操作方式

### 5.1 開案與數學目標確認

1. 建立 `H0xx_遊戲名稱/` 專案資料夾。
2. 讀取並確認 `game_rule.md`。
3. **與使用者確認本專案的數學模型組合**——每款遊戲的數學模型都不一樣，不得逕自沿用他款設定。未特別說明時，預設組合為：
   - A／B 兩個 Variant × 92／94 兩個 RTP，乘開共 **4 個版本**（92A、92B、94A、94B）。
   - 每個版本都有 Newbie／Oldhand 兩種 Profile。
   - 各版本依其支援內容有對應的押注區（Oldhand 小／中／大 Bet 層級）。
4. 列出所有正式支援組合：RTP、Variant、Profile、Oldhand 小／中／大 Bet、NB／EB 或 BF／SF 模式類別、Bet Mode、Card System Off／On。
5. 為每個組合定義 Link／Bonus Game／Game RTP、Total RTP、Link 資格、Hit Rate、Feature Frequency、BG／FG Max Multiplier 與其他遊戲專屬指標。
6. 將未決定的判獎順序、倍率分母、Feature 上限與例外退回確認；未確認前不製作正式模型。

### 5.2 建立基礎數學模型

1. 先完成 Base Game，再依狀態順序完成 Feature。
2. 建立 Symbol、Paytable、Reel Strip／Weight、Table 與 Bet Mode。
3. 建立 BG、FG、Cascade、Multiplier、Retrigger、Jackpot 等流程。
4. 計算 RTP Breakdown 與理論 Max Win，不只計算 Total RTP。
5. 建立基礎數學 XLSX，版本依規格使用 1 碼。

### 5.3 建立 RTP／Variant 與 Card System

1. 只建立 5.1 與使用者確認過的 92／94、A／B 組合（未特別說明時為 92A、92B、94A、94B 四版本，各含 Newbie／Oldhand 與對應押注區）。
2. A／B 表示數學 Variant，不表示 Newbie／Oldhand。
3. 依 Profile、Oldhand 小／中／大 Bet 與 Bet Mode 建立 BG／FG 卡片區間及權重；NB／EB 以實際模式押注、BF／SF 以 Feature 基礎押注選擇層級。
4. 確認每張正權重卡片的區間可達，並定義 Retry 行為。
5. 建立 RTP／Variant XLSX，版本依規格使用四段格式。

### 5.4 轉檔與 Config 驗證

1. 在數學模型的 `Game Description` 工作表記錄每項 Config 資料的來源。
2. 由 AI 依 Source 與 Mapping 轉出 Config；專案內不建立、不維護 Excel↔Config 轉檔工具。
3. 執行欄位、型別、陣列長度、ID、Weight、Min／Max、版本與模式驗證。
4. 比較轉檔前後資料，確認 Config 可由 Source 重建且沒有非預期差異。
5. 轉檔錯誤時修正 Source 或 Mapping 後重新轉出，不直接修改 Config 大型陣列。

### 5.5 Simulator 開發與 Debug

1. 先完成自然機率核心，再加入 Card System 篩選與 Retry。
2. 讓 Simulator 直接讀取正式 Config，不另寫一份參數。
3. 建立固定 Seed、單執行緒與逐局 Trace 模式。
4. 建立強制／指定案例，驗證無獎、一般獎、Wild、Scatter、Feature、Retrigger、倍率與封頂。
5. 小場次確認正確後，再加入 Numba、多執行緒、BATCH_RUNS 與 Excel 報表。

### 5.6 模擬順序

模擬必須依下列順序執行：

1. 小場次、Card System Off：驗證流程與報表。
2. 中場次、Card System Off：確認自然機率 RTP 與分布。
3. 大場次、Card System Off：以 NB 10⁹ 局（BF 為 10⁸ 局）產出自然機率正式報表。
4. 卡片權重調性校準：依上一步報表分配各得分區間的卡片權重，使分布、RTP 拆分與 FG 週期符合目標遊戲調性；完成後才進入 Card System On。
5. 小場次、Card System On：確認抽卡、Profile、Oldhand 押注層級、Link 資格、倍率上限、Mode 與 Retry。
6. 中場次、Card System On：調整區間、權重與目標 RTP。
7. 所有正式組合的大場次模擬。
8. Max Win、低機率 Feature 與 Retry 邊界的專項驗證。

最低批次矩陣：

| 類型 | RTP／Variant | Profile | `bet_tier_amount` | Bet Mode | Card System |
|---|---|---|---|---|---|
| 自然機率基準 | 基礎 Config | 不適用 | 各門檻所需代表值 | 每個支援 Mode | Off |
| Newbie | 每個正式 RTP／Variant | Newbie | 不分層級，但仍記錄判定金額 | 每個支援的 NB／EB／BF／SF | On |
| Oldhand 小 Bet | 每個正式 `94x`／Variant | Oldhand | `< $2`，至少驗證 `$1.99` | 每個支援的 NB／EB／BF／SF | On |
| Oldhand 中 Bet | 每個正式 `92x`／Variant | Oldhand | `$2～$100`，至少驗證 `$2`、`$100` | 每個支援的 NB／EB／BF／SF | On |
| Oldhand 大 Bet | 每個正式 `92x`／Variant | Oldhand | `> $100`，至少驗證 `$100.01` | 每個支援的 NB／EB／BF／SF | On |

- NB／EB 的 `bet_tier_amount` 使用實際模式押注金額；BF／SF 使用 Feature 購買價格除以 Feature Price 倍數後的基礎押注。
- 若遊戲支援 EB 2x，至少驗證 base bet `$1` 會以 `$2` 判為中 Bet。
- 若遊戲支援 BF 75x，至少驗證購買 `$75` 判為小 Bet、購買 `$150` 判為中 Bet。

不存在的 Mode、Profile 或 Variant 不建立空批次，也不以全零結果冒充驗證完成。

### 5.7 調參循環

每一次調參都執行完整循環：

```text
確認差距與原因
    ↓
修改對應 Source XLSX
    ↓
依異動內容更新版本
    ↓
重新產生 Config
    ↓
執行轉檔與資料驗證
    ↓
先跑小場次確認流程
    ↓
再跑中／大場次確認統計
    ↓
保存新 Record 並與前版比較
```

調參時依序判斷：

1. 先確認程式與統計口徑是否錯誤。
2. 再檢查自然機率的 Paytable、Reel、Table、Feature。
3. 最後才調整 Card System 區間與權重。
4. 不得只為讓 Total RTP 接近目標而忽略 RTP Breakdown、Hit Rate、Feature Frequency、分布或 Retry。

### 5.8 對帳與交付

1. 選定可重現的代表性 RNG／Seed。
2. 逐項核對 Config、Simulator 與 Demogame 的盤面、判獎、Feature、倍率、Total Win、Coin In 與 Retry。
3. 完成所有正式組合的最新 Record。
4. 將正式 Config 與歷史版本關係寫入 `Versions/` 與 manifest。
5. 確認第 2 節必要產出文件全部齊備且為同一正式版本。
6. 清除暫存檔、舊測試輸出及不屬於正式交付的檔案。
7. 依第 9 節完成最終驗收。

**交付 SPS 打包**（第 5 步後端對接；2026-10-22，以 H020 超級寶石為範例）

- 放在 `其他/To SPS/`，每次交付打成**一個 zip**：`<GameID>_<RTP／Variant 四碼版本去點>.zip`（例：`101007_2220.zip`＝2.2.2.0、`101015_6000.zip`＝6.0.0.0）。
- zip 內只放：`config.js`、該遊戲所有 `config_<RTP><Variant>.js`、`Simulator.py`、`給SPS說明_<四碼版本>.txt`；不放數學模型 XLSX、PARsheet、報表、json。
- `給SPS說明_<版本>.txt` 寫：與上一個交付版本的差異（基礎數學、規則／程式要後端同步的地方、卡片權重）、驗證目標與我方 Card-On 結果（判定見模擬程式規範 §1.2.2）。
- 舊版 zip 保留不刪（追溯用）；`To SPS/` 內不留散檔，只放各版 zip。
- 驗證結果確定後才打包；打包後重新交付須換新版本號，不得覆寫已交付的 zip。

### 5.9 數值報告（對標競品與前作）

卡片權重完成後（第 4 節卡片權重調性校準之後），產出數值報告（即本作與競品、前作的差異分析），比較本作與競品（及使用者指定的前作）的玩法指標，作為調性是否到位的依據。

**檔案與格式**

- 檔名 `其他/數值報告_<遊戲中文名>.md` ＋ 同名 `.html`（例：`數值報告_宙斯 2500`、`數值報告_超級鑽石`、`數值報告_錢來襲`），兩份內容一致；不另取其他檔名。舊名 `差異分析_<遊戲中文名>` 一律改為此名。
- 遊戲名稱一律用英文名（例：Super Diamond、Super Ace、Lucky Ace），不用 H0xx 代號。
- **大標題＝`<本作英文名> 數值報告`**（例：`Super Diamond 數值報告`），不寫「A vs B vs C」；比較對象改在「基本資訊」章交代。
- 章節（頁簽）名稱照下表「必要章節」的中文名，不加英文括號（例：寫「連消分布」，不寫「連消分布（Combo）」）。
- HTML 最上方放「← 返回 Demo」，連回 `../index.html`；從 Demo 點進來時改為回上一頁。Demo 的數值報告按鈕在同一分頁開啟，推上網頁後也能用瀏覽器上一頁返回。
- **新報告要收錄到 Omniplay 首頁**：數值報告區不會自動掃描，第一次產出並推上 GitHub 後，在 `AI 工作區/Jumbo_Output/catalog.js` 的「數值報告」區加一筆（title 遊戲中文名、kind "數值報告"、url 用 rhino-boss.github.io 完整網址、game 代號、desc 一行「本作 vs 競品：主要章節」、date 產出日期），同時把 index.html／all.html 的 `?v=` 快取版號加一碼，再推上 Jumbo_Release。（2026-10-22）
- HTML 版式同 `市場資訊/H5/遊戲資訊/` 的競品分析報告：每章一個頁簽、頁簽只排一列可橫拉但不顯示拉條；表格不得出現橫向拉條（儲存格自動換行）。
- **卡片版型**（2026-10-22）：HTML 產出後一律跑 `py -X utf8 專案需知/其他/_report_card_style.py <數值報告_xxx.html>`：淺灰底＋圓角卡片（深色模式為深灰卡片）、膠囊頁簽、襯線大標題，每節（`###`）一張卡片；倍率線型的圖例每一條線都可點選開關。可重複執行，重產 HTML 後再跑一次即可。
- 百分比表格套條件式橫條（同競品報告：同表共用刻度、最大值以強調色、合計列不畫）；表格內只放百分比，不附括號內的分子／分母。

**比較口徑**

- 本作與前作一律用 **Card-On**（正式 RTP／Variant、Oldhand）報表；競品用實機側錄資料。自然機率（Card-Off）只可作附加欄，不得當主比較欄。
- 模擬在模擬機執行（NB ≥ 10⁶ 局、BF ≥ 10⁵ 次），報表存 `Record/` 並在報告來源表列出檔名。
- 指標口徑與競品報告一致；口徑不同時（例：分母只算初始盤面）以競品口徑為準並在該節說明。

**必要章節**

| 章節 | 內容 |
|---|---|
| 1. 基本資訊（放在最前面） | 頁簽之外只留大標題。**開頭第一節為「比較對象」表**：固定三欄「類別｜遊戲｜為什麼比」、固定三列「競品／前作／同系列」；遊戲寫英文名＋廠商或版本（例：Money Coming（JILI）、Money Boost 1.0.0.2（原始版））；為什麼比用一句話說明比較目的；沒有的列遊戲欄填「—」並註明（例：目前沒有同系列作品。）。**報告抬頭資訊一律放在本章**：產出日期、比較口徑（本作／前作／競品各用哪種資料、Profile）、本作版本與主要設定摘要（盤面表與選表比例、補牌與倍數規則、賠率、FG 階梯、BF 價格、EB、自然率門檻、Max Win 等）、**資料來源表**（來源｜樣本數｜報表檔名）。**遊戲簡介 200 字內**：盤面、怎麼贏、特色機制、FG 怎麼觸發、BF 價格，寫到玩家看完就懂規則。**玩法深淺**（NB、BF 分列，與競品／前作／同系列並列）：RTP、標準差（NB 以押注計、BF 以購買價計）、**≥1000x／≥5000x／≥10000x 週期**（以底注計；NB 為每局、BF 為每次購買），並給一句「平／深」結論（看標準差與存活中位數，平均把數由 RTP 決定不具鑑別度）。**存活模擬**：1000 人各帶 1000 元、每把押 1 元玩 NB 至不夠下注，列平均、中位數、最早死 10%（P10）、最晚死 10%（P90）把數；以 Card-On 報表每局總得分分布（BG 非觸發局＋觸發局含觸發把）抽樣，註明抽樣方式。（2026-10-22） |
| 2. 核心指標 | Total RTP、BG Hit Rate、FG Hit Rate（每轉）、FG 週期；有 Buy Feature 的遊戲加列 **BF 贏錢率**（見第 10 章） |
| 3. 金框比例 | 平均每盤金框數、每格金框率、有金框盤面占比、各輪金框率（BG／FG 分開） |
| 4. 金框使用率 | 被消到而翻牌的金框數 ÷ 初始盤面金框數（BG／FG 分開） |
| 5. 倍率線型 | NB-BG、NB-FG、BF 各兩張折線圖：主圖（縱軸 BG 0–1%、FG／BF 0–16%）＋**放大圖（縱軸 BG 0–0.1%、FG／BF 0–1%）**，每張都含競品、前作、本作（卡片後，實線）與**本作自然機率（Card-Off，卡片前，同色虛線，預設隱藏、點圖例才顯示）**；64 區間全標；縱軸固定（BG 0–1%、FG／BF 0–16%），**圖例可點選切換各線顯示／隱藏**（關閉的圖例淡化加刪除線）；附 FG／BF 門檻機率表（含本作自然欄）；**滑鼠游標移到圖上鎖定該區間**，畫垂直線並列出各線數值（隱藏的線不列）；**圖例只寫名稱＋版本**（例：Super Ace、Super Diamond v5.0.0.0、Super Diamond v5.0.0.0 自然），不加括號說明；**圖下不加說明**；**每個區間都畫點**，機率 0 的點在 0 的位置，整條線全部連起來（不斷開）且**線半透明**，超過縱軸上限的部分被圖框裁掉；**x 軸寫法** `0`、`0 < x <= 1`、`1 < x <= 2`…（整數不加小數點，有小數才寫）；**競品一律灰色**，本作用彩色 |
| 6. 連消分布 | BG 每局、FG 每轉的 0／1／2／3／4／5+ 次，含與競品的差（pp） |
| 7. 大鬼出現率 | BG 每局、FG 每轉；並註明本作 BG 幾局一次、FG 每場幾次 |
| 8. 符號消除分布 | 各符號 3／4／5 連的 Hit Rate 與 RTP（BG／FG 分開） |
| 9. WILD 倍數分布 | 有帶倍數 Wild 的遊戲才需要：各種 Wild（如小鬼、大鬼本體、分裂）分開列各倍數占比 |
| 10. BF 回收分布（贏錢率） | 有 Buy Feature 的遊戲才需要。口徑＝每次購買的總贏分 ÷ **購買價**（各遊戲自己的價格，例：競品 40.5x、本作 50x）；分段同競品報告：< 20%、< 40%、< 60%、< 80%、< 100%（賠錢）、**> 100%（贏錢率）**、> 150%、> 200%、> 300%、> 500%，並列 BF RTP。競品用側錄、本作／前作用 Card-On BF 報表；報表倍率區間沒切在門檻上時以相鄰區間估計並註明「約」 |
| 11. 得分區間與最大獎機率 | 由卡片權重 `config_9xx.js` 精算（非模擬）。每個 **RTP／Variant（A／B 版）× 押注模式（NB／EB／BF）× 新老手 × 押注層級（小／中／大 Bet；卡片不分層級時標「不分」）** 一列：BG 得分區間（有權重的最低～最高區間）、FG／BF 得分區間、**最大獎區間**（可開出的最高區間）、**最大獎機率**（每局；BF 為每次購買）與週期 |

沒有對應機制的章節（例如無金框、無大鬼）可省略，但要在報告開頭註明；頁簽編號一律從 1 依序連號，省略章節後也重新連號（不沿用本表編號）。指標未達使用者設定的對標目標時，於回報中列出差距與可調的槓桿，由使用者決定是否調整；調整後重跑 Card-On 並重出數值報告。

## 7. 異動時的重跑範圍

| 異動 | 必做流程 |
|---|---|
| Paytable、Reel、Table、Feature、Bet Mode、判獎 | 更新基礎 XLSX與版本 → 同步受影響 RTP／Variant → 轉 Config → 全部受影響批次重跑 → Demogame 對帳 |
| Card System 區間或權重 | 更新受影響 RTP／Variant XLSX 第 2 碼 → 轉 Config → Card System On 批次重跑 → 檢查占比與 Retry |
| SCR | 更新受影響 RTP／Variant XLSX 第 3 碼 → 轉 Config → 重跑 SCR 相關批次 |
| 文件、說明或排版 | 依規格更新第 4 碼；若不影響執行結果，不沿用舊版號產生新正式報表 |
| Simulator 數學邏輯 | 修正程式 → 固定 Seed 回歸 → 小場次 → 所有受影響正式批次 → Demogame 對帳 |
| 報表或顯示邏輯 | 驗證統計來源未變 → 核對 Console 與 Excel → 依影響範圍重產報表 |

## 8. 禁止事項

- 未確認 Game Rule 就自行補猜核心數學規則。
- 直接修改由 XLSX 產生的 Config 參數來避開轉檔。
- 建立或保留 Excel↔Config、Config↔Excel 的轉檔工具；轉換一律由 AI 執行。
- Simulator、Demogame 與 Config 各維護一套參數。
- 只跑 Card System On，不保留自然機率基準。
- 只驗證 Total RTP，不驗證 RTP Breakdown、分布、Feature 與 Retry。
- Card System Retry 時重抽目標卡、重複扣款或污染場次統計。
- 未升版就覆寫正式 XLSX、Config 或 Record。
- 建立產品未使用的空白 B Variant、Mode 或 Profile。
- 直接複製舊專案的不相容命名、版本、報表欄位或遊戲專屬統計。
- 用全零欄位表示不存在或尚未驗證的功能。
