4. 開新專案必讀流程

開啟新的遊戲專案（或接手既有模型改版）前，必須依下列順序讀完相關規範：

  1. 本 README：共通原則與完成條件。
  2. 開發流程.md：整體流程、製作順序與階段關卡。
  3. 數學模型規範.md：建立數學模型與 Card System 前必讀。
  4. 數學文件規範.md：撰寫 Game Rule、Help 等文件前必讀。
  5. 送驗文件規範.md：製作 Game Description DOCX、Math Document Description 與數學模型送驗版前必讀。
  6. 模擬程式規範.md：撰寫 Simulator 與產生 Config 前必讀。
  7. Demogame規範.md：製作 Demogame 前必讀。
  8. 腳本規範.md：製作表演腳本前必讀。
  9. 提案報告規範.md：製作提案報告（提案說明簡報）前必讀。
  10. 壓測說明書.md：安排後端壓測與判讀壓測報表前必讀。
  11. 後端報表筆記.md：核對後端 SPS 報表（倍率權重、Card System）前必讀。

只執行部分工作時，至少要讀完本 README 與該工作對應的文件。

5. 維護規則：HTML 同步

本資料夾另提供彙整版 igaming_specification.html（根目錄全部規範合併、頁籤式），各產線資料夾另有自己的彙整版（如 Landbase/landbase_specification.html），皆由 _build_html.py 從 md 自動產生。

  • 任何一份 .md 更新後，必須在同一次修改中重跑產生器同步 HTML：
  py _build_html.py
  • 不得直接手改任何一份彙整版 HTML；內容修正一律改 md 再重建。
  • 產線資料夾內的 .md 連回根目錄規範時寫 ../檔名.md，產生器會轉成根 HTML 的對應頁籤。

6. 共通原則

數學文件／XLSX
      ↓ AI 轉檔與驗證
    Config
     ├─→ 模擬程式 → Record 報表
     └─→ Demogame  → 操作與逐局對帳
  • 數學文件與 Source/*.xlsx 是規格來源，Config 是程式執行時的共同參數來源。
  • Excel 與 Config 之間的轉換（含 game_help_draft.md → {GameID}_Help.xlsx、數學模型 → PARsheet）一律由 AI 執行；專案內不建立、不維護轉檔工具。
  • 模擬程式與 Demogame 必須讀取同一份 Config，不得各自維護另一套輪帶、權重、Paytable 或 Feature 參數。
  • game_rule.md 必須說明玩法、判獎順序、倍率口徑、Feature 流程與例外；程式不可補猜未定義的規則。
  • Game Rule 是遊戲規則的正式說明來源；數學模型、程式與 Help 必須與其一致。
  • Help 必須依 Game Rule 編寫，並同時維護 {GameID}_Help.xlsx 與對應的 Markdown 文件；兩者內容不得不一致。
  • 同一項資料若在多個檔案出現，修改時必須同步更新並完成對帳。
  • 未支援的 RTP、Variant、Bet Mode、Profile 或 Feature，不得出現在 Config、Simulator 批次或 Demogame 選單。
  • 會影響結果分布、RTP、觸發率、最大獎或 Retry 的修改，都必須更新版本並重新模擬。

7. 完成條件

模型只有在下列條件全部成立後才可視為完成：

  1. 數學規則與計算口徑明確，無未決定的核心邏輯。
  2. Config 可由數學來源重建，版本與參數可追溯。
  3. Simulator 已完成所有支援組合的統計驗證。
  4. Card System 的權重、區間、Retry 與失敗監控通過。
  5. Demogame 的代表性單局可與 Simulator 對帳。
  6. 開發流程.md 第 2 節的必要產出文件（game_rule.md、game_help_draft.md／{GameID}_Help.xlsx、game_description.md、數學模型／PARsheet、config.js、Simulator.py、index.html、數值報告_<遊戲中文名>.md＋.html、{GameID}_Game Description.docx、{GameID}_Math Document Description.md＋_EN.md）全部齊備，與 Game List 均為同一正式版本，且必要的 Markdown 文件皆已同步更新。

Slot 數學開發流程

本文件定義新 Slot 專案的數學開發流程、製作順序、操作方式、階段產物與完成條件。

實作欄位、命名、版本、Card System、Simulator、Demogame、Config 與報表格式等細節，統一依照本資料夾的各規範文件（總覽見 _README.md）。本文件不重複定義實作規格；內容有差異時，以各規範文件為準。

適用範圍：Project/Slots/H0xx_遊戲名稱/ 下的新遊戲數學模型、既有模型改版，以及 RTP、Card System、Feature 或 Bet Mode 參數調整。

1. 過往專案整理後的標準做法

過往專案可看到數種演進中的做法：

  • H013、H015、H019 使用 RTP Config、Simulator 與 Record 的基本流程。
  • H016、H028 已拆分基礎 config.js 與 RTP／Variant Config，並保留 Versions/，較符合目前標準。
  • H026 同時存在 92／94 與 A／B Variant，適合作為多模型組合的參考。
  • 早期專案（H013～H027）曾使用 xlsx_to_config.py、model_sync.py 等轉檔腳本同步 Source 與程式資料；此做法已淘汰，Excel 與 Config 之間的轉換一律由 AI 執行，專案內不建立、不維護轉檔工具。

新專案採用以下統一原則：

  1. game_rule.md 定義玩法，數學 XLSX／Source/ 定義正式參數。
  2. Config 必須由 Source 轉出（轉換由 AI 執行，不建立轉檔工具），不直接手改轉出的參數。
  3. Simulator 與 Demogame 使用同一份 Config。
  4. 先驗證 Card System Off 的自然機率，再驗證 Card System On。
  5. 每次調參都依「Source → 版本 → Config → Simulator → Record → 對帳」完整重跑。
  6. 舊專案若與目前命名、版本或報表格式不同，不直接複製舊格式；依現行規格建立。

5. 各階段操作方式

5.1 開案與數學目標確認

  1. 建立 H0xx_遊戲名稱/ 專案資料夾。
  2. 讀取並確認 game_rule.md。
  3. 與使用者確認本專案的數學模型組合——每款遊戲的數學模型都不一樣，不得逕自沿用他款設定。未特別說明時，預設組合為：
    • A／B 兩個 Variant × 92／94 兩個 RTP，乘開共 4 個版本（92A、92B、94A、94B）。
    • 每個版本都有 Newbie／Oldhand 兩種 Profile。
    • 各版本依其支援內容有對應的押注區（Oldhand 小／中／大 Bet 層級）。
  4. 列出所有正式支援組合：RTP、Variant、Profile、Oldhand 小／中／大 Bet、NB／EB 或 BF／SF 模式類別、Bet Mode、Card System Off／On。
  5. 為每個組合定義 Link／Bonus Game／Game RTP、Total RTP、Link 資格、Hit Rate、Feature Frequency、BG／FG Max Multiplier 與其他遊戲專屬指標。
  6. 將未決定的判獎順序、倍率分母、Feature 上限與例外退回確認；未確認前不製作正式模型。

5.2 建立基礎數學模型

  1. 先完成 Base Game，再依狀態順序完成 Feature。
  2. 建立 Symbol、Paytable、Reel Strip／Weight、Table 與 Bet Mode。
  3. 建立 BG、FG、Cascade、Multiplier、Retrigger、Jackpot 等流程。
  4. 計算 RTP Breakdown 與理論 Max Win，不只計算 Total RTP。
  5. 建立基礎數學 XLSX，版本依規格使用 1 碼。

5.3 建立 RTP／Variant 與 Card System

  1. 只建立 5.1 與使用者確認過的 92／94、A／B 組合（未特別說明時為 92A、92B、94A、94B 四版本，各含 Newbie／Oldhand 與對應押注區）。
  2. A／B 表示數學 Variant，不表示 Newbie／Oldhand。
  3. 依 Profile、Oldhand 小／中／大 Bet 與 Bet Mode 建立 BG／FG 卡片區間及權重；NB／EB 以實際模式押注、BF／SF 以 Feature 基礎押注選擇層級。
  4. 確認每張正權重卡片的區間可達，並定義 Retry 行為。
  5. 建立 RTP／Variant XLSX，版本依規格使用四段格式。

5.4 轉檔與 Config 驗證

  1. 在數學模型的 Game Description 工作表記錄每項 Config 資料的來源。
  2. 由 AI 依 Source 與 Mapping 轉出 Config；專案內不建立、不維護 Excel↔Config 轉檔工具。
  3. 執行欄位、型別、陣列長度、ID、Weight、Min／Max、版本與模式驗證。
  4. 比較轉檔前後資料，確認 Config 可由 Source 重建且沒有非預期差異。
  5. 轉檔錯誤時修正 Source 或 Mapping 後重新轉出，不直接修改 Config 大型陣列。

5.5 Simulator 開發與 Debug

  1. 先完成自然機率核心，再加入 Card System 篩選與 Retry。
  2. 讓 Simulator 直接讀取正式 Config，不另寫一份參數。
  3. 建立固定 Seed、單執行緒與逐局 Trace 模式。
  4. 建立強制／指定案例，驗證無獎、一般獎、Wild、Scatter、Feature、Retrigger、倍率與封頂。
  5. 小場次確認正確後，再加入 Numba、多執行緒、BATCH_RUNS 與 Excel 報表。

5.6 模擬順序

模擬必須依下列順序執行：

  1. 小場次、Card System Off：驗證流程與報表。
  2. 中場次、Card System Off：確認自然機率 RTP 與分布。
  3. 大場次、Card System Off：以 NB 10⁹ 局（BF 為 10⁸ 局）產出自然機率正式報表。
  4. 卡片權重調性校準：依上一步報表分配各得分區間的卡片權重，使分布、RTP 拆分與 FG 週期符合目標遊戲調性；完成後才進入 Card System On。
  5. 小場次、Card System On：確認抽卡、Profile、Oldhand 押注層級、Link 資格、倍率上限、Mode 與 Retry。
  6. 中場次、Card System On：調整區間、權重與目標 RTP。
  7. 所有正式組合的大場次模擬。
  8. Max Win、低機率 Feature 與 Retry 邊界的專項驗證。

  2. 再檢查自然機率的 Paytable、Reel、Table、Feature。
  3. 最後才調整 Card System 區間與權重。
  4. 不得只為讓 Total RTP 接近目標而忽略 RTP Breakdown、Hit Rate、Feature Frequency、分布或 Retry。

5.8 對帳與交付

  1. 選定可重現的代表性 RNG／Seed。
  2. 逐項核對 Config、Simulator 與 Demogame 的盤面、判獎、Feature、倍率、Total Win、Coin In 與 Retry。
  3. 完成所有正式組合的最新 Record。
  4. 將正式 Config 與歷史版本關係寫入 Versions/ 與 manifest。
  5. 確認第 2 節必要產出文件全部齊備且為同一正式版本。
  6. 清除暫存檔、舊測試輸出及不屬於正式交付的檔案。
  7. 依第 9 節完成最終驗收。

5.9 數值報告（對標競品與前作）

卡片權重完成後（第 4 節卡片權重調性校準之後），產出數值報告（即本作與競品、前作的差異分析），比較本作與競品（及使用者指定的前作）的玩法指標，作為調性是否到位的依據。

檔案與格式

  • 檔名 其他/數值報告_<遊戲中文名>.md ＋ 同名 .html（例：數值報告_宙斯 2500、數值報告_超級鑽石、數值報告_錢來襲），兩份內容一致；不另取其他檔名。舊名 差異分析_<遊戲中文名> 一律改為此名。
  • 遊戲名稱一律用英文名（例：Super Diamond、Super Ace、Lucky Ace），不用 H0xx 代號。
  • HTML 版式同 市場資訊/H5/遊戲資訊/ 的競品分析報告：每章一個頁簽、頁簽只排一列可橫拉但不顯示拉條；表格不得出現橫向拉條（儲存格自動換行）。
  • 百分比表格套條件式橫條（同競品報告：同表共用刻度、最大值以強調色、合計列不畫）；表格內只放百分比，不附括號內的分子／分母。

比較口徑

  • 本作與前作一律用 Card-On（正式 RTP／Variant、Oldhand）報表；競品用實機側錄資料。自然機率（Card-Off）只可作附加欄，不得當主比較欄。
  • 模擬在模擬機執行（NB ≥ 10⁶ 局、BF ≥ 10⁵ 次），報表存 Record/ 並在報告來源表列出檔名。
  • 指標口徑與競品報告一致；口徑不同時（例：分母只算初始盤面）以競品口徑為準並在該節說明。

必要章節

章節內容
0. 核心指標Total RTP、BG Hit Rate、FG Hit Rate（每轉）、FG 週期
1. 金框比例平均每盤金框數、每格金框率、有金框盤面占比、各輪金框率（BG／FG 分開）
2. 金框使用率被消到而翻牌的金框數 ÷ 初始盤面金框數（BG／FG 分開）
3. 倍率線型NB-BG、NB-FG、BF 三張折線圖，每張都含競品、前作、本作；64 區間全標；縱軸固定（BG 0–1%、FG／BF 0–16%），超過上限的區間不繪製並在圖下列出；附 FG／BF 門檻機率表
4. 連消分布BG 每局、FG 每轉的 0／1／2／3／4／5+ 次，含與競品的差（pp）
5. 大鬼出現率BG 每局、FG 每轉；並註明本作 BG 幾局一次、FG 每場幾次
6. 符號消除分布各符號 3／4／5 連的 Hit Rate 與 RTP（BG／FG 分開）

1. 數學模型

數學模型是包含公式、計算過程、輪帶、權重、參數與驗證依據的完整文件，也是產出 PARsheet 與 Config 的數學來源。

1.1 必要內容

模型開始實作前，數學文件至少要定義：

  • Game ID、遊戲名稱、盤面尺寸與 Lines／Ways／Cluster 等得分方式。
  • Symbol、Paytable、Wild／Scatter 規則與判獎順序。
  • BG、FG、Cascade、Multiplier、Retrigger、Jackpot 等流程。
  • Normal Bet、Extra Bet、Buy Feature、Super Feature 的成本與差異。
  • 各 RTP 家族、Variant、Player Profile 與押注層級的 Link／Bonus Game／Game RTP 拆分及 Total RTP。
  • Oldhand 必須依小 Bet／中 Bet／大 Bet 分別定義倍率權重。
  • Feature Trigger Rate、Hit Rate、Max Win／Max Multiplier 與上限。
  • Card System 的區間、權重、倍率分母、Retry 與失敗處理。
  • 同局同時符合多項條件時的處理優先順序。

計算口徑必須明確區分：

RTP = Total Win ÷ 實際 Total Bet
卡片判定倍率 = 指定結果得分 ÷ card_system_coin_in
Max Multiplier = Round Total Win ÷ 該模式定義的基準成本

1.4.6 Demo 版 RTP（120%）

上在 Demo 網頁（展示、試玩用）的版本，RTP 目標為 120%。以正式上線的權重為底，只調整卡片權重，不動輪帶、Paytable 與 Feature 規則。

差額    = 120% − 來源版本 RTP
BG 補足 = 差額 × 1/2   → 加在 BG 的 (25, 30] 區間
FG 補足 = 差額 × 1/2   → 縮短 FG 週期
  • BG：提高 (25, 30] 區間的權重，使 BG RTP 增加差額的一半。增加的權重從 (-1, 0] 區間扣除，其餘區間不動，各欄總和仍為 1,000,000,000。
  • FG：提高 FG 觸發卡的權重、縮短 FG 週期，使 FG RTP 增加差額的一半；FG 的倍率區間權重不動，每場 FG 的平均倍數不變。增加的觸發權重同樣從 (-1, 0] 扣除。
  • 新的 FG 週期：新週期 = 原週期 × 原 FG RTP ÷（原 FG RTP ＋ 差額 ÷ 2）。
  • 例：來源版本 BG 72%、FG 20%、FG 週期 300，總計 92% → 差額 28%；BG 補 14% 到 86%，FG 補 14% 到 34%，新週期 ≈ 300 × 20 ÷ 34 ≈ 176.5。
  • 計算 RTP 與驗證都以 Card On 實跑為準，模擬結果須在 120% 的 2σ 內。
  • Demo 版權重只用於 Demo 網頁，不得進入正式上線的 Config 或送驗文件；Demo 版的工作簿、Config 與報表要在檔名或版本註記清楚標示為 Demo。

              2. Card System

              2.1 定位與限制

              Card System 是結果篩選與分流機制，不是獨立玩法。遊戲先依原始輪帶、盤面、判獎與 Feature 流程產生結果，再依預先抽出的卡片條件決定接受或重跑。

              Card System 可控制倍率區間、要求觸發 Free Game、依 Newbie／Oldhand 與 Oldhand 小／中／大 Bet 改變結果分布，並依 Bet Mode 拆分 BG、FG、Buy Feature 與 Super Feature 的目標。

              Card System 不得直接修改輪帶、Paytable、判獎公式、符號功能、FG 局數或演出流程。重跑會改變最終結果分布與 RTP，因此必須以實際流程模擬，不能只用權重推算。

              2.3 卡片判定

              range 卡使用 (min, max]：

              結果倍率 > min 且 結果倍率 <= max
              • (15, 20] 不包含 15x、包含 20x；需要包含 0x 時可用 (-1, 0]。
              • Newbie BG 的最高可用區間為 (25, 30]，FG 的最高可用區間為 (100, 120]；超過各自上限的區間權重必須為 0。
              • Oldhand 小／中 Bet FG 的最高可用區間為 (10000, 20000]；Oldhand 大 Bet FG 的最高可用區間為 (1000, 2000]。

              天花板機制（觸發局的得分上限，以重骰實現）：

              • BG 觸發 FG 的那一把，BG 得分必須 ≤「該 Profile BG 卡組最高有權重區間」的上限（例：Newbie BG 最高有權重區間 (25, 30] → 上限 30x）；超過上限就整把重骰（與 free_game 卡的觸發重試合併判定：重骰到「有觸發且 BG 得分 ≤ 上限」為止）。
              • 非觸發局由區間卡判定本來就落在區間內，不受天花板影響；卡片關閉（自然機率模擬）不套用。
              • 重骰使觸發局 BG 平均變為截斷條件平均 E[X | X ≤ 上限]：Detail／Detail_Newbie 的 Free Game 列平均倍率必須填此值（會與同列 Pay÷Cnt 的自然值不同，屬正常，須註記），BG 權重配平以此值計算 RTP。
              • 模擬器必須實作相同重骰，否則 Card-On 驗證與真實遊戲不一致（上限低的 Profile 差異明顯，例：Newbie 約 1pp）。
              • 任一區間超過目前 Profile／押注層級的 Max Multiplier 時，其權重必須為 0。
              • BG 已觸發 FG 時，即使 pay_bg 落入區間，也不得當作一般 BG range 結果。
              • free_game 卡未觸發 FG 時必須重跑 BG。
              • free_game 卡必須同時驗證 BG 倍率上限（BG Trigger Cap）：除觸發 FG 外，觸發該次 BG 的倍率不得超過同一 Profile／押注層級／Mode 之 base_game 內所有正權重 range 卡的最大 max。
              • BG Trigger Cap 使用 Normal Bet 基準成本計算，判定式為 pay_bg / card_system_coin_in <= cap；等於上限時可接受，超過上限時整把 BG 重跑。
              • weight = 0 的 range 卡不得用來放大 cap；啟用 free_game 卡的 Profile／Mode 必須至少有一張正權重 range 卡可提供 cap。
              • 事件卡只定義接受條件，不得直接放置 Scatter 或直接呼叫 FG。

              2.3.1 Link 資格

              • Link 資格一律依第 1.4.3 節算出的 bet_tier_amount 判斷；NB／EB／BF／SF 都使用同一組 < $2、$2～$100、> $100 邊界。
              • Newbie 不得觸發或獲得 Link 彩金，Link RTP 必須為 0%。
              • Oldhand 小 Bet 不得觸發或獲得 Link 彩金，Link RTP 必須為 0%。
              • Oldhand 中 Bet 與大 Bet 可以觸發 Link 彩金，Link RTP 目標為 2%。
              • link_enabled = false 時不得只把 Link 派彩改成 0；結果中不得出現已觸發但不派彩的 Link 事件或演出。
              • Link 資格、觸發流程與 RTP 統計必須由 XLSX、Config、Simulator 與 Demogame 使用同一套設定。

              卡片權重（含倍率上限、天花板重骰）調整後，必須確認「畫面會出現的元素，在 Card System 開啟時都有機會得分」，不得出現只出現、永遠不會得分的情況。

              • 檢查範圍：每個 RTP／Variant × Bet Mode × Profile／押注層級逐一檢查；凡該組合在畫面上看得到的元素都要列入，例如：
                • 規格或盤面會出現的倍數球、倍數 Wild、高倍符號（例：1000x／2500x 球）；
                • 轉盤、Bonus 的每一格獎項；
                • 特色符號（倍數、Respin、Bonus）在「有得分」情況下的出現；
                • 盤面可組成的各種得分組合（例：數字串接遊戲的每種數字分）。
              • 判定方式：以 Card-On 的實際分布計算（精算優先；無法精算時用模擬機 ≥ 10⁸ 局），每個元素「得分出現機率 > 0」才算通過；只看到出現、但所在倍率區間權重為 0 或被倍率上限擋掉者，判為不通過。
              • 不通過時的處理（擇一，並在數值報告註明）：
                1. 調整卡片權重，讓該元素所在區間有可抽到的正權重（區間在所用的表上自然機率要夠高，避免 Retry Limit Exceeded）；
                2. 若產品上就不該開出，改輪帶／權重讓該元素不在畫面出現，或在 Help 與規則中移除。
              • 檢查結果（各元素的得分機率或「通過／不通過」）列在數值報告；有任何不通過不得視為完成交付。

              1.4 用詞一致性

              用詞不一致不會讓數值出錯，但送驗時容易被挑，屬警告等級（明顯錯字升為錯誤）：

              • 單一文件內部：同一概念不得混用大小寫／連字號／空格變體（GOLD-FRAME vs GOLD-FRAMED、Free Game vs FreeGame）、單複數（Free Spin vs Free Spins 同語境混用）或同義換名（同一機制一下 Free Game、一下 Free Spin；一下 Wild、一下 Joker）。
              • 跨三份文件：功能名稱、符號名稱、RTP 分類名（Base Game／Free Game／Bonus／Link）在 Game Description、Math Document Description、PARsheet 之間必須同名。
              • 中英對照：同一中文概念只對應一組英文譯名（「免費遊戲」不得一處對 Free Game、另一處對 Free Spin）。

              1.5 SHA1 清單

              送驗報告（BMM 的 Draft／Letter）會逐檔列出送驗檔案的 SHA1 並據以認證。我方必須在送驗包內留一份對應清單 {GameID}_SHA1.txt，日後報告的 SHA1 表才有東西可比；被質疑時能立刻證明「BMM 驗的是不是我們手上這一份」。

              規則

              • 每一次產出送驗壓縮檔前都要重產清單，且清單要一起打包進 zip。順序固定：先產清單，再打包；否則 zip 內的清單會是舊的或缺漏。
              • 清單涵蓋送驗包內所有送驗標的（Game Description、Math Document Description、PARsheet/*.xlsx、Simulator/*）；不列入清單本身，排除 ~$ 開頭的 Office 暫存檔與 __pycache__/。
              • 路徑用相對於遊戲資料夾的形式（含子資料夾，如 PARsheet\H026192.xlsx），依相對路徑排序。
              • SHA1 為 40 碼大寫十六進位；Generated 填產生當天，MODIFIED 填檔案自身的修改時間。
              • 檔案一律二進位複製，不得開啟後另存：xlsx／docx 重存會改變位元組，SHA1 就與 BMM 認證的對不上。落地後逐檔重算 SHA1 確認與來源相同。
              • 換掉已被報告認證的檔案，等於讓該報告的 SHA1 失效：已有 Draft 的要請 BMM 依新版重出，已有 Letter 的先確認是否真的要動。
              • 產完清單掃一眼有無重複雜湊：不同檔案不該有相同 SHA1（實例：106003 的 H506R_MSweight_BG.xml 與 _FG.xml 雜湊相同，BG／FG 權重被交付成同一份檔案）。

              2. Game Description

              送驗用的 Game Description 以數學文件規範.md的完整版為基礎，移除 1.3 禁止項目（Extra Bet／Buy Feature／Super Feature 與 >$2 門檻相關章節與敘述）後產出；除刪減處外必須與完整版完全一致。

              格式（字型、字級、邊界、標題與表格樣式）一律複製既有已核准的 Game Description 文件，不重新自建格式——公司對格式的核准是一次性的，自行重建有偏離已核准樣式的風險。

              • 內容以該遊戲的 {GameID}_Help.xlsx 或 game_help_draft.md 的英文欄逐字填寫，不得改寫、摘要或自創文字——Help 是已核准的規則措辭唯一來源，改寫會製造兩份互相矛盾的文件。

              • 佔位符（[WW]、[C1]、{12}、X2 等）原樣保留；{n} 花括號要嘛全篇保留、要嘛全篇展開為實際數字，不得混用。
              • 保持 Help 的章節順序，不重排、不遺漏；純圖片佔位列（[走線圖 ...]、[跳階示意圖]）跳過。

              • Title 樣式段落「GAME DESCRIPTION」＋置中一般樣式段落放遊戲英文名。

              模擬程式規範

              1. 模擬程式

              Simulator.py 是數學模型的主要驗證工具。數學邏輯、批次設定、Console 輸出與 Excel 報表必須使用相同的統計口徑。

              1.1 程式架構

              1.1.1 加速：Numba、多執行緒

              • 高頻數學核心使用 Numba 編譯；適用的核心函式使用 @njit(nogil=True)。
              • 使用多執行緒平行執行模擬，例如 ThreadPoolExecutor；每個 Worker 必須持有獨立的 RNG 狀態。
              • 正式計時前先執行 Warm-up，Numba 首次編譯時間不得計入 duration。
              • Numba Core 只處理數值及固定型別 Array／Tuple；Config 解析、字串、DataFrame 與 Excel 留在 Python 層。
              • 預先配置統計陣列與暫存 Buffer，模擬迴圈內不得反覆建立大型物件。
              • 場次平均分配給各 Worker，餘數由前幾個 Worker 各多執行一場；合併後必須等於 total_rounds。
              • Worker 回傳相同 shape／dtype；Count 與 Pay 欄位相加，Max 欄位取最大值。
              • 固定 RNG、逐局 Trace 與 Debug 重現模式使用單執行緒。

              1.1.2 程式邏輯

              程式依下列順序執行：

              1. 讀取 BATCH_RUNS 的本批參數。
              2. 載入 config_file 的自然機率參數。
              3. 載入 config_rtp_file 的倍率權重參數。
              4. 驗證兩份 Config 的 game_id、版本與資料相容性。
              5. 將 Config 正規化為模擬核心使用的固定型別資料。
              6. 依 bet_mode、Card System 開關、Profile 與基礎押注額建立本批設定，並選出押注層級、Link 資格及倍率上限。
              7. 執行 Warm-up，再開始正式計時與多執行緒模擬。
              8. 合併 Worker 統計，計算 RTP、Hit Rate、Feature、Retry 與遊戲專屬指標。
              9. 依固定格式印出執行結果。
              10. 需要輸出時，將相同結果寫入 Record/*.xlsx。

              數學核心與報表／顯示邏輯必須分離。Card System 關閉時，不得執行抽卡或 Retry；config_rtp_file 不得改變 config_file 所定義的原始盤面與自然機率邏輯。

              1.1.3 執行結束後印出的內容

              每個 Batch 結束後必須依第 1.3 節的順序與格式輸出，不得只印 RTP。欄位名稱固定使用英文，數值格式由共用格式化函式處理。

              1.2.1 BATCH_RUNS

              BATCH_RUNS 用於定義要依序執行的模擬組合。每一筆至少包含：

              欄位必要說明
              config_file是自然機率參數檔；提供輪帶、Table、盤面與原始遊戲機率。
              config_rtp_file是倍率權重參數檔；提供 RTP／Variant 與 Card System 使用的倍率權重。
              bet_mode是押注模式，例如 0 為 Normal Bet；其他值依遊戲規格定義。
              total_rounds是本批正式模擬的付費 Round 數，必須為正整數。
              card_system_enabled是是否啟用 Card System，型別為 Boolean。
              card_system_is_newbie是true 為 Newbie、false 為 Oldhand；Card System 關閉時不套用 Profile。

              BATCH_RUNS = [

        "config_file": "config.js",
        "config_rtp_file": "config_92A.js",
        "bet_mode": 1,
        "total_rounds": 1_000_000,
        "card_system_enabled": True,
        "card_system_is_newbie": False,
        "base_bet": 1,
    },
]

              • 每批重新載入兩份 Config，不得沿用上一批的全域狀態。
              • Config 的 game_id 不一致時立即停止，不得繼續模擬或輸出報表。
              • Card System Off 必須另跑自然機率基準；正式大場次前先以小場次檢查流程與報表。
              • NB／EB 必須用實際模式押注金額驗證 $1.99、$2、$100、$100.01 邊界；BF／SF 必須用反推後的 Feature 基礎押注驗證相同邊界。

              1.3 執行結束後印出的內容

              1.3.1 固定順序與共用格式

              Console 輸出順序是固定規範，不得依 dict、DataFrame 或統計完成時間任意排序。每個 Batch 必須依下列順序輸出：

              1. Batch 標題：=== Batch n/total: {...} ===。
              2. 遊戲資訊：game_name、game_id。
              3. Config 與版本：config_file、config_rtp_file、math_version、card_system。
              4. 執行設定：bet_mode、bet_multi、feature_price_multiplier、base_bet、bet_amount、bet_tier_amount、bet_tier、link_enabled、max_multiplier_bg、max_multiplier_fg、coin_in、total_rounds、duration。
              5. RTP 與 Feature 統計：從 rtp_total 到 avg_fg_spins。
              6. FG／特殊符號統計：bg_trigger_fg_cnt、bg_trigger_fg_pay、special_symbol_cnt、SCR。
              7. 波動資訊：volatility_std、standard_error。
              8. Card System 資訊：從 card_system_profile 到 retry_limit_fg；只在 Card System 開啟時整段顯示。
              9. 遊戲專屬資訊：<< By Game Info >> 及該遊戲規定的 By Game 欄位。
              • 欄位必須依下方範例逐項排列，不得交換前後順序。
              • 空白行只用於區塊分隔，不影響欄位順序；不得在同一區塊中插入其他欄位。

              • game_id 與所在遊戲資料夾一致。

              • RTP／Variant Config 的版本第 1 碼，必須與 config.js 及基礎 XLSX 的版本相同。
              • Config 檔名、類型、內部 RTP／Variant 與來源 XLSX 相符。
              • 所有 Weight 非負，啟用選項的總權重大於 0。
              • Newbie 與 Oldhand 小／中／大 Bet 的權重、Link 資格、RTP 拆分及倍率上限齊全且互相一致。

              3. 補牌方式

              每款有消除機制的遊戲，必須在 Game Rule、Config 對應說明與 Demogame 中指定唯一補牌方式。Simulator 與 Demogame 必須使用相同邏輯。

              1. 消除後原地補牌
                • 中獎符號消除後，只在原本的空格位置抽取並顯示新符號。
                • 盤面上未消除的符號維持原座標，不播放向下移動動畫。
                • 新符號在空格原位播放 Refill 動畫。
              2. 消除後掉落補牌
                • 中獎符號消除後，同一 Reel／Column 上方未消除的符號依重力向下補位。
                • 剩餘空格由新符號從盤面上方掉入。
                • 動畫必須區分既有符號的 Settle 與新符號的 Drop／Refill。
              3. 特殊補牌（By Game）
                • 不符合前兩類的 Random、Parallel、跨欄移動、整盤替換或其他特殊補牌皆歸此類。
                • 必須在該遊戲的 game_rule.md 與數學模型的 Game Description 工作表中明確定義抽取來源、移動方向、補牌順序、保留位置及動畫。
                • 不得把單一遊戲的特殊補牌邏輯寫成所有遊戲共用的預設行為。
              • 補牌資料必須來自 Config 定義的 Reel／Drop Table／Weight，不得只為動畫另外抽一組結果。
              • 補牌後重新判獎的次數、盤面與得分必須可由 Debug 結果重現，並與 Simulator 對帳。
              • Symbol 轉 Wild、鎖定位置或不補牌的位置，必須先依遊戲規則處理，再執行選定的補牌方式。

              4. 必要行為

              • 支援 Normal Spin，以及遊戲實際存在的 Extra Bet、Buy Feature、Super Feature。
              • Bet 顯示與 Credit 扣款使用實際模式成本；Win 依流程加入。
              • Auto、Speed、Reset 不得改變 RNG、得分或統計結果。
              • BG、Cascade、FG、Retrigger 與 Feature 狀態按真實流程播放。
              • Config、Version、Profile、押注層級、Card System 與 Language 只顯示實際支援的內容。

              1. 用途與定位

              表演腳本是預先錄製的 RNG 序列與固定結果，供前端在特定情境直接重放，用於新手體驗、Buy Feature 展示與 Free Spin 系統等。

              4. 挑選規則

              4.1 新手體驗

              • 每支權重＝1、押注＝1；同名 A／B 兩支等權重擇一。
              • 總倍率為體驗設計值，製作前與使用者確認（參考值：Free Game 12x、Jackpot Game 10x）。

              4.2 Buy Feature

              • 每個版型三支：高／中／低 RTP 各一，另配抽選權重；押注＝Buy Feature 價格倍數。
              • 加權整合必須等於 96.00%：Σ(RTP × 權重) ÷ Σ(權重) = 96.00%。
              • 三檔 RTP 先定，權重由上式解出並整數化；解出後驗算到小數 2 位精確。
              • 參考例（前作 92 版）：105.67%×800＋88.80%×200＋81.53%×435 → 加權 96.00%。

              4.3 Free Spin 系統

              • 適用新手 NB 的免費遊戲段（一段 10 把）。
              • 挑法：10 把中挑一把跑 0-1x 腳本、挑一把跑 9x 腳本，其餘各把不中獎。
              • 9x 腳本固定 10 支，抽選權重鎖死全部＝1（等權重擇一），不得調整。
              • 整段合計約 10x（參考值：0-1x＝44%＋9x＝955.56% → 999.56%）。

              4.4 版型與共用

              • 腳本表依 RTP 版型分組（例：92 版一張）；同一支 RNG 序列若在多個 RTP 版可重放出相同結果，可跨版共用並註記。
              • 大額投注使用獨立模型（_Bet100）的遊戲：腳本倍率不得超過該模型的倍率上限（例：FG 上限 2,000x）。

              5. 製作前必須與使用者確認

              1. 新手體驗涵蓋哪些押注模式（NB 以外是否含 EB／BF 體驗）。
              2. 各體驗腳本的目標倍率（Free Game／Jackpot Game）。
              3. 腳本表做哪些 RTP 版型、是否跨版共用。
              4. Buy Feature 三檔 RTP 的目標值（權重由 96% 約束解出）。

              6. 交付檢查

              • ☐ 腳本清單依第 2 節結構建立，未支援的模式沒有腳本。
              • ☐ 每支 RNG 序列已在正式 Config 下重放驗證，結果與表列 Multi 一致。
              • ☐ Buy Feature 各版型加權整合＝96.00%（小數 2 位精確）。
              • ☐ Free Spin 系統：9x 腳本 10 支、權重全部＝1；0-1x 與 9x 各佔一把、其餘不中獎。
              • ☐ 腳本倍率未超出該模式（含 _Bet100 模型）的倍率上限。
              • ☐ 輪帶／掉落改版後已重新驗證重放（或重錄）。

                5.3 判定

                項目標準
                總 RTP（不含 JP）σ = volatility_std ÷ 模式倍數 ÷ √TotalSpin，**\實測 − 目標\≤ 2σ**；volatility_std 取同 Config／Profile／模式的 Simulator Card-On 報表
                有權重的區間z = (實測占比 − 權重) ÷ √(權重 × (1 − 權重) ÷ N)，**\z\≤ 3**
                權重為 0 的區間次數必須為 0（超限保留最後結果的情況除外，數量須 ≤ Retry 超限次數）
                最高／最低有次數的區間與權重表的最高／最低有權重區間相同（樣本太少時最高區間可能沒抽到）
                觸發轉 BG 得分不得超過 Config free_game 卡的 max（BG Trigger Cap）
                區間平均倍數與 Avg_Multi 工作表相近；差異大時代表區間內條件分布不同

                N 為該欄的總樣本數（BG 用 TotalSpin，FG 用總場數）。Simulator 的 volatility_std 以 Normal Bet 基準成本計，換成 RTP 的 σ 時必須除以模式倍數（EB ÷2、BF ÷100），漏除會讓 EB／BF 的 σ 被高估、偏差看起來比實際小。單一報表 64 格同時檢定，偶有一兩格 |z| 落在 3 附近屬正常；多格同向偏離才是問題。

                天花板說明

                本文件屬於 專案需知/ 專案需知文件集，總覽、共通原則與完成條件見 _README.md。

                天花板是系統對派彩金額設的上限。超過上限的結果整把重骰：重骰後該結果不會出現，不是把派彩截到上限。數學模型、Config、Simulator 與 Demogame 必須實作同一套天花板。

                1. 金額上限

                範圍押注 <= $1,500押注 > $1,500超過時
                單把 BG 派彩$500,000$1,000,000整把重骰
                單場 FG 派彩$2,000,000$5,000,000整把重骰
                系統賠付上限（單把總派彩）$10,000,000$10,000,000整把重骰
                • 押注 $1,500 屬於低的那一級；只有大於 $1,500 才適用 $1,000,000／$5,000,000。
                • 押注金額的判定方式與數學模型規範.md第 1.4.3 節相同：NB／EB 用實際押注金額，BF／SF 用購買價格反推的基礎押注。
                • 系統賠付上限對所有押注一律 $10,000,000，是 BG、FG 上限之外的最後一道保護。

                2. 對倍率上限的影響

                每個押注層級的倍率上限必須讓該層最大押注踩不到天花板，否則高注玩家會實際觸發重骰、RTP 系統性偏低：

                BG 倍率上限 × 該層最大押注 ≤ BG 上限
FG 倍率上限 × 該層最大押注 ≤ FG 上限
                遊戲最大押注BG 倍率上限FG 倍率上限
                $1,000500x2000x
                $1,500333x1333x
                $5,000（例：H026）200x1000x
                • 配權重時以各卡片區間的上限驗算：區間上限 × 該層最大押注超過天花板的區間，不得配權重。
                • 計算結果比數學模型規範.md第 1.4.4 節的預設上限低時，以天花板推得的值為準，並記錄於數學文件。
                • 押注跨越 $1,500 的遊戲，<= $1,500 與 > $1,500 要分開驗算。

                3. 實作與驗證

                • Simulator 與 Demogame 必須實作相同的重骰，否則模擬結果與實際遊戲不一致。
                • 卡片系統的觸發局 BG 上限（數學模型規範.md第 2.3 節的天花板機制）是另一道限制，兩者同時成立。
                • 模擬報表要能看出重骰次數；重骰比例明顯不為 0 時，先檢查倍率上限與區間權重是否違反第 2 節。

                4. 檢查清單

                • ☐ 各押注層級的 BG／FG 倍率上限已依第 2 節驗算並記錄於數學文件。
                • ☐ 超過天花板的卡片區間權重為 0。
                • ☐ Simulator 與 Demogame 已實作 BG、FG 與系統賠付上限的重骰。
                • ☐ 正式模擬的重骰次數為 0 或已說明原因。

                1. 新手體驗（D 版）

                1.1 目的

                1.3 規則

                • 設定得分取代判定回合的原始得分，不是額外加上；原始得分高於設定得分時，總得分可能反而降低。
                • 第二次判定使用已套用第一次的結果：第一次的判定回合若被改寫，會計入第二次判定的 RTP。
                • 新手期只做新手體驗，不做老手救援；新手體驗 RTP 預算為 2%。

                1.4 押注與演出（待確認）

                以下為建議做法，定案前需與企劃、前後端確認：

                • 不同押注：RTP 以實際得分 ÷ 實際押注計算；設定得分以判定回合的 Total Bet 計價。
                • Extra Bet：以含加押的實際 Total Bet 計算 RTP 與設定得分。
                • Buy Feature：BF 局不計入 RTP 統計範圍；判定回合落在 BF 局時順延到下一個非 BF 局。
                • 異常加押：設定得分以 min(判定回合押注, 新手期押注中位數) 計價，避免在可預期的判定區間突然加押套利。
                • 演出對應：Card System 重骰出一個總得分等於設定得分的完整結果；結果含 FG、Scatter Pay 或 Mini Game 時以整包總得分計算。
                • Jackpot Game：判定回合不得觸發 Jackpot Game（互斥）。

                2. 老手救援

                本節為中辦的做法；北辦另有一套做法（未納入本文件）。兩辦的救援池、累積數值與統計全部分開計算。

                基礎配置 92% ＋ 救援預算 5% ＝ 總 RTP 97%

                2.1 前情提要

                • 好體驗只有隔天會記得，救援必須當天發生才有留存效果。
                • 當日未開出 50× 以上大獎的老手，隔日流失率明顯上升；決定留存的是當天有沒有一次夠大的體驗，不是輸贏總額。
                • 當日遊玩超過 500 轉的玩家，隔日留存都在 60% 以上，留存效益最高的救援區段在前 400 轉。
                • 玩到 401 轉以上的玩家隔日留存約 60%，隔天基本上會回來玩；我們的遊戲太平，這段玩家需要的是記憶點。
                • SPS 最小監測單位為 40 轉，最快每 40 轉判定並救援一次。

                2.2 機制目標

                • 短期體驗不好就救：以當日的短期體驗為判斷基準，體驗不好當天就出手，不等長期統計。
                • 補上缺席的大倍數體驗：好體驗定義為當日最大單局倍數。玩得夠久卻沒碰到大倍數的玩家，在流失發生前的當天由系統給出該倍數，演出與自然大獎無法區分。
                • 製造記憶點（延伸救援）：401 轉後的玩家留存已不是問題，用偶發的 500× 加深對遊戲的印象；體驗真的很差時仍會出手。

                2.3 機制介紹／數值設定

                2.3.1 運作方式

                • 以天為循環：每天台灣時間 04:00 刷新，當日轉數、當日 RTP 與救援池餘額全部歸零重計。
                • 主救援（當日 40～400 轉）：每 40 轉一個觸發區間（觸發點前後 5 轉，例如 35～45、75～85 轉），每人每天在區間內隨機挑一轉判定，須同時符合：
                  • 條件 1：前 40 轉 RTP < 50%
                  • 條件 2：當日累積 RTP 低於該觸發點門檻
                • 延伸救援（當日 440～1,000 轉，進行中）：自第 440 轉起每滿 40 轉判定（固定轉數），須同時符合：
                  • 條件 1：往前抓 200 轉 RTP < 50%
                  • 條件 2：前 40 轉 RTP < 40%
                • 判定回合本身不納入統計；當日不到 35 轉不判定，超過 1,000 轉停止判定。
                • 命中時由 Card System 重骰產生救援倍數的結果；該轉最終得分取「自然得分」與「救援倍數 × Bet」較高者，成本以增量記帳：救援成本 = 救援後最終得分 − 該轉自然得分。
                • 每一筆救援發放前都要通過救援池檢查（第 2.3.3 節）。
                • 救援得分計入當日累積 RTP，被救過的玩家通常自然脫離觸發區；判定轉在區間內隨機，玩家無法預測、也無法從畫面判斷是否為救援。

                每次 Spin 後提撥投注額的 1% 進救援池。這筆提撥同時記入兩本帳，是同一筆錢的兩種檢視角度，不是各自獨立的兩筆提撥：

                提撥額 = 該轉 Total Bet × 1%

共同池餘額 = Σ 全平台提撥 − Σ 全平台已發救援成本
個人池餘額 = Σ 該玩家提撥 − Σ 該玩家已領救援成本
                池守什麼沒錢時

                個人池單一玩家不長期超領改用嚴格標準複判；通過仍可救援（透支）

                B.3.7 判定順序

                到達判定回合時，依下列順序處理：

                1. 先依 3.3.8 決定預定獎項及本次完整救援成本。
                2. 共同池檢查：餘額不足 → 直接取消救援；餘額足夠 → 進入個人池檢查。共同池關閉時跳過此步。
                3. 個人池檢查：
                  • 個人池足夠 → 使用 3.3.5 的一般短期／中期／長期門檻判定。
                  • 個人池不足 → 改用 3.3.9 的嚴格門檻判定。
                4. 所套用的門檻通過 → 發放救援並依 3.3.10 記帳；未通過 → 不救援。

                B.3.10 成本記帳

                救援成本 = 救援流程產生的該轉完整最終得分
                • 救援成功時，共同池與個人池均按完整救援結果扣款；自然結果不抵銷救援成本。
                • 成本以救援流程實際產生的最終得分計算（含 Scatter Pay），不得使用卡片目標倍數，否則會低估支出。
                • 報表的「倍率差」僅供比較有／無機制結果，公式為 救援結果 − 自然結果；若自然結果較高，此欄可為負數，但不影響救援成本記帳。
                • 正式系統依實際投注事件時間順序更新共同池；模擬器依轉數推進所有玩家時，同一轉內使用固定亂數種子打散玩家順序，避免共同池結果偏向較小的玩家編號。

                B.3.11 異常加押檢查

                判定救援前須往前檢查玩家的歷史押注，辨識玩家是否在可能取得救援前異常提高押注。

                需要進一步定義：

                • 往前檢查的押注轉數。
                • 使用平均押注、中位數或其他數值作為基準。
                • 當下押注高於歷史基準多少時，視為異常加押並取消救援。

                B.3.12 玩家取得救援後的行為

                記錄玩家取得救援後是否立即停止遊玩，作為機制效果及套利風險的觀察指標。目前不直接將「拿到救援後不玩」判定為套利。

                B.3.13 RTP 驗證與待確認事項

                模擬時必須同時驗證：

                • 老手期總 RTP 收斂於 97%（96% 基礎 + 1% 救援）。
                • 共同池餘額不得為負。
                • 被共同池、個人池與嚴格標準分別擋下的次數須分別統計。
                • 透支比例與 50×／20× 發放占比列入報表。

                待確認事項：

                • 個人池初始額度：1% 提撥約需 2,000 轉攢滿 20×、5,000 轉攢滿 50×，前期救援幾乎都走透支路徑；候選方案為進老手期贈送初始額度（例如 50 × Bet）或維持 0，先模擬透支比例再定案。
                • 「當日體驗 50×」的定義：「當日」的日切基準（平台時區日曆日或 session）、是否含 BF／SF 局、是否含救援產生的結果、以單局整包（含 FG）或單次事件計。
                • 共同池的範圍（建議每款遊戲各一池）與時間範圍（建議滾動窗口）。
                • BF／SF 是否提撥與計入判定窗口（建議不提撥、不計入）。
