## 4. 處理過的故障（2026-09-21）

**症狀**：VM 上的 bot 完全收不到訊息。

**診斷過程**：
1. `getMe` 正常 → token 有效，bot 帳號（@walking_encyclopedia_bot「打雜小弟」）存在。
2. `getWebhookInfo` 發現被設了 webhook：`https://tele.goldenherd.com/tg/webhook/8817922272`（Cloudflare IP 172.67.196.78），且 webhook 當天仍在收訊（最後錯誤 502）。
3. Telegram 規則：設了 webhook 後 `getUpdates` 一律回 **409 Conflict** → polling 版 bot 整個被斷線。實測確為 409。

**處置**：呼叫 `deleteWebhook?drop_pending_updates=true` 移除 webhook，驗證 `getUpdates` 恢復正常。polling 即恢復（python-telegram-bot 遇 Conflict 會自動重試，必要時重啟程序）。

**根因疑慮（未結案）**：`tele.goldenherd.com` 來歷不明，若非自家所設，代表 **token 已外洩**（token 明碼在程式裡）。對方可隨時再設回 webhook、故障會復發。當時建議：
1. 去 @BotFather 對此 bot **Revoke current token** 換新。
2. Token 改從環境變數讀，不要明碼。

**本 session 不知道使用者後來是否已換 token。** 若又出現「突然收不到訊息」，第一步先查 `getWebhookInfo`。

## 5. 踩雷與使用者偏好

- 回報問題時使用者通常只要「先恢復能用」，治本方案（換 token）提出讓他自己決定，不要擅自 revoke（會讓 VM 上跑的舊 token 立即失效）。
- 診斷 Telegram 側不用登 VM：`getMe` → `getWebhookInfo` → `getUpdates`（409=有 webhook 或另一實例在輪詢）三步就能定位。
- 程式有 port 48726 實例鎖：若在 VM 上手動再起一份，會因鎖而退出（或若鎖機制失效，雙實例互搶 getUpdates 也會 409）。
- 機密值（token、管理者 ID）一律不要寫進文件／訊息，只指到程式行號。
