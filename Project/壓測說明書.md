這份文件回答兩個問題：**要壓什麼**，以及**壓出來的數字怎麼判**。

設定來源為 [Slot 開發注意事項](./Slots/slot_development_specification.md) 第 1.4 節與
[iGaming 機制說明書](./System/iGaming%20機制說明書.md)；本文件不重複定義設定本身。

目前採用的機制版本：**新手體驗 D 版**、**老手救援 B 版**。

壓測與其他驗證工具的分工：

| 工具 | 產出 | 驗證對象 |
|---|---|---|
| 數學模型 XLSX | 理論 RTP、倍率權重 | 模型本身的理論值 |
| Simulator | 單一 Config／Bet Mode／Profile 的大場次報表 | 單一組合的 Game RTP、Feature 觸發率、Card System |
| **壓測** | 固定玩家數 × 固定把數的後端報表 | **玩家實際歷程下的 RTP**，含新老手切換與機制介入 |
| `System/simulator_system.py` | 多分頁玩家模擬報表 | 機制本身的觸發率、Pool 上限、RTP 增量 |

關鍵差異：Simulator 每批固定一個 Profile，壓測則是**同一位玩家從第 1 轉跑到第 N 轉**，中途由新手期切到老手期，並且會被新手體驗與老手救援介入。

# 要壓什麼？（必跑組合）

## 壓測規模與把數

壓測以「玩家數 × 每位玩家把數」定義。範例：20,000 位玩家 × 每人 500 把 = 10,000,000 spins。

每人把數決定機制能不能驗到：

| 機制 | 生效轉數 | 需要的最少把數 |
|---|---|---:|
| 新手體驗 D 第一次判定 | 第 50 轉 | 50 |
| 新手體驗 D 第二次判定 | 第 150 轉 | 150 |
| 老手救援 B 起始 | 第 301 轉（新手期 200 ＋ 計算基底 100） | 301 |
| 老手救援 B 第 1 個完整返還區間 | 301～450 | **450** |
| 老手救援 B 第 2 個完整返還區間 | 451～600 | **600** |

**建議每人 600 把以上**，讓老手救援 B 至少有 2 個完整返還區間。500 把只有 1 個完整區間，救援樣本偏少。

## 押注分級與換算

```text
實際押注 = Coin in × currency denom
```

`currency denom` 直接寫在報表檔頭，不必另外查。目前平台值為 `0.002000`，即 `實際押注 = Coin in ÷ 500`。

| 分級 | 判定依據 | Game RTP 版本 | 可拉 Link | 上限倍數 |
|---|---|---|:---:|---|
| 小 Bet | `< $2` | 94 版 | ✗ | 依數學文件「倍率線型」 |
| 中 Bet | `$2 ~ $100` | 92 版 | ✓ | 依數學文件「倍率線型」 |
| 大 Bet | `> $100`（預設，各遊戲可不同） | 92 版 | ✓ | 2000x（預設，各遊戲可不同） |

- 一般模式（NB／EX1／EX2）用**實際押注**分級，界線固定 `$2` 與 `$100`。
- BF／SF 用**基礎面額**分級，界線放大為 `倍率 × $2` 與 `倍率 × $100`（等價於用面額判 `$2`／`$100`）。
  Buy Feature 的高價不會讓玩家升級到更高的 Bet 分級。

## 測項產生規則

先取得該遊戲支援的押注模式（`NB`／`EX1`／`EX2`／`BF`／`SF`）與各模式的押注倍率。不支援的模式整組跳過。

每個支援的模式產生「小／中／大押注 × 新手／老手」共六格測項，再套三條排除規則：

| 排除規則 | 適用 | 原因 |
|---|---|---|
| 倍率 `≥ 2` 時不產生**小押注** | NB／EX1／EX2 | Extra Bet 最低成本已是 $2，不可能落在小 Bet |
| 倍率 `> 100` 時不產生**中押注** | NB／EX1／EX2 | 最低成本已超過中 Bet 上界 |
| **大押注不產生新手** | NB／EX1／EX2 | 大 Bet 玩家不會是新手 |

BF／SF 不套用上述排除，六格全跑。

|---:|---|---|---|---|---:|

| 2 | NB | 小押注 | 老手 | `x < 2` | 94% |

| 4 | NB | 中押注 | 老手 | `2 ≤ x ≤ 100` | 92% |
| 5 | NB | 大押注 | 老手 | `100 < x` | 92% |
| 6 | EX1 | 中押注 | 新手 | `2 ≤ x ≤ 100` | 93% |
| 7 | EX1 | 中押注 | 老手 | `2 ≤ x ≤ 100` | 92% |
| 8 | EX1 | 大押注 | 老手 | `100 < x` | 92% |
| 9 | BF | 小押注 | 新手 | `x < 150` | 92.5% |
| 10 | BF | 小押注 | 老手 | `x < 150` | 92.5% |
| 11 | BF | 中押注 | 新手 | `150 ≤ x ≤ 7500` | 92.5% |

## Coin in 撞號要注意

`Coin in` 唯一決定實際押注，因此唯一決定 Bet 分級 — 但**分不出 Bet Mode**。H026 的 20 檔面額 × 3 模式共 60 組，其中 16 個 `Coin in` 值對應到多種組合：

| 情況 | 數量 | 影響 |
|---|---:|---|
| Buy Feature 與 Normal／Extra 同號 | 5 | **目標 RTP 不同**（92.5% vs 92%），會判錯目標 |
| Normal 與 Extra 同號 | 11 | 目標相同，但 BG／FG 結構差異大（0.32/0.60 vs 0.68/0.24） |

目標衝突的 5 個：`Coin in` 150,000／300,000／600,000／750,000／1,500,000。

判定時必須以報表檔頭的 `extraBet`（BetType）為準，不可只看 `Coin in`。

# 壓測標準

## 報表怎麼看

### Formal RTP Report

壓測的判定對象是 `Formal RTP Report`（TG 上傳 txt 或含 txt 的 zip／rar）。結構：

```text
Formal RTP Report
Report ID: <報表編號>
Generated At: <產生時間>
- machineType = <Game ID>
- extraBet = <BetType>
- Bet = <實際押注>
- OldHand Init = <enabled | disabled>

Scenario RTP
整體 RTP
- Game RTP = xx.xx%
- Jackpot RTP = xx.xx%
- Bonus Game RTP = xx.xx%
前 50 次 Spin ...
前 200 次 Spin ...
RTP <=200 ...
RTP >200 以後 ...

SettingID RTP
SettingID 1 xxx（一般）
- Game RTP = xx.xx%
- Jackpot RTP = xx.xx%
- Bonus Game RTP = xx.xx%
SettingID 2 xxx（新手體驗 D）
...

SettingID Trigger Count
...
```

### Scenario RTP：五個時間切片

| 顯示欄 | 來源標籤 | 涵蓋範圍 | 是否判定 |
|---|---|---|---|
| 整體 | `整體 RTP` | 全部 spin | 只判 `0 ≤ x < 100%` |
| ~50 | `前 50 次 Spin` | 每位玩家第 1～50 轉 | 只判 `0 ≤ x < 100%` |
| ~200 | `前 200 次 Spin`（或 `前 100 次 Spin`） | 每位玩家第 1～200 轉 | 只判 `0 ≤ x < 100%` |
| **OG ~200** | `RTP <=200`（或 `<=100`） | **新手期**（≤200 轉） | **依目標值判定** |
| **OG 200~** | `RTP >200 以後` | **老手期**（>200 轉） | **依目標值判定** |

前三欄是觀察用，只確認沒有爆掉。真正的目標值判定只做後兩欄。

因為報表本身已經把新手期與老手期分開，**逐欄各判自己的目標值，不需要做加權平均**。

每一欄都有三個 RTP：`Game RTP`、`Jackpot RTP`（＝Link）、`Bonus Game RTP`（＝Bonus）。

### SettingID RTP：機制拆分

各機制的 RTP 貢獻由 SettingID 分開列出：

| SettingID | 名稱 | 歸屬 |
|---|---|---|
| 1 | 一般（沒有機制） | 自然結果基準 |
| 2, 4, 5, 6, 7, 8 | 新手救援、新手體驗 D（新手體驗 FG）、新手 mini game 體驗 D（新手體驗 JP）等 | **新手體驗**，取 Game RTP **加總** |
| 3 | 老手救援 | **老手救援**，取 Game RTP |

### 新老手模式的區分

`OldHand Init` 決定這次壓測玩家的起始身分：

| `OldHand Init` | 模式 | 玩家歷程 | OG ~200 欄的目標 |
|---|---|---|---|
| `disabled` | **新手** | 從第 1 轉開始，≤200 轉是新手期 | 新手目標（93%） |
| `enabled` | **老手** | 玩家一開始就是老手 | 老手目標（92% 或 94%） |

若 `OldHand Init` 欄位缺漏，退而用「Jackpot RTP 是否 > 0」推斷（老手才會有 Link 收入）。這是備援，不是正規判斷依據。

### 統計資料要去哪裡拿

同一次雲端執行還會產出 **RTP Validator** 的逐分支 txt（每個 `Coin in` × `WTIdx` 一個資料夾）。它不是判定的主報表，但提供了統計判定需要的關鍵資料：

| 欄位 | 用途 |
|---|---|
| `pool[n] hit = N, ttlWin = X, avg = Y, rtp = Z` | 各彩金獎級的**命中次數**，用來算 Link／Bonus 的標準誤 |
| `TotalSpin`、`TotalBet`、`currency denom` | 樣本量與押注換算 |
| `log_*.txt` 的 `std` | 波動度 σ，用來算 Game RTP 的標準誤 |

`pool[n] rtp` 的分母是**基準押注**（`default_coin_in`，H026 為 100），不是該次的實際 `Coin in`。所以同一個 pool 的 rtp 在不同押注下應該一致，這本身就是一項檢查。

## 目標值

### Game RTP

| 模式 | 押注 | OG ~200（新手期） | OG 200~（老手期） |
|---|---|---:|---:|
| 新手（`OldHand Init = disabled`） | 低押注 `< $2` | 93% | 94% |
| 新手 | 高押注 `≥ $2` | 93% | 92% |
| 老手（`OldHand Init = enabled`） | 低押注 | 94% | 94% |
| 老手 | 高押注 | 92% | 92% |
| Buy／Super Feature | 全部 | 92.5% | 92.5% |

低／高押注的判定依據：一般模式看 `Bet` 本身；BF／SF 看 `Bet ÷ 模式倍率`。

### Link 與 Bonus

| 模式 | 押注 | Link OG ~200 | Link OG 200~ | Bonus 兩欄 |
|---|---|---:|---:|---:|
| 新手 | 低押注 | 0% | 0% | 2% |
| 新手 | 高押注 | 0% | 2% | 2% |
| 老手 | 低押注 | 0% | 0% | 2% |
| 老手 | 高押注 | 2% | 2% | 2% |
| Buy／Super Feature（低押注） | — | 0% | 0% | 4% |
| Buy／Super Feature（高押注） | — | 老手 2%／新手 0% | 2% | 老手 2%／新手 4% |

**Link 目標為 0% 時必須精確等於 0%**，不套用任何容許範圍 — 這是規則問題不是精度問題（小 Bet 不能拉 Link、新手期不能拉 Link）。

### 機制目標

| 項目 | 來源 | 目標 | 判定欄 |
|---|---|---:|---|
| 新手體驗 | SettingID 2, 4, 5, 6, 7, 8 的 Game RTP 加總 | 1% | OG ~200 |
| 老手救援 | SettingID 3 的 Game RTP | 1% | OG 200~ |

容許範圍 0%～2%。這是**產品設定的容許區間**，不是統計容差，直接用區間判定，不套信賴區間那一套。

> 注意：老手救援 B 版的返還公式為 `(0.95 − Total Win / Total Bet) × Total Bet`
> （機制說明書 3.2.4），是補到 RTP 95%，而觸發門檻只要 `RTP < 50%`。
> 機制說明書 3.2.9 已標註「返還目標寫 55% 但公式是 95%，兩者不一致」。
> 因此 1% 這個目標在 B 版下是否成立需要實測確認，見〈待確認事項〉。

## 為什麼不用固定容差

固定容差（例如「一律 ±1.0pp」）在不同格子的鬆緊差距非常大。以 H026 實測為例：

| 項目 | 固定容差 | 相當於幾個標準誤 |
|---|---|---|
| Game | ±1.0pp | 3.4 ～ 7.0 |
| Bonus | ±0.5pp | 22 ～ 31 |
| Link（低押注） | ±1.5pp | 4.1 |
| Link（高押注） | ±1.5pp | **155** |

同一條 ±1.5pp，在低押注勉強合理，在高押注鬆到任何錯誤都會通過。Bonus 的 ±0.5pp 等於完全不檢查。

反過來說，Game 的 ±1.0pp 太寬也有代價：**0.6pp 的真實偏差會被判通過**。實例就在 H026 2026-08-21 那批 — `NoExtraBet`、`Coin in = 500`（面額 $1，小 Bet）的老手那次，Game RTP = 93.4111%，若目標是老手低押注 94%，差 −0.59pp，約 2.3 ～ 4.1 個標準誤，統計上顯著，但固定容差判它通過。

## 判定方法：95% 信賴區間

```text
標準誤   SE = σ / √N
判定     |實測 − 目標| ≤ 1.96 × SE  →  通過
```

等價說法：**目標值落在實測值的 95% 信賴區間內就算通過**。

這不是新發明的方法 — 系統輸出的 `log_*.txt` 已經在算這件事：

```text
5_0.0_0_rtp_0.9458_std_4.517_minRtp_0.943_maxRtp_0.9486_totalRtp_0.95_FALSE
```

其中 `minRtp` / `maxRtp` 就是 `rtp ± 1.96 × std / √N`：

```text
0.9458 − 1.96 × 4.517 / √10,000,000 = 0.94300  → 檔案 minRtp = 0.9430 ✓
0.9458 + 1.96 × 4.517 / √10,000,000 = 0.94860  → 檔案 maxRtp = 0.9486 ✓
```

行尾的 `FALSE` 即「目標 `totalRtp` 不在此區間內」。

## σ 從哪裡來

依下列優先序取得，並在報告中註明用了哪一個：

| 優先 | 來源 | 說明 |
|---:|---|---|
| 1 | 報表／`log_*.txt` 的 `std` | 該次執行自己算出來的波動度，最準確 |
| 2 | 同遊戲 Simulator 報表的 `volatility_std` | 需取相同 Config／Bet Mode／Profile 的那一批 |
| 3 | 同一格重複 k 次執行的樣本標準差 | `k ≥ 3` 才可用；k 次的差異直接反映真實雜訊 |

σ 會隨 Profile 與押注變化，不可跨格套用。H026 實測 σ 範圍 4.5 ～ 9.3（同一個 betMultiplier 的新手與老手就差到 1.8 倍）。

## Link 與 Bonus 用命中次數算

彩金是低頻高額事件，用 σ 不合適，改用 Poisson：

```text
單一 pool：  相對誤差 = 1 / √hit
             SE_pool  = rtp_pool / √hit

合成      ：  SE_Link  = √( SE_pool[1]² + SE_pool[2]² )
             SE_Bonus = √( SE_pool[3]² + SE_pool[4]² )
```

`hit` 取自 RTP Validator txt 的 `pool[n] hit`。

兩個限制要知道：

- `hit = 0` 時無法估計 SE。此時只能判「目標是否也為 0%」；若目標非 0% 而命中 0 次，屬**樣本不足**（不是失敗），須累積更多次執行。
- 累進式彩金（`pool[1]`、`pool[2]`）的獎額本身會變動，上式只算了「中幾次」的誤差、沒算「中多少」的誤差，所以是**下界**。若已知獎額的變異係數 `CV`，改用 `SE_pool = rtp_pool × √(1 + CV²) / √hit`。

## 三級判定

| 差異 | 判定 | 意義 |
|---|---|---|
| `≤ 1.96 SE` | ✅ 通過 | 目標在 95% 信賴區間內 |
| `1.96 ~ 3 SE` | ⚠️ 警示 | 需補跑或提出說明 |
| `> 3 SE` | ❌ 異常 | 純雜訊造成的機率 < 0.3%，幾乎確定是設定問題 |

報告中一律寫成「差 X.X 個標準誤」，不要只寫 pp — 前者才能判斷嚴重程度。

## 累積多次壓測

同一格執行 k 次後取平均，標準誤縮小 `√k` 倍：

```text
SE_k = SE / √k
```

| k | SE 縮小倍數 | 可偵測的最小偏差（以 SE = 0.25pp 為例） |
|---:|---:|---:|
| 1 | 1.00 | 0.49pp |
| 2 | 1.41 | 0.35pp |
| 4 | 2.00 | 0.25pp |
| 9 | 3.00 | 0.16pp |

這是**留下壓測成功紀錄的統計理由**：紀錄不只是備查，累積起來可以把偵測能力提高。低押注的 Link（單次 SE 約 0.36pp）尤其需要靠累積才驗得動。

## 判定流程

**Step 1 前置檢查**

- [ ] `machineType` 對應到要驗的遊戲。
- [ ] `extraBet`（BetType）、`Bet`、`OldHand Init` 三個欄位都有值。
- [ ] 已依 `Bet` 與模式倍率判出低／高押注。
- [ ] 已取得該格的 σ 與各 pool 的 `hit`。
- [ ] 已知 `N`（該欄涵蓋的 spin 數）。

任一項缺漏 → 判「資料不足」，不得出通過或失敗。

**Step 2 對應測項**

由 `extraBet` → 模式，`Bet` → 級距，`OldHand Init` → 新老手，定位到〈要壓什麼？〉的測項。

**Step 3 前三欄合理性**

`整體`／`~50`／`~200` 三欄的 Game RTP 必須落在 `0 ≤ x < 100%`。超出即異常，不必再往下判。

**Step 4 目標值判定**

對 `OG ~200` 與 `OG 200~` 兩欄，逐項套 95% 信賴區間：

| 項目 | 目標 | SE 來源 |
|---|---|---|
| Game | 〈目標值〉的 Game RTP 表 | σ / √N |
| Link | 〈目標值〉的 Link 表 | pool[1]、pool[2] 的 hit |
| Bonus | 〈目標值〉的 Bonus 表 | pool[3]、pool[4] 的 hit |

Link 目標為 0% 的格子例外：直接要求精確為 0%。

**Step 5 機制判定**

新手體驗（SettingID 加總）與老手救援（SettingID 3）是否落在 0%～2%。

**Step 6 硬檢查**

見〈硬檢查〉。任一項不符即整份失敗，不受統計容差保護。

**Step 7 結論**

- 全部通過 → 該測項標記為壓測成功，記錄 `Report ID`、時間、σ 來源、k 值。
- 有警示 → 補跑後合併判定。
- 有異常或硬檢查失敗 → 失敗，附上差幾個 SE 與可能原因。

## 硬檢查

不涉及統計容差，不符合就是錯：

| 檢查項 | 條件 |
|---|---|
| 小 Bet 不可拉 Link | 小 Bet 所有欄的 `Jackpot RTP` 必須為 0，且 `pool[1]`、`pool[2]` 的 hit 必須為 0 |
| 新手期不可拉 Link | 新手模式的 `OG ~200` 欄 `Jackpot RTP` 必須為 0 |
| 前三欄範圍 | `整體`／`~50`／`~200` 的 Game RTP 必須 `0 ≤ x < 100%` |
| RTP 拆解 | `Game RTP + Jackpot RTP + Bonus Game RTP` 須等於總 RTP（浮點誤差內） |
| 上限倍數 | 各分級的實際開出最大倍數不得超過該分級上限；大 Bet 預設 2000x |
| BG Trigger Cap | BG 進 FG 的最大倍數不得超過同 Profile 的 BG Trigger Cap |
| Scatter Pay | 遊戲無 Scatter Pay 時對應欄位必須為 0 |
| `pool[n] rtp` 一致性 | 同一個 pool 的 rtp 在不同 `Coin in` 下應一致（分母是基準押注，與實際押注無關） |
| Bet Mode 對應 | 判定用的目標必須依 `extraBet` 決定，不可只看 `Coin in` |

## 常見異常與處置

| 現象 | 可能原因 | 處置 |
|---|---|---|
| Game 差 2 ～ 3 SE | 邊界情形 | 補跑到 k = 4 再判；合併後 SE 減半 |
| Game 差 > 3 SE 且各押注同方向 | 設定或口徑錯誤 | 追查 Config 家族、Profile、押注分級是否套錯 |
| Game 差 > 3 SE 但只有一格 | 該格設定單獨出錯 | 檢查該 `Coin in` 的 WTIdx／Config 對應 |
| Link = 0% 但目標 2% 且 `hit = 0` | 樣本不足，不是失敗 | 累積更多次執行；或改用理論觸發率驗算 |
| Link = 0% 但目標 2% 且 `hit > 0` | 獎額或權重設定錯 | 追查彩金設定 |
| Link > 0% 但目標 0% | Bet 分級或 Link 資格設定錯 | **硬性錯誤**，直接退回 |
| Bonus 偏差 > 3 SE | Bonus 精度很高，偏差幾乎一定是真的 | 追查 `pool[3]`／`pool[4]` 權重與獎額 |
| `pool[n] rtp` 隨 `Coin in` 變動 | 彩金分母口徑錯 | 追查後端 rtp 計算 |
| 缺某個測項 | 該組合未納入本批壓測 | 列入待跑，不得視為通過 |
| `OldHand Init` 缺漏 | 報表欄位不全 | 用 Link > 0 推斷並在報告註明，或要求重出報表 |
