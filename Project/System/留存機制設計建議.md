# 留存機制設計建議

## 1. 文件說明

本文件針對「跨多款遊戲、在總體 RTP 精準可控的前提下，降低玩家在痛苦階段流失」的需求，提出建議架構。

- 對照對象：現行新手體驗 D 版與老手救援 C 版（見 [玩家遊戲歷程](./玩家遊戲歷程.md)）。
- 本文件為設計建議，不是已定案規格。定案前需完成第 8 節的模擬驗證。

### 1.1 需求前提

| 項目 | 需求 |
|---|---|
| 總體 RTP | 每款遊戲 `97.0%` |
| 配置方式 | 新老手時期的 Config RTP 配得較低，剩餘空間留給機制 |
| 適用範圍 | 多款遊戲，遊戲調性差異可能很大 |
| 目標 | 讓處於痛苦階段的玩家被機制作用，降低流失風險 |
| 反套利 | 針對每一種情況做不同檢查，不容許任何玩家透過特殊手段套利 |
| 公平 | 所有玩家公平地玩同一款遊戲 |

### 1.2 需要先定義的口徑

「總體 RTP 97%」有多種可能解讀，本文件採用下列定義，若與實際需求不同，第 3 節的預算拆解需重算：

```text
每款遊戲、每個押注層級，對該層級全體玩家、全生命週期：
Σ 實際 Total Win ÷ Σ 實際 Total Bet = 97.0% ± 0.1%
```

- 分母使用玩家實際扣款金額，含 Extra Bet 加價與 Feature 購買價。
- Link、Bonus Game、Game、新手機制、老手機制的派彩全部計入分子，不重複計算。
- 現行規範的 Total RTP 為 NB／EB `96%`、BF／SF `96.5%`；提升到 `97%` 分別多出 `1.0` 與 `0.5` 個百分點的空間，本文件的預算拆解以此為基礎。

## 2. 現行架構的三個結構性問題

建議的每一項都是為了解掉下列問題，先列出來以便對照。

### 2.1 成本由觸發條件決定，RTP 只能事後補救

現行流程是：條件命中 → 決定獎項 → 估算發出後平台 RTP → 超過 `97%` 就取消。這是一個「先花錢、再看超不超支」的結構，後果有三：

- 機制成本無法事前得知，基礎 Config 要留多少空間只能靠模擬反覆試。
- 平台 RTP 是全體共用的單一數字，一位大 Bet 玩家的自然大獎會直接擠掉一批小 Bet 玩家的救援。
- 護欄一旦頂到，救援整批取消——同樣痛苦程度的玩家，因為排在後面就拿不到。這與「公平」的目標直接衝突。

### 2.2 痛苦門檻寫死絕對數字，跨遊戲不可移植

短期 RTP `< 40%`、中期 `< 60%／50%／40%` 這類門檻，在不同調性的遊戲上行為完全不同：

- 低波動遊戲（Hit Rate 高、FG 常見小倍數）：50 轉窗口 RTP 很少掉到 40% 以下，機制幾乎不作用。
- 高波動遊戲（FG 週期長、單次倍數大）：50 轉窗口 RTP 低於 40% 是常態，機制天天觸發，預算立刻爆掉。

同一組數字不可能同時適用兩者。門檻必須相對於各遊戲自身的分布來定義。

### 2.3 判定回合可預測，且防套利只有單一 binary gate

- D 版固定在第 50、150 轉判定。這是可觀察、可複製、必然會被玩家社群發現的規律。
- C 版每 50 轉週期的前 40 轉隨機 1 次，比 D 版好，但「後 10 轉固定不判定」等於公告了安全區。
- 目前唯一的防套利是「當下押注高於歷史平均就取消」。這擋得住一次性暴力加押，擋不住緩步爬升押注、也擋不住低押注養資格再換層級領取。

## 3. 建議架構：預算驅動的救援帳（Rescue Ledger）

### 3.1 核心轉向

把「條件驅動」改成「預算驅動」：

```text
現行：痛苦命中 → 發多少算多少 → 平台 RTP 超標就取消
建議：每一元投注都產生固定比例的救援預算 → 痛苦決定何時提領、提領多少
```

機制的總成本不再是估算值，而是**恆等於玩家自己投注所產生的預算**。RTP 從「需要控制的變數」變成「定義上成立的等式」。

### 3.2 預算拆解

以 NB／EB 為例（BF／SF 見第 3.7 節）：

| 分項 | 建議值 | 說明 |
|---|---:|---|
| Base Game RTP | `92.5%` | Config 實配的自然結果，含 BG／FG／Jackpot |
| Link | `2.0%` | 中／大 Bet；小 Bet 為 `0%` |
| 新手預算 `r_n` | `0.5%` | 只在新手期提領 |
| 老手救援預算 `r_r` | `2.0%` | 老手期提領 |
| **Total** | **`97.0%`** | |

小 Bet 沒有 Link 的 `2.0%`，建議將該空間**併入救援預算而非 Base Game RTP**：

| 押注層級 | Base Game | Link | 新手 | 救援 | Total |
|---|---:|---:|---:|---:|---:|
| 小 Bet | `92.5%` | `0.0%` | `0.5%` | `4.0%` | `97.0%` |
| 中 Bet | `92.5%` | `2.0%` | `0.5%` | `2.0%` | `97.0%` |
| 大 Bet | `92.5%` | `2.0%` | `0.5%` | `2.0%` | `97.0%` |

理由：小 Bet 以新手與低消費玩家為主，正是最容易流失的族群，那 2 個百分點用在留存上的邊際效益高於放進自然分布。

### 3.3 Ledger 運作

每位玩家、每款遊戲、每個押注層級各持有一個獨立 ledger（記為 `L`）。

**累積**：每一轉投注 `b` 時

```text
L += b × r_r
```

**提領**：發放救援時

```text
提領額 = min(L, 目標金額, 該情境上限)
L -= 提領額
```

- 提領額的定義是**增量**：`救援後該轉最終得分 − 原始自然得分`。不是最終得分全額。
- `L` 不得為負。允許小額透支時，必須設透支上限並由後續投注優先回補，且透支額列入報表。

**精確度**：

```text
實際救援 RTP = Σ提領 ÷ Σb = (Σb × r_r − L_結束) ÷ Σb = r_r − (L_結束 ÷ Σb)
```

誤差只有一項：**未提領餘額 ÷ 總投注**。這是可以直接量測、直接對帳的數字，不需要靠模擬推估。

### 3.4 未提領餘額的處理

未提領餘額是唯一的 RTP 漏損來源，也是公平性的關鍵。建議：

| 情境 | 處理 |
|---|---|
| 新手期結束（第 200 轉） | 新手 ledger 餘額**轉入老手救援 ledger**，不歸零 |
| 玩家長期未進入痛苦階段 | 在階段畢業點（例如第 500 轉）將餘額以一次性 FG 形式結算發出 |
| 玩家中途離開 | 餘額保留，設保留期（建議 180 天），期內回來可繼續提領 |
| 保留期屆滿 | 歸零並列入漏損報表 |

「運氣好所以領不到」不應該變成「運氣好所以 RTP 較低」。畢業結算讓每位玩家的救援回收期望值都等於 `r_r`，這是第 7 節公平性 P1 的實現方式。

### 3.5 Base Config RTP 是最壞情況的下限

必須明確認知的取捨：短生命週期玩家（例如只玩 30 轉）幾乎不會提領，他的實測 RTP 就是 Base Game RTP 加 Link。

因此 **Base Game RTP 不是可以任意壓低的自由變數，它是「玩最少的玩家所體驗到的 RTP」下限**。建議 Base Game RTP 不低於 `92.5%`，並在數學文件中列出「不同生命長度玩家的實測 RTP 曲線」，而不是只列一個 97%。

### 3.6 週期與判定回合

Ledger 已經負責控制成本，週期制的作用縮小為**控制發放節奏**（避免玩家察覺規律）。建議：

- 保留 50 轉週期作為節奏上限：每週期最多提領 1 次。
- 判定回合改為不可預測但可審計：`slot = HMAC(server_secret, player_id ‖ game_id ‖ cycle_index) mod 50`，取值涵蓋整個 50 轉，**不保留固定不判定區**。
- 判定回合命中但實際未提領（Pain Score 未達門檻、或 ledger 餘額不足）時，**不消耗該週期的提領機會**，改為在該週期內重排一次。

固定不判定區必須移除：它等於對外公告安全區，是純粹的套利資訊。

### 3.7 Buy Feature／Super Feature

建議 **BF／SF 的投注不進入救援 ledger，也不計入痛苦窗口統計**，並以獨立的 `r_r_bf` 管理（或設為 0）。

理由：BF／SF 是玩家主動選擇的高變異行為，不是被動承受的痛苦。把 BF 投注納入 ledger 會產生一條套利路徑——用高成本 BF 快速累積 budget，再以 NB 的低成本情境提領。

## 4. 痛苦度量：Pain Score

### 4.1 為什麼不能只用 RTP

RTP 只描述錢的比例。讓玩家關掉遊戲的通常是心理維度：

- 我曾經有 5000，現在只剩 800（回撤）
- 我已經 300 轉沒進 FG 了（節奏斷裂）
- 我連續 40 轉一分沒中（乾旱）

這三項在高波動遊戲上比 RTP 更早出現、也更致命。現行 C 版把「未進 FG 轉數」整條移除，建議以相對倍數的形式加回。

### 4.2 建議公式

四個維度各正規化到 `0 ~ 1`，加權求和：

```text
Pain = w_d·D + w_r·R + w_f·F + w_s·S
```

| 代號 | 維度 | 計算 | 建議權重 |
|---|---|---|---:|
| `D` | 資金回撤 | `(peak_balance − current_balance) ÷ peak_balance`，再對該遊戲 baseline 回撤分布取百分位 | `0.35` |
| `R` | 期望落差 | `1 − percentile(短期窗口 RTP)`，百分位取自該遊戲同窗口的 baseline 分布 | `0.25` |
| `F` | 節奏斷裂 | `min(1, 未進 FG 轉數 ÷ (2 × 該遊戲 FG 平均週期))` | `0.25` |
| `S` | 乾旱 | `min(1, 最長連續無得分轉數 ÷ 該遊戲 baseline P95)` | `0.15` |

- 權重總和必須為 `1`，寫在 Config 而非程式，允許各遊戲微調。
- **所有正規化基準都來自該遊戲自己的 baseline 模擬**，這是跨遊戲可移植的關鍵：規格一份，每款遊戲附一張自己的基準表。

### 4.3 發放階梯

| Pain Score | 提領目標 | 說明 |
|---|---|---|
| `< 0.60` | 不提領 | 尚未進入痛苦階段 |
| `0.60 ~ 0.75` | 目標 = 該遊戲 FG 倍率分布 P40 | 小幅回補，維持節奏 |
| `0.75 ~ 0.90` | 目標 = P60 | 中幅回補 |
| `≥ 0.90` | 目標 = P75 | 大幅回補 |

- 目標金額用**該遊戲 FG 倍率分布的百分位**表達，不寫死 `15x`／`30x`。高波動遊戲給 15x 玩家沒有感覺，低波動遊戲給 30x 又過於突兀。
- 實際提領額 = `min(目標金額, L, 情境上限)`，情境上限見第 5 節。

### 4.4 發放形式

- **加碼式，不是覆蓋式**。在自然結果之上注入增量，帳上唯一定義為增量。現行 D 版的覆蓋式可能讓玩家總得分反而降低（`70% ~ <100%` 那格直接改成 0 分），這既傷體驗也讓成本口徑混亂。
- **包在既有演出裡**。做成「這一把剛好進了 FG」，不要有專屬的救援演出或提示。玩家一旦能辨識救援發生的條件，該條件就成為套利目標。
- **考慮分期發放**。把增量拆成後續 N 轉的加成而非一次結算，可同時降低「拿到就跑」的一次性收割價值，並延長體驗改善的持續時間。

## 5. 反套利設計

### 5.1 總原則

> **救援的計價基準必須是「產生資格的那段歷史的投注成本」，不是「領取當下的押注」。**

現行的「當下押注高於歷史平均就取消」是單一 binary gate，可用緩步爬升押注繞過。Ledger 架構把防護從「規則擋不擋得住」變成「數學上能提領多少」——這是根本差異。

舉例：玩家以最低押注 `$0.2` 空轉 1000 轉試圖養資格，累積的 ledger 僅為 `1000 × 0.2 × 2% = $4`。無論他之後怎麼加押，可提領上限就是 `$4`。不需要任何額外規則。

### 5.2 三道結構性防護

1. **分層獨立 ledger**：小／中／大 Bet 各自累積、各自提領，不可互相挪用。這一條擋掉最經典的手法：低押注養資格、高押注領獎。
2. **份額制而非金額制**：ledger 記錄「以當時 `bet` 為單位的份額」，提領時按當下 `bet` 換算，且**換算率上限為 1**——不得以更高的當下押注放大提領。
3. **窗口加權計價**：情境上限 = `k × 產生痛苦那個窗口的加權平均押注`（建議 `k = 30`），不使用當下這一把的押注。

### 5.3 逐情境檢查表

| # | 套利手法 | 為什麼會有效 | 對應檢查 |
|---:|---|---|---|
| 1 | 低押注養資格、高押注領取 | 資格由 RTP 決定、金額由當下押注決定 | 分層獨立 ledger ＋ 份額換算率 ≤ 1 ＋ 窗口加權計價 |
| 2 | 判定回合前一把加押 | 判定回合可預測 | 判定回合改為 HMAC 決定且涵蓋全 50 轉；提領計價使用窗口加權押注，當下這把不具權重優勢 |
| 3 | 緩步爬升押注規避平均檢查 | 平均押注是移動的，緩慢加押不會觸發 gate | 改用窗口加權計價後此手法失效；另加「押注序列單調性」監控作為異常偵測 |
| 4 | 故意小額快速空轉拉低 RTP | RTP 是比率，小額輸最便宜 | Pain Score 納入絕對回撤維度 `D`；ledger 上限本身限制可提領金額 |
| 5 | 拿到救援立即離場（一次性收割） | 救援是淨正 EV 的離散事件 | 分期發放；離場不沒收餘額（讓「跑」沒有額外收益，也不需懲罰正常玩家） |
| 6 | 多帳號農新手期 | 新手期 RTP 較優且有贈送 | 新手預算掛在裝置／支付工具／IP 群組層級，同群組共用單一新手預算池；新手贈送金額壓低並優先給不可直接提現的形式 |
| 7 | 跨遊戲挑選（A 遊戲養痛苦、B 遊戲領取） | 現行規則明訂跨遊戲合併 RTP | **ledger 改為 per (player, game, bet_tier)**，提領必須發生在產生投注的同一遊戲；痛苦偵測可跨遊戲，提領不可 |
| 8 | 用 BF／SF 洗預算 | BF 單價高、累積快 | BF／SF 投注不進救援 ledger，也不計入痛苦窗口 |
| 9 | 兩人／團隊分工（一人養、一人領） | 資格可轉移則可分工 | 資格與 ledger 綁單一帳號，不可轉移、不可贈與 |
| 10 | 反覆進出遊戲重置窗口 | 窗口是「前 N 轉」，重登可能重置 | 窗口狀態以玩家為單位持續累積，不因 session 邊界、換遊戲或重登入清空 |
| 11 | 用 Extra Bet 倍數放大救援 | EB 的 Total 較高，若以 EB Total 計價則可放大 | 提領計價一律使用 Normal Bet 基準成本，與 Card System 倍率分母口徑一致 |
| 12 | 卡在 ledger 剛好足額的邊界反覆觸發 | 每週期一次提領，維持在門檻邊界可最大化頻率 | 設最小提領門檻（`L < 目標金額 × 0.5` 時不提領，累積到下一週期），避免高頻小額提領 |

### 5.4 平台護欄的定位改變

建議把現行的「平台 RTP > 97% 即取消救援」與「老手 C 增量 > 1pp 即取消」從**即時攔截**改為**監控告警**。

理由：ledger 已在數學上保證收斂，即時攔截唯一的作用是製造「先到先領」的不公平。若實測仍偏離預期，那是程式缺陷或有人正在套利，應該修掉或封鎖，不是靜默地砍掉正常玩家的救援。

保留一個 circuit breaker 作為異常處理：單日救援支出偏離期望超過 3σ 時告警並凍結高額提領，同時觸發人工檢視。這是異常路徑，不是常態設計。

## 6. 跨遊戲移植方式

一份規格套用所有遊戲，差異全部收斂到每款遊戲的一張基準表。

### 6.1 每款遊戲需產出的基準表

由模擬器在數學驗證階段自動產出，寫入 Config：

| 欄位 | 內容 | 用途 |
|---|---|---|
| `rtp_window_dist` | 50／200／500 轉窗口累積 RTP 的分位數 | Pain 的 `R` 維度正規化 |
| `drawdown_dist` | 資金回撤幅度分位數 | Pain 的 `D` 維度正規化 |
| `fg_cycle_mean` | FG 平均觸發週期 | Pain 的 `F` 維度正規化 |
| `dry_streak_p95` | 連續無得分轉數 P95 | Pain 的 `S` 維度正規化 |
| `fg_multiplier_dist` | FG 總倍率分位數（P40／P60／P75） | 發放階梯的目標金額 |

### 6.2 Config 新增區塊

```text
retention
├─ newbie
│  ├─ rtp_share            (r_n)
│  ├─ pain_threshold
│  └─ payout_ladder
├─ rescue
│  ├─ rtp_share            (r_r，依押注層級分別設定)
│  ├─ pain_weights         (w_d / w_r / w_f / w_s)
│  ├─ pain_threshold
│  ├─ payout_ladder
│  ├─ cycle_length         (50)
│  ├─ cap_multiple         (k)
│  └─ min_payout_ratio     (0.5)
├─ ledger_policy
│  ├─ scope                (player × game × bet_tier)
│  ├─ overdraft_limit
│  ├─ retention_days       (180)
│  └─ graduation_spin      (500)
└─ baseline                (第 6.1 節的五張基準表)
```

### 6.3 調性差異的額外調整

以下項目允許各遊戲覆寫，但必須在數學文件註明理由：

- 高波動遊戲可提高 `w_f`、`w_s`（節奏與乾旱是主要痛點），降低 `w_r`。
- 低波動遊戲可提高 `w_d`、`w_r`。
- 極高波動遊戲（最大獎 > 10000x）可提高 `r_r`，因為痛苦階段更長、更頻繁。此時 Base Game RTP 需相應下調，Total 仍維持 `97.0%`。

## 7. 公平性的三條可驗證性質

「公平」必須寫成可以用模擬驗證的性質，否則無法交付檢查。建議定義：

| 代號 | 性質 | 驗證方式 |
|---|---|---|
| **P1** | **期望等價**：同一押注層級、投注總額相同的任兩位玩家，救援回收率期望相同（`= r_r`） | 模擬後將玩家按自然運氣分位分組，各組的救援 RTP 應全部收斂到 `r_r ± 0.05pp` |
| **P2** | **無先後歧視**：救援不因平台預算耗盡而被取消 | 統計「因平台護欄取消」的次數，常態運行下應為 `0` |
| **P3** | **無套利**：任何改變押注序列的策略，都無法使 `E[總回收 ÷ 總投注]` 超過 `97% + ε` | 對抗策略模擬（見第 8.2 節） |

P1 是 ledger 加畢業結算的直接結果。P2 是移除即時攔截的直接結果。P3 需要主動驗證。

## 8. 交付與驗證清單

### 8.1 Ledger 對帳（每次模擬必跑）

```text
Σ提領 + L_結束 + 漏損 == Σ投注 × r_r
```

三項必須逐押注層級、逐遊戲對帳，誤差為 0（浮點誤差除外）。這是機制正確性的第一道檢查，不通過就不必看 RTP。

### 8.2 對抗策略模擬（Adversarial Bot Suite）

第 5.3 節每一行都要有一個對應的 bot，實作該手法並實測其 RTP。這是目前完全缺少、但最重要的新增驗證項目。

| Bot | 策略 |
|---|---|
| `min_bet_farmer` | 全程最低押注空轉 |
| `bet_escalator` | 每 10 轉將押注提高 10% |
| `tier_jumper` | 小 Bet 玩 500 轉後跳到大 Bet |
| `slot_sniper` | 嘗試偵測判定回合並在該回合加押 |
| `hit_and_run` | 取得救援後立即離場並重新開始 |
| `game_hopper` | 在多款遊戲間輪替，各玩 50 轉 |
| `bf_washer` | 以 BF／SF 累積後改用 NB 提領 |
| `boundary_camper` | 維持 Pain Score 在門檻邊界 |

**通過標準**：所有 bot 的實測 RTP 不得超過 `97.0% + 0.3pp`；任一 bot 超標即視為設計缺陷，必須修正規則而非調整參數掩蓋。

### 8.3 報表新增欄位

- 各玩家運氣分位的救援 RTP（驗 P1）
- ledger 未提領餘額分布、畢業結算金額、保留期屆滿漏損
- 各 bot 的實測 RTP（驗 P3）
- Pain Score 分布、各階梯提領次數與金額
- 因 ledger 不足、最小提領門檻、情境上限而縮減或跳過的次數
- 不同生命長度玩家（30／100／200／500／1000 轉）的實測 RTP 曲線

### 8.4 開發前檢查

- [ ] 「總體 RTP 97%」的口徑已依第 1.2 節定義並經確認。
- [ ] 各押注層級的 `Base + Link + r_n + r_r` 加總精確等於 `97.0%`。
- [ ] Base Game RTP 不低於短生命週期玩家可接受的下限。
- [ ] 該遊戲的五張 baseline 基準表已由模擬產出並寫入 Config。
- [ ] Pain 權重總和為 1，且覆寫理由已記錄於數學文件。
- [ ] 判定回合為 HMAC 決定，無固定不判定區。
- [ ] ledger 範圍、透支上限、保留期、畢業結算點已定義。
- [ ] 第 5.3 節十二項套利手法各有對應檢查與對應 bot。
- [ ] Ledger 對帳等式在模擬中誤差為 0。
- [ ] P1／P2／P3 三條公平性性質均已驗證通過。

## 9. 需要先決定的事項

以下四項會影響架構，建議在進入模擬前確認：

1. **合規路徑**：依玩家個人狀態調整結果的機制，在部分送驗市場屬於需揭露或受限制的 adaptive RTP。常見的合規做法是讓 base game 數學保持固定 RTP 單獨送驗，救援以 bonus／free round 形式從行銷預算出帳——ledger 架構本身就是一個 bonus 帳，天然適合這條路徑。需確認各目標市場的實際要求。
2. **ledger 範圍**：本文件建議 per (player, game, bet_tier)，與現行「跨遊戲合併」相反。跨遊戲合併對玩家視角較友善，但會開出第 5.3 節第 7 項的套利路徑，且讓每款遊戲的 97% 無法獨立成立。需就這個取捨做決定。
3. **變異度取捨**：救援預算越大，個人 RTP 越收斂，遊戲刺激感越低。建議 `r_r` 不超過 `3%`，並將發放包在 FG 演出中以維持隨機感。
4. **新手預算的階段內口徑**：`r_n = 0.5%` 是生命週期口徑；由於只在前 200 轉提領，玩家在新手期實際體感的機制 RTP 會遠高於 0.5%。數學文件必須同時列「階段內 RTP」與「生命週期 RTP」兩個數字，避免現行文件中兩種口徑混用的情況再次發生。
