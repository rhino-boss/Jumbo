# Slot 數學開發流程

本文件定義新 Slot 專案的**數學開發流程、製作順序、操作方式、階段產物與完成條件**，也是接手開發者（人或 AI：Claude 或其他模型）的入口：讀完就能在這個工作區開一款新專案、照順序做到交付，並知道每一步用哪個工具、哪裡要停下來問使用者。

實作欄位、命名、版本、Card System、Simulator、Demogame、Config 與報表格式等細節，統一依照 `專案需知/開發規範/` 下的各規範文件（總覽見 [_README.md](../其他/_README.md)）。本文件不重複定義實作規格；內容有差異時，以各規範文件為準。

適用範圍：`Slots/H0xx_遊戲名稱/` 下的新遊戲數學模型、既有模型改版，以及 RTP、Card System、Feature 或 Bet Mode 參數調整。

## 1. 接手須知

### 1.1 閱讀順序

1. 依序讀完以下文件，再動手：
   1. 本文件
   2. [_README.md](../其他/_README.md)：開發規範總覽，有文件清單與專有名詞
   3. [產出與紀錄規範.md](../開發規範/產出與紀錄規範.md)：必要產出、修改紀錄格式、專案目錄
   4. [錯誤清單.md](../開發規範/錯誤清單.md)：過去犯過的錯，新遊戲開工前掃一遍
   5. 產線規範：Omniplay 看 [導覽.md](../開發規範/Omniplay/導覽.md)，Landbase、Reskin 看各自資料夾
2. 接手既有遊戲時，另外讀該遊戲的 `Notes/修改紀錄.md`、`Notes/注意事項.md`。
3. 被問到「之前怎麼決定的」時，先查 [工作紀錄.md](../../../工作紀錄.md)；客戶與內部反饋在 `Slots/其他/一些記錄/反饋紀錄.md`。
4. 不確定的規則一律問使用者，不要從舊遊戲猜。舊專案的命名、版本與報表格式有很多是過渡期做法（見 §2.1）。

## 2. 規則

### 2.1 基本原則

過往專案可看到數種演進中的做法：

- H013、H015、H019 使用 RTP Config、Simulator 與 Record 的基本流程。
- H016、H028 已拆分基礎 `config.js` 與 RTP／Variant Config，並保留 `Versions/`，較符合目前標準。
- H026 同時存在 92／94 與 A／B Variant，適合作為多模型組合的參考。
- 早期專案（H013～H027）曾使用 `xlsx_to_config.py`、`model_sync.py` 等轉檔腳本同步 Source 與程式資料；此做法已淘汰，Excel 與 Config 之間的轉換一律由 AI 執行，專案內不建立、不維護轉檔工具。

新專案採用以下統一原則：

1. `game_rule.md` 定義玩法，數學 XLSX／`Source/` 定義正式參數。
2. Config 必須由 Source 轉出（轉換由 AI 執行，不建立轉檔工具），不直接手改轉出的參數。
3. Simulator 與 Demogame 使用同一份 Config。
4. 先驗證 Card System Off 的自然機率，再驗證 Card System On。
5. 每次調參都依「Source → 版本 → Config → Simulator → Record → 對帳」完整重跑。
6. 舊專案若與目前命名、版本或報表格式不同，不直接複製舊格式；依現行規格建立。
7. `game_rule.md` 是遊戲規則的正式來源，要寫明玩法、判獎順序、倍率口徑、Feature 流程與例外；數學模型、程式與 Help 都要與它一致，程式不可補猜未定義的規則。
8. 同一項資料出現在多個檔案時，修改要同步更新並完成對帳。
9. 未支援的 RTP、Variant、Bet Mode、Profile 或 Feature，不得出現在 Config、Simulator 批次或 Demogame 選單。
10. 會影響結果分布、RTP、觸發率、最大獎或 Retry 的修改，都要更新版本並重新模擬（升版前先問使用者，見 §2.2）。

### 2.2 必問事項

| 情況 | 說明 |
|---|---|
| 跳版本號 | 所有遊戲都不得自行升版。覺得該升時先問；版本號記在 `Source/version.txt`（只寫一行，同遊戲所有模型共用），不寫在 xlsx 裡；各碼何時升見 §5.1 |
| 數學模型組合 | 每款不同，開案時確認（預設 92A／92B／94A／94B，各含 Newbie／Oldhand） |
| 規格參數 | Cascade 階梯、賠率表等不得自改；要改先提出 |
| Game Rule 未定義的規則 | 退回確認，程式不補猜 |
| 調性 | 卡片權重的調性要使用者確認才算完成 |
| 既有遊戲套新規則 | 新規則（例：Math Document Description 改出 DOCX 中英兩版）只套用新遊戲，舊遊戲要改先問 |

### 2.3 禁止事項

- 未確認 Game Rule 就自行補猜核心數學規則。
- 直接修改由 XLSX 產生的 Config 參數來避開轉檔。
- 建立或保留 Excel↔Config、Config↔Excel 的轉檔工具；轉換一律由 AI 執行。
- Simulator、Demogame 與 Config 各維護一套參數。
- 只跑 Card System On，不保留自然機率基準。
- 只驗證 Total RTP，不驗證 RTP Breakdown、分布、Feature 與 Retry。
- Card System Retry 時重抽目標卡、重複扣款或污染場次統計。
- 未升版就覆寫正式 XLSX、Config 或 Record。
- 建立產品未使用的空白 B Variant、Mode 或 Profile。
- 直接複製舊專案的不相容命名、版本、報表欄位或遊戲專屬統計。
- 用全零欄位表示不存在或尚未驗證的功能。

### 2.4 權限與對外

- **模擬機**：只碰 `/root/Simulator`；嚴禁改 sshd、密碼、SELinux。AI 不代打任何密碼。
- **SVN**：AI 只負責把檔案放進 SVN 工作資料夾，commit／上傳由使用者做。
- **git**：只 commit 自己改的檔案，不要把別人進行中的修改一起帶上去。
- **產線隔離**：Omniplay（OP）是使用者團隊負責，Landbase（LB）、Reskin（RS）是外團隊。
  - 三方互不知道對方的數值設定，只有使用者可以看全部。
  - 三站的規範、文件、網頁互不提及、不共用。
- **交給 SPS**：只交 `config*.js` 與 `Simulator.py`，不交 xlsx、PARsheet、json（§4.8）。

### 2.5 檔案

- 不在專案資料夾留 `.bak` 或暫存檔。暫存放 AI 自己的暫存區，驗證完就刪。
- 用程式改數學模型 xlsx 時：
  - 清值要連格式一起清；寫值要從同檔同類儲存格複製樣式。
  - 存檔後跑 `專案需知/其他/_check_xlsx_style.py`，ERROR 必須為 0（見 math-model-xlsx-edit skill）。
- 共用權重欄跨版本必須**逐格完全相同**，不允許 ±1 的整數化尾差；以代表版複製到其他版。A／B 版差異範圍以外的內容也一樣（§4.3）。
- `專案需知/` 的任何 `.md` 改完，同一次修改內都要跑 `py 專案需知/其他/_build_html.py`。這支會重建網頁、發佈團隊版並同步 SVN 說明書；HTML 不得手改。
- 改 `demogame_common.js`／`.css` 時，必須同時升所有遊戲 `index.html` 引用的 `?v=` 版號，否則線上會吃到快取的舊檔。

### 2.6 模擬

- **≥ 10⁶ 局一律到模擬機跑**，本機只跑 ≤ 10⁵ 局的流程測試。
  - Simulator 要用 `ProcessPoolExecutor`；ThreadPool 受 GIL 限制只用到 1 核。
  - 模擬機**一次只跑一個多程序工作**。7 GB RAM 會爆，曾經導致整台卡死。
  - 跑法：`nohup bash run_xxx.sh > run_xxx.log &`，跑完用 `scp` 把 `Record/*.xlsx` 拉回本機。
- 臨時、探索性的模擬只跑 10⁶ 局就回報。正式場次只用在正式文件與解權重（NB 10⁹ 局、BF 10⁸ 局）。
- 驗證規則：
  - 相同權重只跑一筆；BF 不跑 Newbie。
  - 先跑 10⁶ 再跑正式場次。
  - 結果表要有「符合」欄，判定方式見模擬程式規範 §1.2.2。
- 調完卡片權重必查：規格上會出現的元素（例如 1000x／2500x 球），會不會因為卡片上限變成只出現、不得分。

### 2.7 溝通

- 一律用**繁體中文**回覆。回覆只講重點，不要長篇表格與完整推導。
- 使用者改過的檔名以磁碟現況為準，不得改回；產生器的輸出名與所有引用都要跟進新名。
- 時間戳記一律用實際時間（`Get-Date`／commit 時間），不可自編。

## 3. 流程

### 3.1 階段總覽

```flow
遊戲發想
  > 1.1 競品分析 :: 競品數據報告
  > 1.2 提案 :: 提案簡報
  > 1.3 開案 :: game_rule.md、數學目標、模型組合
數學開發
  > 2.1 數學模型製作 :: 數學模型 | 2.2 模擬程式撰寫 :: Simulator.py | 2.3 Demogame 製作 :: index.html
  > 2.4 遊戲調性調整 :: A 版調性（NB／EB／BF／SF）
  > 2.5 調性補齊 :: B 版、老手大／中／小押注、新老手
  > 2.6 文件製作 :: Help、PARsheet、Game Description、Game List、腳本規格、送驗文件
  > 2.7 交付前檢查 :: SPS、數學模型、模擬程式三方一致，玩家不會有爭議
遊戲上線
  > 3.1 數據觀察 :: 上線觀察
  > 3.2 Demo 報告 :: Demo 報告 pptx
```

2.1～2.3 同時開發，三者要互相對帳（Source、Config、Simulator、Demogame 一致）才進 2.4。其餘不得因為某個程式可以先寫就跳過前置規則。上一步的條件成立、並通過 §3.2 檢查後，才進入下一步。標 **停** 的條件必須由使用者確認。

**交付前檢查：玩家看到的結果必須跟規則一致**。規則上看得到、玩家會以為能得分的東西，實際上就要能得分；不能出現「規則可以得分、實際沒得分」或「出現了卻永遠不會得分」的情況。過去的例子：

- BF 按下後的進場盤（BG spin）出現了符合得分條件的盤面，但程式邏輯一律不得分，玩家會看到規則上該得分卻沒得分。進場盤要靠輪帶本身保證不得分。

**過程中的紀錄**：修改紀錄、注意事項、上線觀察，從開案到上線的每一步都要記錄（位置見 §5.2）。

交付之後：

- **送驗**：收到 Draft／Letter 時用 `submission-intake` 歸檔、檢查、更新狀態（串 `inspection-report-checker`、`report-file-management-ctool`、`submission-status-overview`），各關卡停下來給使用者確認。
- **進測**：PARsheet R 檔與 Source 原檔放進 SVN 對應資料夾（§1.2），由使用者自己 commit。

## 4. 製作

### 4.1 開案

1. 在 `Slots/` 建立 `H0xx_遊戲名稱/` 專案資料夾。
2. 讀取並確認 `game_rule.md`。
   - 建立 `Notes/注意事項.md`：讀 [錯誤清單](../開發規範/錯誤清單.md)，把本作可能再犯的列進「二、錯誤清單提醒」（格式見[產出與紀錄規範](../開發規範/產出與紀錄規範.md)第 1 節）。
3. **與使用者確認本專案的數學模型組合**——每款遊戲的數學模型都不一樣，不得逕自沿用他款設定。未特別說明時，預設組合為：
   - A／B 兩個 Variant × 92／94 兩個 RTP，乘開共 **4 個版本**（92A、92B、94A、94B）。
   - 每個版本都有 Newbie／Oldhand 兩種 Profile。
   - 各版本依其支援內容有對應的押注區（Oldhand 小／中／大 Bet 層級）。
   - **定義 A／B 版的差異範圍**：寫明 A、B 差在哪些地方（新手期、老手期、哪些押注模式或押注層級）。差異範圍以外的內容 A、B 必須一模一樣；例如只設計老手期差異時，新手期的 A、B 版內容要完全相同。
4. 列出所有正式支援組合：RTP、Variant、Profile、Oldhand 小／中／大 Bet、NB／EB 或 BF／SF 模式類別、Bet Mode、Card System Off／On。
5. 為每個組合定義 Link／Bonus Game／Game RTP、Total RTP、Link 資格、Hit Rate、Feature Frequency、BG／FG Max Multiplier 與其他遊戲專屬指標。
6. 將未決定的判獎順序、倍率分母、Feature 上限與例外退回確認；未確認前不製作正式模型。

### 4.2 基礎模型

1. 先完成 Base Game，再依狀態順序完成 Feature。
2. 建立 Symbol、Paytable、Reel Strip／Weight、Table 與 Bet Mode。
3. 建立 BG、FG、Cascade、Multiplier、Retrigger、Jackpot 等流程。
4. 計算 RTP Breakdown 與理論 Max Win，不只計算 Total RTP。
5. 建立基礎數學 XLSX；建立 `Source/version.txt`，初始版本見 §5.1。

### 4.3 RTP／Variant 與 Card System

1. 只建立 §4.1 與使用者確認過的 92／94、A／B 組合（未特別說明時為 92A、92B、94A、94B 四版本，各含 Newbie／Oldhand 與對應押注區）。
2. A／B 表示數學 Variant，不表示 Newbie／Oldhand。只在開案定義的差異範圍內不同；範圍外（例：只設計老手期差異時的新手期）以 A 版為代表逐格複製到 B 版，不得有任何差異（同 §2.5 共用權重欄規則）。
3. 依 Profile、Oldhand 小／中／大 Bet 與 Bet Mode 建立 BG／FG 卡片區間及權重；NB／EB 以實際模式押注、BF／SF 以 Feature 基礎押注選擇層級。
4. 確認每張正權重卡片的區間可達，並定義 Retry 行為。
5. 建立 RTP／Variant XLSX，與基礎模型共用 `version.txt` 的版本。

### 4.4 Config

1. 在數學模型的 `Game Description` 工作表記錄每項 Config 資料的來源。
2. 由 AI 依 Source 與 Mapping 轉出 Config；專案內不建立、不維護 Excel↔Config 轉檔工具。
3. 執行欄位、型別、陣列長度、ID、Weight、Min／Max、版本與模式驗證。
4. 比較轉檔前後資料，確認 Config 可由 Source 重建且沒有非預期差異。
5. 轉檔錯誤時修正 Source 或 Mapping 後重新轉出，不直接修改 Config 大型陣列。

### 4.5 Simulator

1. 先完成自然機率核心，再加入 Card System 篩選與 Retry。
2. 讓 Simulator 直接讀取正式 Config，不另寫一份參數。
3. 建立固定 Seed、單執行緒與逐局 Trace 模式。
4. 建立強制／指定案例，驗證無獎、一般獎、Wild、Scatter、Feature、Retrigger、倍率與封頂。
5. 小場次確認正確後，再加入 Numba、多程序（`ProcessPoolExecutor`）、BATCH_RUNS 與 Excel 報表。

### 4.6 模擬順序

模擬必須依下列順序執行（≥ 10⁶ 局到模擬機跑，見 §2.6）：

1. 小場次、Card System Off：驗證流程與報表。
2. 中場次、Card System Off：確認自然機率 RTP 與分布。
3. 大場次、Card System Off：以 NB 10⁹ 局（BF 為 10⁸ 局）產出自然機率正式報表。
4. 卡片權重調性校準：依上一步報表分配各得分區間的卡片權重，使分布、RTP 拆分與 FG 週期符合目標遊戲調性；完成後才進入 Card System On。
5. 小場次、Card System On：確認抽卡、Profile、Oldhand 押注層級、Link 資格、倍率上限、Mode 與 Retry。
6. 中場次、Card System On：調整區間、權重與目標 RTP。
7. 所有正式組合的大場次模擬。
8. Max Win、低機率 Feature 與 Retry 邊界的專項驗證。

最低批次矩陣：正式組合是「新手／老手 × A／B 版 × NB／EB／BF／SF × 老手小／中／大押注」的排列組合（BF／SF 不跑新手），每個存在的組合都要有一筆。

| 類型 | RTP／Variant | Profile | `bet_tier_amount` | Bet Mode | Card System |
|---|---|---|---|---|---|
| 自然機率基準 | 基礎 Config | 不適用 | 各門檻所需代表值 | 每個支援 Mode | Off |
| Newbie | 每個正式 RTP／Variant | Newbie | 不分層級，但仍記錄判定金額 | 每個支援的 NB／EB（BF／SF 不跑 Newbie） | On |
| Oldhand 小 Bet | 每個正式 RTP／Variant | Oldhand | `< $2`，至少驗證 `$1.99` | 每個支援的 NB／EB／BF／SF | On |
| Oldhand 中 Bet | 每個正式 RTP／Variant | Oldhand | `$2～$100`，至少驗證 `$2`、`$100` | 每個支援的 NB／EB／BF／SF | On |
| Oldhand 大 Bet | 每個正式 RTP／Variant | Oldhand | `> $100`，至少驗證 `$100.01` | 每個支援的 NB／EB／BF／SF | On |

- NB／EB 的 `bet_tier_amount` 使用實際模式押注金額；BF／SF 使用 Feature 購買價格除以 Feature Price 倍數後的基礎押注。
- 若遊戲支援 EB 2x，至少驗證 base bet `$1` 會以 `$2` 判為中 Bet。
- 若遊戲支援 BF 75x，至少驗證購買 `$75` 判為小 Bet、購買 `$150` 判為中 Bet。

不存在的 Mode、Profile 或 Variant 不建立空批次，也不以全零結果冒充驗證完成。

### 4.7 調參循環

每一次調參都執行完整循環：

```text
確認差距與原因
    ↓
修改對應 Source XLSX（跑 _check_xlsx_style.py）
    ↓
先問使用者是否升版；要升就改 version.txt
    ↓
重新產生 Config，執行轉檔與資料驗證
    ↓
本機跑小場次確認流程
    ↓
到模擬機跑中／大場次確認統計
    ↓
保存新 Record 並與前版比較
    ↓
寫修改紀錄
```

**只給目標時出 5 個版本**：使用者只說明目標（例：「R3 特色出現時 Hit Rate 拉高多少」「特色多出一點」），沒指定改哪裡時，AI 自己找可調的參數，調出 **5 個版本**，附指標對照表（現行版＋5 個候選，列出目標指標與會被連帶影響的指標，如 RTP、Hit Rate、FG 週期）讓使用者挑；探索階段每版只跑 10⁶ 局，挑定後才照上面的循環升版、跑正式場次。

調參時依序判斷：

1. 先確認程式與統計口徑是否錯誤。
2. 再檢查自然機率的 Paytable、Reel、Table、Feature。
3. 最後才調整 Card System 區間與權重。
4. 不得只為讓 Total RTP 接近目標而忽略 RTP Breakdown、Hit Rate、Feature Frequency、分布或 Retry。

會改到哪些東西、要重跑什麼，查 §5.1。

### 4.8 對帳與交付

卡片權重完成後出數值報告（[數值報告規範](../開發規範/數值報告規範.md)）；上線後出 Demo 報告（步驟 3.2）（[Demo報告規範](../開發規範/Demo報告規範.md)）。

1. 選定可重現的代表性 RNG／Seed。
2. 逐項核對 Config、Simulator 與 Demogame 的盤面、判獎、Feature、倍率、Total Win、Coin In 與 Retry。
3. 完成所有正式組合的最新 Record。
4. 將正式 Config 與歷史版本關係寫入 `Versions/` 與 manifest。
5. 確認[產出與紀錄規範](../開發規範/產出與紀錄規範.md)第 1 節的必要產出文件全部齊備且為同一正式版本。
6. 清除暫存檔、舊測試輸出及不屬於正式交付的檔案。
7. 依 §5.4 完成最終驗收。

**交付 SPS 打包**（步驟 2.7 交付前檢查；2026-10-22，以 H020 超級寶石為範例）

- 放在 `Output/To SPS/`，每次交付打成**一個 zip**：`<GameID>_<RTP／Variant 四碼版本去點>.zip`（例：`101007_2220.zip`＝2.2.2.0、`101015_6000.zip`＝6.0.0.0）。
- zip 內只放：`config.js`、該遊戲所有 `config_<RTP><Variant>.js`、`Simulator.py`、`給SPS說明_<四碼版本>.txt`；不放數學模型 XLSX、PARsheet、報表、json。
- `給SPS說明_<版本>.txt` 寫：與上一個交付版本的差異（基礎數學、規則／程式要後端同步的地方、卡片權重）、驗證目標與我方 Card-On 結果（判定見模擬程式規範 §1.2.2）。
- 舊版 zip 保留不刪（追溯用）；`To SPS/` 內不留散檔，只放各版 zip。
- 驗證結果確定後才打包；打包後重新交付須換新版本號，不得覆寫已交付的 zip。

**挑 BF 腳本：提供累積權重範圍**（步驟 2.6 文件製作的腳本規格；2026-10-28，以 H045 超級鑽石為範例）

- 挑腳本階段**不改數學模型**，只讀現行 `config_<RTP><Variant>.js` 的 Card System。
- 主動提供**最接近 BF 平均倍數的兩個區間**：BF 平均倍數 ≈ 購買價 × BF RTP 目標（例：H045 為 50 × 92.5% ≈ 46x → `(40, 45]`、`(45, 50]`）。
- 每個區間**只給一個數字**（骰 0～總權重 − 1 的累積權重值），**數字不加千分位逗號**。
- 數字的算法：依 config 卡片順序從 0 累加，某區間的範圍＝`[前面所有卡權重加總, 前面加總＋本格權重 − 1]`，骰到範圍內就開該區間（與 Simulator `pick_card` 相同）。

- 新手卡片若與老手相同要註明。

## 5. 交付與紀錄

### 5.1 異動重跑

版本統一記在 `Source/version.txt`（同遊戲所有模型共用一個四碼版本），詳見[數學模型規範](../開發規範/Omniplay/數學模型規範.md) §1.3。升某一碼時後面的碼歸零；所有升版都要先問使用者（§2.2）。

| 異動 | 版本 | 必做流程 |
|---|---|---|
| 調性調整：改自然機率參數（Paytable、Reel、Table、Feature、Bet Mode、判獎） | 第 1 碼 | 改 Source → 轉全部 Config → 全部受影響批次重跑 → Demogame 對帳 |
| 調性調整：改倍率權重，且調性差異大 | 第 2 碼 | 改受影響 RTP／Variant XLSX → 轉 Config → Card System On 批次重跑 → 檢查占比與 Retry |
| 補 SCR | 第 3 碼 | 改受影響 RTP／Variant XLSX → 轉 Config → 重跑 SCR 相關批次 |
| 其他修正（含倍率權重位數錯位、只差一點點的微調；文件、說明或排版） | 第 4 碼 | 依影響範圍重跑；不影響執行結果時，不沿用舊版號產生新正式報表 |
| Simulator 數學邏輯 | 依造成的結果判斷 | 修正程式 → 固定 Seed 回歸 → 小場次 → 所有受影響正式批次 → Demogame 對帳 |
| 報表或顯示邏輯 | 不升版 | 驗證統計來源未變 → 核對 Console 與 Excel → 依影響範圍重產報表 |

### 5.2 產出與紀錄

每個專案必須產出的文件與 `修改紀錄.md` 格式見[產出與紀錄規範.md](../開發規範/產出與紀錄規範.md)。紀錄寫在：

| 紀錄 | 位置 | 寫什麼 |
|---|---|---|
| 修改紀錄 | 各遊戲 `Notes/修改紀錄.md` | 只記數學調性；依四碼版本分節，句尾附日期（產出與紀錄規範 §2） |
