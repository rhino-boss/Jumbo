# 卡片系統說明書

## 1. 文件目的

本文件用來說明 slot 遊戲中的「卡片系統（Card System）」共通設計。

此系統的用途不是新增一套獨立玩法，而是為模擬、驗證、報表或分流控制提供一層「結果篩選規則」。
系統會先照遊戲原本的盤面流程產生結果，再依照預先抽到的卡片條件，判斷該結果是否可接受；若不符合，則重跑本局，直到符合條件或達到重試上限。

本說明書刻意不綁定特定遊戲、特定盤面、特定 RTP 版本或特定程式架構，可作為新遊戲導入卡片系統時的通用規格基底。

---

## 2. 卡片系統的定位

卡片系統本質上是「結果目標控制機制」，常見用途如下：

- 控制某一局結果要落在哪個倍率區間
- 控制某一局是否必須觸發免費遊戲
- 區分不同玩家輪廓或分流條件
- 區分不同下注模式下的結果分布
- 讓模擬結果更貼近指定的分群目標

卡片系統通常不直接改寫以下核心規則：

- 輪帶內容
- 消除 / 連消邏輯
- 賠付表
- Wild / Scatter / Multiplier 的原始判獎規則
- 免費遊戲本身的演出流程

換句話說，卡片系統通常是「結果產生後的接受條件」，不是「盤面生成規則本體」。

---

## 3. 基本流程

一個通用的卡片系統流程可分成以下步驟：

1. 先決定本局的執行模式。
   常見如 `Normal Bet`、`Extra Bet`、`Feature Buy`。
2. 依玩家分群或設定，決定要使用哪組卡片 profile。
   常見如 `newbie`、`oldhand`、一般玩家、測試玩家等。
3. 從對應 profile 依權重抽出一張卡片。
4. 按照遊戲原本流程跑完這一局，取得 BG / FG / BF 等結果。
5. 用卡片條件檢查結果是否符合。
6. 若符合則接受本局結果。
7. 若不符合則重跑本局。
8. 若重跑次數達上限仍不符合，則保留最後一次結果，並記錄 retry limit 命中。

---

## 4. 卡片的常見種類

卡片系統通常至少有以下兩類卡片：

### 4.1 區間卡 `range`

用途：
要求某段結果的倍率必須落在指定區間內。

常見欄位：

- `type`: `range`
- `min`: 區間下限
- `max`: 區間上限
- `weight`: 抽到這張卡的權重

判定方式常見為：

- `multiplier > min`
- `multiplier <= max`

也就是使用 `(min, max]` 這種半開半閉區間。

### 4.2 事件卡 `free_game`

用途：
要求本局必須觸發某個事件，最常見的是 `Free Game`。

常見欄位：

- `type`: `free_game`
- `weight`: 抽到這張卡的權重

判定方式常見為：

- 本局必須成功觸發 FG
- 若未觸發 FG，則視為不符合條件並重抽

### 4.3 可擴充的事件卡

在不同遊戲中，也可以擴充成其他事件型條件，例如：

- `bonus`
- `jackpot`
- `respin`
- `collect_feature`
- `special_symbol_hit`

但原則不變：卡片定義的是「結果條件」，不是畫面表現。

---

## 5. Profile 的概念

卡片通常不會只有一組，而是依不同情境拆成多組 profile。

常見拆法如下：

- 依玩家分群：`newbie` / `oldhand`
- 依下注模式：`normal_bet` / `extra_bet`
- 依場景：`bg` / `fg` / `buy_feature`
- 依版本：A / B / 特定 RTP

通用原則：

- BG 用 BG profile
- FG 用 FG profile
- Feature Buy 用 BF profile
- Extra Bet 若與 Normal Bet 目標分布不同，應有獨立 profile

如果沒有獨立 profile，通常才回退使用一般 profile。

---

## 6. 卡片系統的判定單位

導入卡片系統前，必須先明確定義「卡片在檢查哪一段結果」。

常見有三種：

### 6.1 BG 判定

只看 Base Game 本身結果。

適用於：

- 希望控制 base spin 倍率分布
- 希望控制是否由 BG 觸發 FG

### 6.2 FG 判定

只看 Free Game 總結果。

適用於：

- 希望控制免費遊戲包的總倍數
- 希望控制某個 FG profile 的高低區間

### 6.3 單局總和判定

看本局最終總結果，例如：

- `pay_total = pay_bg + pay_fg`

適用於：

- Feature Buy
- 直接購買功能
- 任何以整包結果為主的模式

這件事一定要先定義清楚，否則很容易出現：

- 設計以為卡片在控總分
- 程式其實只在控 BG
- 文件寫成控 FG

三者互相不一致。

---

## 7. 乘數 / 倍率的分母定義

卡片系統最容易出錯的地方之一，是「倍率分母」。

倍率通常定義為：

`multiplier = score / coin_in`

但必須明確規定 `coin_in` 到底取哪一個值。

常見做法有兩種：

### 7.1 直接用實際成本

例如：

- `Normal Bet` 用正常下注成本
- `Extra Bet` 用加價後成本
- `Feature Buy` 用購買成本

這種做法直觀，但不同模式下倍率分布會被不同成本基準影響。

### 7.2 統一用基準成本

例如：

- `Extra Bet` 實際成本雖較高
- 但卡片系統判定時仍以 `Normal Bet` 的基準成本當分母

這種做法常用於：

- 希望不同模式共用同一套倍率區間邏輯
- 希望卡片分布不要因下注價格改變而整體偏移

因此每個遊戲都必須明確定義：

- 實際結算成本
- 卡片判定成本

這兩者可以相同，也可以不同，但不能模糊。

---

## 8. Retry 機制

卡片系統的核心行為是「不符合就重跑」。

因此必須設計 retry 機制。

建議至少包含：

- `enabled`: 是否啟用卡片系統
- `retry_limit`: 單局最多可重跑幾次
- `retry_fail_reason`: 失敗原因
- `retry_total`: 本局實際重跑次數

常見失敗原因：

- BG 未命中倍率區間
- BG 應觸發 FG 但未觸發
- FG 倍率不符
- BF / 總包倍率不符

設計重點：

- retry limit 太小，目標分布可能達不到
- retry limit 太大，模擬效率會急遽下降
- 權重設定不合理時，會造成大量卡片永遠撞不到

因此卡片權重、遊戲數學模型與 retry_limit 必須一起看，不能分開調。

## 9. 建議資料結構

以下是通用版概念結構：

```json
{
  "card_system": {
    "enabled": true,
    "retry_limit": 5000,
    "profiles": {
      "newbie_bg": [
        { "type": "range", "min": 0.0, "max": 1.0, "weight": 100 },
        { "type": "range", "min": 1.0, "max": 5.0, "weight": 30 },
        { "type": "free_game", "weight": 5 }
      ],
      "newbie_fg": [
        { "type": "range", "min": 0.0, "max": 10.0, "weight": 50 },
        { "type": "range", "min": 10.0, "max": 50.0, "weight": 20 }
      ],
      "oldhand_bg": [
        { "type": "range", "min": 0.0, "max": 1.0, "weight": 90 }
      ],
      "buy_feature": [
        { "type": "range", "min": 20.0, "max": 100.0, "weight": 100 }
      ]
    }
  }
}
```

實作時可依專案需求改名，但建議保留以下資訊：

- 是否啟用
- 重試上限
- profile 名稱
- 卡片類型
- 區間上下限
- 權重

## 10. 實作原則

### 10.1 先抽卡，再跑結果

推薦流程是：

1. 先決定本局 profile
2. 先抽出目標卡
3. 再跑本局結果
4. 最後驗證是否符合

這樣可以明確表達：
本局是朝哪種結果目標去驗證。

### 10.2 卡片只負責驗證，不負責產圖

卡片系統不應直接介入：

- 停輪
- 排版
- 特效
- UI 顯示

除非遊戲明確要求卡片系統參與內容生成，否則應將它維持在「結果驗證層」。

### 10.3 Profile 命名要能直接看懂

不建議只用：

- `profile_1`
- `profile_2`
- `group_a`

建議改成：

- `newbie_bg`
- `oldhand_fg`
- `extra_bet_bg`
- `buy_feature`

讓規格、程式、報表可以互相對應。

### 10.4 報表要能看見卡片系統狀態

輸出結果建議至少紀錄：

- `card_system on/off`
- 使用的 profile
- bet mode
- retry 次數
- 是否 hit retry limit

否則後續很難驗證數學結果是否真的受卡片系統影響。

---

## 11. 文件撰寫建議

若要把卡片系統寫進遊戲規則文件，建議分成四段：

### 11.1 目的

說明卡片系統是為了：

- 分群控制
- 模擬驗證
- 結果分布控制

### 11.2 套用範圍

明確寫出哪些模式會套用，例如：

- Normal Bet
- Extra Bet
- Feature Buy

### 11.3 判定方法

寫清楚：

- 是看 BG、FG 還是總包
- 是看倍率區間還是事件觸發
- 分母使用哪種成本

### 11.4 失敗處理

寫清楚：

- 不符合條件時會重抽
- 有 retry limit
- 達上限後如何記錄

---

## 12. 最容易出錯的地方

以下是卡片系統最常見的誤判點：

### 12.1 以為卡片系統是改 RTP，本質上其實是重抽條件

卡片系統會影響最終分布，但它通常不是直接改 paytable 或 reel。

### 12.2 沒分清楚 BG / FG / BF 的判定段

同一套卡片名稱，可能實際在不同段落生效。

### 12.3 沒分清楚實際成本與卡片判定成本

這會直接導致倍率區間全部偏掉。

### 12.4 只改 profile 權重，沒看 retry limit

權重再漂亮，只要遊戲本體打不到那個區間，一樣會大量重抽失敗。

### 12.5 文件、config、runtime 三邊不同步

最常見的錯誤組合是：

- 文件寫 A
- config 配 B
- 程式實際跑 C

因此卡片系統的檢查一定要同時對：

- 規格文件
- 設定檔
- Runtime 實作

---

## 13. 導入新遊戲時的檢查清單

導入卡片系統前，建議逐項確認：

1. 是否真的需要卡片系統，而不是單純改數學模型
2. 卡片要控制的是 BG、FG、BF 還是總包
3. 是否需要依玩家分群拆 profile
4. 是否需要依 bet mode 拆 profile
5. 倍率分母使用實際成本還是基準成本
6. retry_limit 設多少合理
7. 報表是否會記錄 retry 與 profile
8. 文件是否已明確描述卡片條件與失敗處理
9. config 是否與 runtime 實作一致
10. 若卡片關閉，遊戲是否仍能正常執行

---

## 14. 通用結論

卡片系統是一個通用的結果控制框架，可以套用到不同 slot 遊戲中。

它最重要的三個核心觀念是：

1. 先抽目標卡，再驗證結果
2. 不符合條件就重跑
3. 所有規則都要明確定義判定段、倍率分母與 retry 行為

只要這三件事定義清楚，卡片系統就能在不同遊戲之間重複使用，而不會因遊戲主玩法不同就失去一致性。
